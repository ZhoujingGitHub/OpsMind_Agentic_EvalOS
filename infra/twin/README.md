# OpsMind M2 协议级数字孪生运行时

该目录是 M2 Twin-T1 的确定性“考场控制器”，不是被测 Agent 的诊断工作流。

- Agent 仍由 Claude Agent SDK + DeepSeek 的模型循环自主选择假设、MCP、Skill 和停止时间。
- 控制器只负责冻结版本、准备场景、隔离 Trial、故障注入、只读观测、PCAP 和确定性重置。
- 调用方只能提交经过校验的 `health/prepare/observe/snapshot/reset` 请求，不能提交 shell、路径、服务名或任意网络规则。
- `evalos-twin` 用户只有执行 `/usr/local/sbin/opsmind-twinctl` 的 sudo 权限。
- Trial 证据目录不在 reset 中删除，便于形成 append-only 证据链。
- 整个物理实验室只认 `/srv/opsmind-twin/physical-lease.json` 这一份租约。LangGraph、Agent+Harness
  和 EvalOS 都只能引用它，不能各自生成第二份租约。
- 租约持久化记录使用模式、候选产品、EvalOS Trial、内部 Trial、唯一 lease、到期时间和主机
  boot_id。主机重启、租约过期、文件损坏或首次从旧版升级都会进入 `quarantined`；管理员必须执行
  固定的 `recover` 请求，完成确定性基线复位后才能重新变为 `idle`。
- 两套真实候选产品始终使用各自原生的协议实验室 MCP 身份调查；EvalOS 不代理工具调用，
  也不把考务管理身份借给候选产品。
- EvalOS 的考务管理器只有 `status/prepare/snapshot/reset` 四个操作。它准备独占物理租约后，
  只把公开租约编号交给运行面核对，不提供候选 SSH 授权、远程观察或远程健康监督入口。
- 两套产品每 60 秒向 EvalOS HTTPS 入口发送独立 Ed25519 签名的短时状态。状态只保存在
  EvalOS 内存 180 秒，说明产品身份、版本、就绪状态及当前 Trial/租约绑定；不包含调查证据、
  Case、Seed、答案、凭据或修复权限。

组件版本、官方来源和 UERANSIM 源码哈希记录在 `stack.manifest.json`。

## 控制器版本与回滚

开发期只使用一套很小的版本机制，不新增服务和数据库：

1. 先获产品经理发布批准，核验与已上线版本的血缘关系，提交并推送准确候选。在没有未提交代码的分支上运行 `python3 infra/twin/build-controller-release.py`；正常新包只取准确 HEAD 的 Git 文件，不取工作区临时文件。
2. 构建结果记录完整 Git 版本、9 个固定文件（8 个运行文件/基线配置和安装工具源码）、逐文件摘要和组件清单摘要。安装工具源码随包归档，但不能从版本包内执行或切换为安装入口。
3. 服务器只使用 `/opt/opsmind-twin-controller/current` 与 `previous` 两个活动指针，指向保存好的完整版本目录；目录内容不覆盖。没有两份不同且完整验证的版本，就不能声称可以回退。
4. 统一入口 `/usr/local/sbin/opsmind-twin-install-release` 是单独部署、由 root 保护的普通文件，只提供 `status`、`install`、`rollback`。发布时另核验这个入口的准确摘要；它不随控制器回退，否则退到历史包可能连版本管理能力一起丢失。
5. 安装与回滚复用核心已有的 `/run/lock/opsmind-twin.lock`，并读取唯一物理租约：必须为空闲、没有残留占用信息、启动号与当前主机一致。忙碌、损坏或重启前的记录直接拒绝；安装器不修租约、不复位考场，也不建立第二套监督。
6. 包的完整性检查在修改运行文件前完成，实际处理与校验使用同一份包内容；拒绝多余文件、链接、越界路径、错误摘要或版本冲突。切换失败恢复原来的入口与版本指向，恢复失败明确报错，不假报成功。
7. `status` 只核验版本归档、实际运行入口文件和安装工具摘要，不探测实验进程。`health` 与 `lease_status` 中的版本字段继续由既有控制器读取；`legacy-unversioned` 表示没有规范版本身份，不等于代码必定错误，也不代表真实链路验收通过。

### 首次将已有实验室纳入版本保存

这不是回滚实验数据，也不是重装实验室。首次替换现有普通文件之前，必须先保全其准确源码版本：

- 使用同一个打包工具的 `--baseline-ref accepted-twin-controller-20260901-physical-lease` 生成旧版恢复包；只接受明确的实验室验收/生产标签，并检查其为当前候选的祖先。工具直接读取该准确提交，不切分支、不合并旧分支。
- 新包正常从 HEAD 构建。分别记录两包的准确版本、路径和摘要，不能把最后生成的摘要复用于另一包。
- 在经批准的管理员操作中，将已验证的新安装工具部署到上述固定入口，再调用 `install NEW_ARCHIVE NEW_RELEASE_ID NEW_SHA256 --baseline OLD_ARCHIVE OLD_RELEASE_ID OLD_SHA256`。
- 安装器核对现场 8 个普通文件与旧包完全一致，先保存旧版，再将运行入口指向旧版，最后统一切换新版本。任何不一致都停止，不把现场未知代码冒充已验收版本。
- 正常后续升级仅使用 `install ARCHIVE RELEASE_ID SHA256`；`--baseline` 只用于首次纳管。普通切换异常会恢复原状；进程在首次绑定中途被强制终止时，已绑定与未绑定的入口仍保持旧内容，复核后可继续安装。两指针尚未切完时可能暂时相同，此时如实报告不能回退，不虚构上一代。
- `rollback` 只切换控制器代码和基线配置，重新核验目标全部文件；不会执行历史包的安装脚本，不改物理租约、实验数据、Trace、账本、密码或修复权限，不删除历史版本。它不代替核心已有的考场复位/重启恢复。

该入口只负责已有实验室的版本保存、切换和恢复；不创建账号、不改 sudo 权限、不加载内核模块、不改系统网络参数。缺少既有主机条件时停止，不能偷偷将升级变成主机重建。

### 本地验证边界

`python3 -B -m unittest discover -s infra/twin -p 'test_*.py'` 在 Linux 临时目录运行发布测试；真实使用本地文件、符号链接和文件锁，但实验室路径、包、租约与故障均为隔离夹具。此测试不访问云端、不启动 Trial，不证明真实断电或服务器部署已经验收。正式发布仍需单独批准和现场验收。

仓库不再保存手工打包且来源不明的控制器压缩包。构建产物只生成在被 Git 忽略的 `.deploy/twin-controller/`，通过版本身份和摘要交付。
