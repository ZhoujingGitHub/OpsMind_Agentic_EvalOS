## 5. LG 数据面根因：已确证（不再是假设）

### 5.1 同轮三点抓包（16:13:39Z–16:13:55Z，N2 已修复之后）

三点共 31 包，**全部出方向，零回包**。`ping -I uesimtun0` 对 MEC 与 DNS 均 100% 丢包，`curl --interface uesimtun0` 失败。

pcap SHA-256：
- `lg-ue-tunnel.pcap` `d555fbf971ef788c9ad405306a36394a7990d3ca4f1a09fc70c9b81a7c4d11ad`

### 5.2 完整因果链

共享控制器 `infra/twin/opsmind_twinctl.py:385-386` 在主机全局安装：

    iptables -t nat -A POSTROUTING -s 10.45.0.0/16 ! -o ogstun -j MASQUERADE

AH 的拓扑脚本在 prepare 时于 nat POSTROUTING **第 1 位**插入：

    iptables -t nat -I POSTROUTING 1 -s $UE_NET -d $SERVICE_NET -o ah-host-a -j ACCEPT

nat 表中 ACCEPT 终止链遍历 → AH 的 UE 源地址保持 `10.45.x.x` → MEC 的回程路由 `10.45.0.0/16` 命中 → 包能回。

LG 的拓扑脚本**只操作 filter 表 FORWARD 链**（全文 4 条 iptables 语句），nat 表一条都没有 → 共享 MASQUERADE 生效 → 源被改写为 `lg-host-a` 的 `10.60.0.1`。

MEC 命名空间 `opsmind-lg-mec` 的全部路由：`10.45.0.0/16 via 10.60.0.13` 与 `10.60.0.12/30` 直连，**无默认路由** → 对 `10.60.0.1` 无路可回 → 有去无回。

### 5.4 与 AH 的业务结果对照（同日、同场景、同症状）

### 5.5 重要：数据面实际有两个叠加问题

1. UE 路由表缺少到 `10.46.0.0/24` 的路由，也无默认路由 → 普通（未绑设备）流量在内核路由查找阶段即 `Network unreachable`
2. 即使绑定 `-I uesimtun0`（`SO_BINDTODEVICE` 绕过路由查找，包确实发出），MASQUERADE 改写源地址后 MEC 无法回包

LG Agent 诊断出的是问题 1，其提案 `route.restore_path(n6)` 只能修问题 1。**两个都必须修**，否则业务仍不通。这与既有分析文档「该动作并不补 UE 源端路由、不应强行放行」的判断一致，但现在有了机制层面的准确区分。

### ④ 的新发现：EvalOS 环境侧硬门也被同一个 task_success 语义污染

链路④ 的 `task_success` 断言证据里同时写着：

    "environment_recovery": true,
    "environment_task_applicable": true,
    "change_policy_passed": true,
    "write_operations": 1, "max_write_operations": 1
    "actualStatus": "inconclusive"

并且硬门 `environment_task_success: true`、`recovery: true` **都通过了**。

但同一轮我用三点抓包证明：UE 到 MEC/DNS 的 ping、DNS、HTTP **全部 100% 失败**，MEC 收到的是被改写的 `10.60.0.1` 且零回包。

**含义：EvalOS 的环境侧硬门继承了共享控制器对 `sctp-blocked` 的窄 `task_success` 定义（不含 ping/dns/http），因此在数据面彻底不通的情况下判定"环境已恢复"。**

本轮 ④ 之所以失败，失败点**全部在报告侧**（root_cause 为空 → rca_quality 0 → task_outcome/expected_status 失败）。
推论：**如果 LG 只是把 root_cause 填上、其余不变，分数会显著上升，而业务仍然完全不通。** 这是一个评分完整性风险，必须与 P0-2 一起修，不能只修 LG 的报告侧。

此项列为 **P0-新增**：EvalOS `environment_task_success` / `recovery` 硬门必须改用独立业务验证事实，而不是共享控制器的场景分。
