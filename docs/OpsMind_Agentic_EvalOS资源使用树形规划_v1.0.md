# OpsMind Agentic EvalOS 资源使用树形规划 v1.0

> 制定日期：2026-08-13
>
> 里程碑口径：**真实 M1 Pilot → M1 结果收口 → M2 数字孪生 → M3 正式评测 → M4 改进闭环 → M5 证据交付**
> 规划目标：优先用好现有两台阿里云 ECS，在不牺牲 A/B 公平性、试验隔离和证据可信度的前提下，把新增采购推迟到确实需要的阶段。

## 1. 结论先行

1. **现有两台 ECS 足够完成真实 M1 Pilot 和 M1 结果收口。** 不需要立刻再买计算型 ECS，但需要给新评测机安装基础运行环境，并建立独立的 EvalOS 证据归档桶。
2. **现有资源只能做 M2 的单场景/单 UE 技术预演，不能按完整 M2 验收。** 新评测机只有 4C8G/40G，低于 PRD/Handoff 对完整数字孪生建议的 4C16G/100G。
3. **M2 的第一个刚性采购点**是同账号、同杭州地域、同 VPC 内的一台临时数字孪生节点，建议 4C16G/100G。
4. **M3 的刚性采购点**是 8C32G/200G 的数字孪生节点，以及至少 1 台、推荐 2 台 8C32G 的 Runner。两台 Runner 的价值主要是缩短 480 个 Trial 的墙钟时间，不是改变评分口径。
5. **主账号保存长期资产，丈夫账号承载可释放的评测算力。** 丈夫账号免费 ECS 的系统盘会随实例释放而删除，因此它只能保存运行中副本，不能成为最终证据唯一存放地。
6. **真实 A/B 必须让两个架构在同一评测机、相同资源限额下串行或成对运行。** 不应把 LangGraph 版固定跑在主账号 ECS、Claude Agent SDK 版固定跑在另一台 ECS 后直接比较，否则硬件、网络和邻居负载会污染结果。

## 2. 口径说明

项目中较早的开发计划把“可信内核”称为 M1，把 L1 A/B Pilot 放在后续里程碑。本规划采用用户指定且与 Handoff 一致的业务口径：

- 已完成的可信内核和模拟回放：真实 M1 的前置条件，不计作真实模型评测结果。
- 真实 M1 Pilot：12 Case × 2 架构 × 3 seeds = 72 个真实 Trial。
- M1 结果收口：冻结、复核、判定和归档 72 个 Trial，不再偷偷改变样本或评分规则。
- M2：Open5GS + UERANSIM 数字孪生，形成 20–30 个可稳定重置的 L2 Case。
- M3：80 Case × 2 架构 × 3 seeds = 480 个正式 Trial。
- M4：基于失败簇进行受控改进，再用固定回归集和隐藏集复测。
- M5：形成可复算、可追溯、可演示的证据包。

## 6. 分阶段详细安排

### 6.1 真实 M1 Pilot：现有资源即可

目标是 12 Case × 2 架构 × 3 seeds = 72 个**真实 DeepSeek 调用** Trial。确定性回放只能作为预检和复算测试桩，报告必须标记为“模拟”，不得混入真实 M1 结果。

EvalLab-E1 的建议资源限额：

| 组件 | CPU 上限 | 内存上限 | 运行方式 |
|---|---:|---:|---|
| EvalOS API + Console + Worker | 1 vCPU | 1.25 GiB | 常驻 |
| 本地队列/缓存 | 0.25 vCPU | 0.25 GiB | 常驻；非权威 |
| L1 只读数据工具服务 | 0.5 vCPU | 0.5 GiB | 常驻 |
| 当前被测架构容器 | 2 vCPU | 2.5–3 GiB | **每次只启动一个** |
| Trial 沙箱与日志代理 | 0.5 vCPU | 0.5 GiB | 随 Trial 创建/销毁 |
| 操作系统与安全余量 | — | 至少 1.5–2 GiB | 不得占满 |

关键执行方式：

1. 将 V1 LangGraph 和 V2 Claude Agent SDK 分别制作为固定 digest 的 OCI 镜像。
2. 两个架构都在 EvalLab-E1 的同一个 Runner 上运行，不把现有生产落点当作评测硬件。
3. 对每个 `case × seed`，采用 A/B 成对串行；A/B 的先后顺序由 Manifest 预先平衡，不能由 Agent 选择。
4. 每个 Trial 使用独立 namespace、只读数据副本、独立工作目录、独立 Trace 和预算计数。
5. Trial 结束即生成校验和并上传主账号 EvalOS OSS；本地只保留短期缓存。
6. 不在免费机上同时运行两个被测架构，不在 M1 安装或启动 Open5GS/UERANSIM。

M1 磁盘预算建议：

| 用途 | 上限 |
|---|---:|
| 系统与基础软件 | 8 GiB |
| Docker 镜像和构建缓存 | 10 GiB |
| L1 Case 快照 | 4 GiB |
| 活跃 Trial、Trace 与报告临时区 | 8 GiB |
| 安全余量 | 10 GiB |

当根分区使用率达到 70% 时暂停新 Trial 并归档；达到 80% 时禁止继续运行。不得依靠“跑完再统一上传”。

### 6.2 M1 结果收口：不新增计算资源

资源工作主要从“执行”转为“冻结与复核”：

- 冻结 Experiment Manifest、Case 版本、seed、镜像 digest、模型配置、预算和评分器版本。
- 标记真实 Trial、模拟回放、无效 Trial、允许重跑的技术原因。
- 重跑只允许用于基础设施失败或事前定义的无效规则，不能因结果不好而重跑。
- 固化代码评分、Judge 评分、人工复核意见和最终裁决；原记录只能追加更正记录，不允许覆盖。
- 输出 M1 结论、置信区间、失败簇、成本和平均耗时；同时列出 M2 候选场景。
- 对 OSS 完整证据做一次离线副本和哈希校验，再进入 M2。

### 6.3 M2 数字孪生：第一次刚性扩容

不建议把 Open5GS、UERANSIM、多个 UE、故障注入和持续 PCAP 全塞进当前 4C8G/40G 免费机。正确做法是保留免费机作为控制面，新增同 VPC 的 Twin-T1：

- 规格：4C16G、100G ESSD，按量或短租。
- 网络：无公网业务入口；只允许 EvalLab-E1 和授权运维源访问。
- 运行：Open5GS、UERANSIM、故障注入、场景重置、PCAP 环形缓存。
- 数据：Case 基线快照只读；每次 Trial 创建独立 namespace；结束后重置并验证。
- PCAP：本地只保留活跃窗口；上传 OSS、校验成功后再清理。

现有免费机可以先做 M2 技术预演：单 gNB、单 UE、单故障、单 Trial 串行。但这只能证明安装和链路可用，**不能签收完整 M2**。

### 6.4 M3 正式评测：正式容量池

正式评测规模为 80 Case × 2 架构 × 3 seeds = 480 Trial。推荐资源形态：

- EvalLab-E1 继续作为 4C8G 控制面；免费额度结束时用同规格 4C8G/80G Control-C1 替换。
- Twin-T2 使用 8C32G/200G，承载正式数字孪生、重置和 PCAP。
- Runner-R1 使用 8C32G/100–200G，为最低可运行配置。
- Runner-R2 使用与 R1 相同的规格和镜像，为推荐配置；主要缩短执行周期。
- 每台 Runner 初始并发上限设为 4 个 Trial；负载测试通过后再提高到 5。
- 全池先从 4 并发验收，确认 CPU、内存、重置时延、PCAP 丢包和 Trace 完整性后再尝试 8–10 并发。
- 如果瓶颈在 Twin，而不是 Runner，应增加第二台 Twin，不应只增加 Runner。

数据库建议采用“先独立、后托管”：

1. 首选在 Control Plane 上部署独立 EvalOS MySQL，业务数据和 EvalOS 数据完全分库分账号，持续备份到 OSS。
2. 若 10 并发压测下查询 P95 超过 2 秒、数据库资源持续超过 70%，或需要公开连续演示，再升级到 RDS MySQL。
3. Redis/Tair 只保存队列、租约、去重缓存，任何关键 Trial 事实都必须写入不可变 Ledger 和 OSS。

### 6.5 M4 改进闭环：复用正式资源

M4 不需要新建一套长期集群，重点是隔离“改代码”和“验代码”：

- 复用 M3 Runner 作为受控编码沙箱；若 M3 资源已释放，临时保留或续用 1 台 8C32G Runner。
- Agent 只能修改白名单目录和独立 Git 分支，不能接触隐藏集答案、Judge Prompt、预算策略和 Ledger。
- 每次候选改进先跑固定失败簇，再跑公开回归集，最后由主账号隐藏门禁服务评分。
- 改进前后必须使用同模型快照、同预算、同 Case 版本和同资源限额。
- 任何失败改进也保留证据，避免只展示成功样本。

### 6.6 M5 证据交付：收缩计算、保留证据

M5 完成后资源退场顺序：

1. 停止创建新 Trial，等待所有 Trace、PCAP 和账本记录归档完成。
2. 生成总 Manifest、对象清单、哈希树和复算说明。
3. 在主账号 OSS 和本地离线存储各保留一份完整证据；发布副本必须脱敏。
4. 确认对象可下载、报告可复算、控制台快照可打开后，释放 Runner 和 Twin。
5. 丈夫账号免费 ECS 只在仍有免费额度且需要演示时保留；释放前不得有唯一数据。
6. 主账号产品 ECS 和 EvalOS 证据 OSS 作为长期保留资源。

## 7. A/B 公平性对应的资源规则

资源分配本身就是评分可信度的一部分：

- 同一 Case 的 A/B 使用同一个数据快照、同一模型版本、同一预算、同一工具权限。
- 优先在同一 Runner 上成对串行，消除硬件差异；需要并发时，R1/R2 必须同规格、同镜像和同资源限额。
- A/B 启动顺序预先写入 Manifest 并做平衡，避免总是让某一架构先跑或吃到热缓存。
- 每个 Trial 启动前清理工作区、缓存和容器网络；共享只读镜像层可以保留，但业务缓存必须隔离。
- 两架构均通过 Evaluation Adapter 接入；EvalOS 不根据架构写两套评分逻辑。
- LangGraph 只存在于 V1 被测架构内部，EvalOS 本身保持模型驱动的 perceive/reason/tool/observe 运行方式，不引入 LangGraph 或静态节点工作流。

## 8. 网络与账号隔离规划

两个账号隔离不影响使用，反而能形成“资产域”和“执行域”的天然隔离。正确的连接原则如下：

1. M1 优先使用脱敏、不可变 Case 包，不让 EvalLab 直接访问产品数据库，因此可以不先建设跨账号 VPC 对等连接。
2. EvalLab 从私有 OSS 下载 Case 包、向 OSS 上传 Trial 证据，使用跨账号最小权限 RAM 授权；禁止公开 Bucket。
3. 如果后续必须调用主 ECS 上的实时 Evaluation Adapter，再建设同地域跨账号 VPC 对等连接或 CEN。
4. 跨账号网络只开放 Adapter HTTPS 端口，不直接开放 MySQL、Redis、PostgreSQL。
5. 所有 Agent API、EvalOS API、数据库和数字孪生端口默认仅私网监听；控制台通过 SSH 隧道或受控网关访问。
6. SSH 继续只允许操作人员当前公网 `/32`，不要改为 `0.0.0.0/0`。
7. Twin 和 Runner 正式阶段尽量不分配公网 IP；通过 NAT/网关访问 DeepSeek API 和软件源。

## 9. 存储与证据生命周期

| 数据类型 | 运行中位置 | 权威位置 | 生命周期 |
|---|---|---|---|
| Case 原始数据 | 主账号产品域 | 主账号受控存储 | 长期，严格权限 |
| 脱敏 Case 包 | EvalLab 本地只读副本 | EvalOS OSS `datasets/` | 每版本长期保留 |
| Trial 工作目录 | Runner 本地 | 非权威 | Trial 后清理 |
| Trace / 工具事件 | Runner 短期缓存 | EvalOS OSS `trials/` | 原始长期保留，热副本按需 |
| PCAP | Twin 环形缓存 | EvalOS OSS `twin/` | M2/M3 原始保留，按生命周期转冷 |
| Ledger / 评分 | Control Plane 数据库 | OSS 不可变快照 + 数据库 | 长期，不覆盖 |
| 镜像 | 丈夫账号 ACR | Git SHA + digest + 必要镜像导出件 | 至少覆盖复算周期 |
| 报告 | Console/Runner 生成 | 主账号 OSS `reports/` + 本地副本 | 长期 |

建议新建独立 EvalOS Bucket，不复用 LangGraph 专用 Bucket。桶应启用私有访问、服务端加密、版本控制、生命周期和操作审计；命名中不要出现真实姓名或秘密信息。

## 10. 采购树与触发条件

### 10.1 现在就需要准备，但不一定产生明显费用

- 主账号：EvalOS 专用私有 OSS，初始 50–100GB 配额规划。
- 丈夫账号：ACR 个人/基础版或等价私有镜像仓库。
- DeepSeek：两架构共用可审计的预算池，但使用独立 Trial 计量。
- RAM：主账号 OSS 对 EvalLab 只授予所需前缀的读写权限。
- 监控：设置丈夫账号免费试用额度和按量计费预警。ECS API 中显示的实例到期时间不等同于免费额度到期时间。

### 10.2 M2 前必须购买

- 1 台 4C16G/100G Twin-T1，杭州地域，优先可用区 I、同 VPC、按量或短租。
- SLS 7–14 天热日志可在 M2 开始时启用；预算特别紧时先用结构化日志 + OSS，但必须保证检索和关联 ID 完整。

### 10.3 M3 前必须或推荐购买

- 必须：1 台 8C32G/200G Twin-T2。
- 必须：至少 1 台 8C32G/100–200G Runner-R1。
- 推荐：第 2 台同规格 Runner-R2，用于把评测周期明显缩短并支持 8 左右并发。
- 条件：RDS MySQL、Tair、第二台 Twin；只在负载测试或可用性目标触发时购买。
- 推荐：SLS 30 天热日志，原始大对象转 OSS。

### 10.4 不建议现在购买

- 不为 M1 购买 8C32G 正式集群。
- 不把第二台免费 ECS 直接扩盘扩内存后同时塞入控制面、Runner 和数字孪生。
- 不先买 RDS/Tair 再寻找用途。
- 不为每个被测架构各买一台不同规格 ECS。
- 不把开放公网端口当作跨账号连接方案。

## 11. 扩容、停机与退场阈值

### 11.1 EvalLab-E1

- CPU 连续 15 分钟超过 70%，或可用内存低于 1.5 GiB：停止增加并发。
- 根分区超过 70%：暂停新 Trial，先归档和清理；超过 80%：禁止继续运行。
- 出现 OOM、Trace 丢失、容器互相影响：M1 仍保持单活，不用 Swap 掩盖容量问题。

### 11.2 Twin

- PCAP 写入出现丢包、场景重置超过预定 SLO、内存持续超过 75%：降低并发。
- M3 目标并发无法在 8C32G Twin 上稳定达到：增加第二 Twin，而不是提高单机超卖。

### 11.3 Runner

- 先以每台 4 并发验收；达到 5 并发前必须做稳定性和成本回归。
- 两个架构在同样负载下出现明显资源争用时，使用成对串行，不通过提高某一架构配额补偿。

### 11.4 退场

- M2 验收后，如果 M3 不能立即开始，释放 T1；快照和 PCAP 已在 OSS 才能释放。
- M3/M4 结束后先释放 R2，再释放 R1/T2；Control Plane 保留到 M5 签收。
- 丈夫账号 ECS 释放前执行“对象数、字节数、哈希清单”三项核对。

## 13. 最终资源判断

按当前两账号资源，能力边界如下：

```text
现有资源
├─ 真实 M1 Pilot：可完成
├─ M1 结果收口：可完成
├─ M2 数字孪生：可做单场景预演，不能正式验收
├─ M3 正式评测：资源不足
├─ M4 改进闭环：可做 L1 小闭环，但完整闭环依赖 M3 资源/结果
└─ M5 证据交付：证据框架可完成，完整交付依赖 M2–M4 完成
```

因此最经济且风险最低的路径是：**现在不买新计算资源，先用免费 EvalLab-E1 完成真实 M1 和结果收口；M2 开始时首次采购 4C16G/100G Twin；M3 再按正式负载采购 8C32G Twin 和 1–2 台 8C32G Runner；M4 复用，M5 归档后释放。**
