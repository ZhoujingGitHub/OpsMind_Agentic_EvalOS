## 确定事实

1. 本轮注入 sctp-blocked。修复前 N2 38412/SCTP DROP 规则累计命中 33 包，关联 COOKIE_WAIT；修复后 DROP 消失，关联 ESTAB。N2 修复真实有效。
2. 08:24:25 UTC 历史动作回执同一对象：task_success=true；post_state.sessions 中 ue_registered=true、pdu_session_established=true、ue_tunnel_present=true；但 post_state.connectivity 同时 ping_dn=false、dns=false、loss_pct=100。此前把独立验证有效概括为整体业务恢复不准确。
3. 线上 recovery_view 对 sctp-blocked 使用“修改次数满足 + 核心服务正常 + 注册成功 + PDU 会话建立”；不以 Ping、DNS、HTTP 为必要条件。session_view 从本轮 UE 日志尾部匹配注册与会话成功文本。这既不能证明实时业务正常，也不是 HTTP 端到端验证。
4. Agent 随后的 HTTP/Ping/DNS 失败有真实工具输出。UE 路由记录只有 10.45.0.0/24 dev uesimtun0、10.47.0.0/30 dev ue0，无普通应用去 10.46.0.80/53 的路由。线上 LG probe_ip/probe_http/probe_dns 使用普通 ping/curl/dig，没有绑定 UE TUN。这能解释 Agent 遇到的本地 Network unreachable；不能单凭它定位 N6 中段故障。
5. 独立控制器 connectivity_view 的 Ping 明确 -I uesimtun0，历史回执该探测仍失败。因此不能把整个问题只归于 Agent 工具未绑网卡，也不能断言业务实际已通。需要区分普通探测的源端路由错误和经隧道探测的后续故障。
6. 后续 N6 提案 08:32:01 生成，当场 policy.diagnosis_only，原因 policy.fault_no_longer_present（原故障已经不存在），并非审批过期或裁判拒绝。链路是控制器 task_success→LG health=healthy→fault_still_present=false→禁止后续动作。这里把原场景成功当作任意新目标均无故障。
7. 第二提案 route.restore_path(n6) 映射为主机侧 N6 路由恢复。公开 UPF/主机路由已有 10.46.0.0/24 via 10.60.0.2 dev lg-host-a；该动作并不补 UE 源端路由。因此模型建议还未证实能解决观察到的失败，不应强行放行。
8. 最终 repair_delivery 取最后动作（未执行 N6）的验证作为最终验证，显示 recovery_verified=false，但说明来自已执行 N2 的“第一次修复成功”。最终 gate=probable 导致 root_cause=null；具体 N2 结论保存在 best_available_conclusion/报告。这不是历史丢失，而是结果层次混在一起。

## 经隧道仍失败的高优先级嫌疑，尚不能称已确认根因

同轮防火墙证据存在 -s 10.45.0.0/16 ! -o ogstun -j MASQUERADE。向 LG 多跳 MEC 发出的 UE 流量也会匹配。MEC 公开路由只有到 10.45.0.0/16 的回程与直连 10.60.0.12/30，没有到主机侧 10.60.0.1 的回程，也没有默认路由。源地址转换后，原来给 UE 10.45.* 配置的回程可能不再适用。FORWARD 计数修复后朝 lg-host-a 为 3 包，反向 0 包，与“有去无回”相符。

这是一条证据支撑较强的 NAT/回程冲突假设，仍需同次采样的抓包或连接跟踪确认实际转换地址和丢包点；不能仅凭累计计数定案。实验室已在上轮封存后复位，当前审查没有重跑故障或修改现场。

## 架构结论

至少三套口径未对齐：场景恢复判定、Agent 业务探测、后续审批。N2 局部修复事实可靠，整体业务恢复没有通过；新动作被局部成功标记错误地排除，最终汇总又混合最后提案与历史执行结果。不能靠延长审批、提高模型置信度、重复 N2 修复、强制第二动作或改成成功标记解决。

应先统一业务路径与探测源，验证 LG 多跳网络和 NAT/回程是否匹配；再分开记录动作成功、具体故障消除、整体任务恢复，审批读取当前提案目标的真实观测。已有 N2 已修复事实应保留，未确认的数据面问题单列，不清空全部诊断。

额外审计发现：线上控制器 recovery_view 仍有 len(changes)==1 的成功条件。它不是本轮第二动作直接被阻止的原因，但若后续确需两次动作，仍会造成误判。此前“取消只能改一次”的目标未在这层彻底落实，需单独列入修复范围；本次没有修改它。
