### F3 没有做，也不需要做

链路④ 之所以能过，是 LG 自己够到了 CONFIRMED 档，`terminal_result.outcome` 变成
`root_cause_confirmed`，EvalOS 适配器的 LG 分支本来就认这个值。
**门槛没挪，是考生够上来了。** D3 那条 AH/LG 判定不对称仍然存在（潜在问题，未被触发），
留在待办里。

### 投影修复（`6bdbe60`）已验证生效

链路② 的 `task_result.conclusion_level = "confirmed"`、`probable_root_causes = []`。
在 `6bdbe60` 之前这两个键**恒为 null**——`product_e2e` 的 `task_result` 是
`app.py:1232` 逐键构造的白名单，写进 `terminal_result` 不等于进了 API。

### F1 每次都在起作用

链路②b/②c 的获批假设都引用了验证器证据
（`protocol-lab:business-verification:…`），该条现在在 `evidence[]` 里
（`quality=verified`、`partial=False`、`coverage=complete`）。
**旧代码下这一条引用会把整个假设作废**，补多少证据都救不回来。

### F4b 从未触发

两轮都没有出现 `gap_collection_allowed`——Gate 一次都没判不过。
**起作用的是 F4a（提示词），不是 F4b（引擎兜底）。** 与方案 §6 的推演一致。

## 3. 必须如实说的三件事

### 3.1 成本涨了约 4 倍

| | 修复前 ② | 修复后 ②b | 修复后 ②c |
|---|---|---|---|
| 模型调用 | 12 | 12 | **42** |
| 输入 token | 461K | 419K | **2.10M** |
| 成本 | $1.42 | $1.22 | **$5.34** |
| 耗时 | 1018s | 1009s | **1445s** |

F4a 那段"缺口能补就补"的指引让它明显更费。**这不是缺陷，是选择的代价**，
但批量评测时（待办里的"不同类别故障批量测试"）会被放大，排期时要按这个量级估。

### 3.2 AH 也会摆动——"逐维度精确复现"这句话作废

AH 链路③ 前两轮都是 **96.43**，这次是 **100**。
grader 版本同为 `evalos-code-grader@5.7.0`、权重没动、登记只改了 LG。
封存投影里维度数值被遮蔽，**我无法归因是哪一维变了**。

所以此前"复现出来的是 AH、摆动的是 LG"**不能再这么讲**：
两个架构都会摆动，样本量（各 3 次）仍然太小。

### 3.3 链路① 没跑，理由

① 是 AH→5G 直连。本轮改动一个字都没碰 AH 产品、也没碰 5G 实验室控制器，
EvalOS 不在这条路径上。而 ③ 已经让 AH 真实跑了一遍实验室并拿到 100，
对"AH + 实验室"的覆盖比 ① 更强。**为省一次租约占用和一次费用而跳过，需要时可随时补。**
