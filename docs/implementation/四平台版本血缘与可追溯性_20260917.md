## 3. EvalOS 的 main 领先线上 6 个提交 —— 为什么这是对的

线上构建的是 `6759ce44`，main 现在是 `3254859`，中间 6 个提交：

```
3254859 docs: 订正"F4a 让链路② 贵了 4 倍"这个说法
f2bf5fb docs: 订正 AH 可复现那句结论，并修掉上一提交里的笔误
fafb73a docs: Gate 修复后的链路验收与回归
397a4fe docs(tools): 订正 evalos-op.sh 里关于控制 API 端口的错注释
de08994 docs(runbook): 补坑 23-27，并更正 f7e1784 的提交信息
f7e1784 tools: 新增 send-file.sh，RUNBOOK 补坑 23-26
```

**已逐路径核对：这 6 个提交只碰 `docs/implementation/` 与 `_work/.../tools/`，
全部不在发布包的 `include` 列表内**（列表只含 `package.json`、`config`、
`docs/contracts`、`packages`、`services/control-api/src`、`infra`、
`apps/console/dist|serve.mjs|package*.json`、`scripts/smoke-m31-deployment.mjs`）。
所以它们不影响线上产物。

**标签指向被构建的那个提交，而不是 main HEAD** —— 这是本项目既有约定，
twin 也是这么做的（标签 `18d3eb90`，main 早已前进）。
理由：生产标签必须能回答"线上跑的是哪一版"，
指向一个没被构建过的提交就是在撒谎。
构建脚本会把 `source_revision` 烧进 `RELEASE.json` 并参与 `content_digest`，
所以从 main HEAD 重新构建**一定**得到不同的 `release_id`，二者不可能等价。

## 4. 待产品经理决定：AH 前端产物要不要合进 main

现状：`92c46f9`（`apps/web/dist/` 三个文件）在
`codex/agent-harness-webdist-for-demo-20260916` 上，
**已打标签 `prod-agent-harness-web-20260916-demo-entry`、分支与标签都已推送**，
与线上逐字节一致。**可追溯性其实已经完整**——差的只是"在 main 上"。

**我的建议：不合。** 两条理由：

1. 它是**构建产物**，不是源码。把 `dist` 放进 main 会让 main 里出现
   一份会随每次前端改动而变的大文件（`index.js` 24627 行）。
2. **它是环境特定的**：API 地址在构建期烧死（`build.mjs:88` 用 `||` 取
   `VITE_AGENT_API`，为此还踩过一次坑）。同一份 `dist` 换个入口地址就失效，
   放在 main 上容易被误当成"通用产物"。

**替代做法**：保持现在这样（标签为准），并在 AH 仓 `apps/web/README` 记一句
"演示产物由 `prod-agent-harness-web-*` 标签追溯，不进 main"。
如果你更看重"一处可查"，那就合——只要明确接受上面两条代价。
