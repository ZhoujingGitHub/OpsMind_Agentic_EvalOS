## 0. 考场怎么进：隧道在当前网络下修不好，走跳板

**2026-09-24 已查清并已绕过。不要再去修隧道，也不要为此登录阿里云。**

### 结论

本机到考场的 WireGuard 隧道不通，**原因是本机所在的 Wi-Fi 网络封禁出站 UDP**，
与考场、与阿里云、与 WireGuard 配置都无关。

### 量出来的证据链（每条都实测过）

| # | 做了什么 | 结果 |
|---|---|---|
| 1 | 以管理员重启 `WireGuardTunnel$opsmind-management` | 服务 Running，**仍不通** |
| 2 | 读考场服务端 `wg show` | 本机公钥 `oekj77C3A/…` **在名单里**，服务端还记着来源 `49.74.72.167:64991`，上次成功握手 17 小时前 |
| 3 | 考场机 `tcpdump` 抓 35 秒，同时本机持续 ping 隧道对端 | **0 个包**（考场机 `iptables -P INPUT ACCEPT`，本机防火墙没挡） |
| 4 | 换产品机当靶子，安全组开到 `udp 1-65535` 放行本机 IP | 仍然 **0 个包** |
| 5 | 向产品机 53/123/443/8080/51820 各发 5 个 UDP | **一个都没到** |
| 6 | 同一网络下 ping / SSH / HTTPS 直连产品机 | **全部正常**（ping 17ms、SSH 登入、HTTPS 拿到 403） |
| 7 | 直发 UDP/53 给 `114.114.114.114`、`223.5.5.5` | 有回包——但发给**非 DNS 主机**的 53 端口同样被丢 |

即：**这个网络放 TCP、放 ICMP，只对少数已知公共 DNS 放 UDP/53，其余 UDP 一律丢弃。**
WireGuard 只能跑 UDP，所以**在这个网络上无解**——换端口也没用（第 5、7 条已经证否）。

### 替代通道：SSH 跳板（已验证，本轮所有考场操作都走它）

```
本机 ──TCP22──► 产品机 114.55.40.170 ──wg──► 考场 10.77.240.1
      opsmind-aliyun 密钥              opsmind-evallab-ed25519 密钥
                                       （私钥不离开本机，用 ProxyCommand 转发）
```

```bash
ssh -o BatchMode=yes -o StrictHostKeyChecking=no \
  -o ProxyCommand="ssh -o BatchMode=yes -i /c/Users/zhoujing/.ssh/opsmind-aliyun -W %h:%p root@114.55.40.170" \
  -i /c/Users/zhoujing/.ssh/opsmind-evallab-ed25519 root@10.77.240.1 'hostname'
# 期望输出 iZbp14ezltpnq8mxic1gsbZ
```

**两个前置条件：**

1. **产品机安全组要放行本机当前公网 IP 的 TCP 22。**
   2026-09-24 已加 `49.74.72.167/32`（描述 `operator-laptop-20260924`）。
   宽带 IP 变了就要重加——**先量出真实出口 IP**，方法见下。
2. **本机到 `114.55.40.170` 要有一条绕开代理的直连路由**（Clash 的 TUN 会接管它）：
   ```
   route add 114.55.40.170 mask 255.255.255.255 <本机网关> metric 1    # 需管理员，重启失效
   ```
   Clash 运行时配置里已经有 `route-exclude-address: 121.40.223.202/32`，
   那是给隧道端点留的口子；产品机没有，所以要手加。

### 怎么量本机真实公网 IP（别用 curl，会被代理骗）

`ipinfo.io` 之类全部经系统代理，返回的是代理出口。可靠办法：
产品机 443 对全网开放，**直接按 IP 发一个带唯一路径的请求，再去它的日志里读来源 IP**。

```powershell
$req = [System.Net.HttpWebRequest]::Create("https://114.55.40.170/我的探针标记")
$req.Proxy = $null          # 关键：绕开系统代理
$req.GetResponse()
```
```bash
ssh ... root@114.55.40.170 'grep -rh 我的探针标记 /var/log/nginx/'
```

## 3. 插进来的那件紧急事（也已修完上线）

阿里云发短信说公网流量免费额度耗尽，**两个账号都收到**。

**根因**：考生侧两个中继工人各**每 0.5 秒**问考场一次「有活吗」，一天 32 万次。
考场与考生**分属两个阿里云账号**，这一问一答只能走公网，两边各自计费。
真实代理请求只有 14.7 万条——**98.5% 的问答内容是「没有」**。

**改法**：挂住等（没活时攥住 15 秒，来活立刻交）。

| | 改前 | 改后 |
|---|---|---|
| 每分钟询问 | 216 次 | **7 次** |
| 派活延迟 | 最多 0.5 秒 | **毫秒级**（比原来快） |

攥 15 秒低于考生工人自己的 20 秒超时，**考生侧一行代码没改**。
`EVALOS_RELAY_CLAIM_WAIT_MS=0` 可一键退回老行为。存证链一行未动。

### 我在这上面栽的两个跟头（都已修，写进 RUNBOOK 25c/25d）

1. **清扫堵死服务**：node:sqlite 是同步的，删 20000 行卡死进程 **13.4 秒**，
   发版冒烟检查从一个明明在监听的接口拿到 502，**连续回滚两次**。
   已改成按时间计量（每次 100 毫秒）。**请求路径上的维护性写操作一律按时间算，不按行数。**
2. **两个进程互不等锁**：服务原先没设 `busy_timeout`，第二个进程占住写锁时
   服务写操作直接抛 `database is locked`。已加 10 秒等锁超时。

## 5. 这个项目最容易重犯的三个错（血泪版）

1. **把文档里的环境描述当常量。** RUNBOOK 曾写着"SSH 三台全部不通"，
   我照抄没验，把凭据过期当成硬阻塞，让产品经理反复扫码好几轮——
   **而那台机器全程可以直接 SSH**。说"连不上"之前先自己连一次。
2. **凭记忆下结论。** 本项目代价最大的错误全出自"先假设、后被现实纠正"。
   改口之前也要量——有两次"订正"本身又错了，因为订正时仍然没跑脚本。
3. **考场不能自造考生看不见的东西。** 词表是，判分算法也是。
   给考生的每一样东西，先问："它能从现场看到这个吗？"
