## 2. 对照业界：这个骨架是对的

**TM Forum 自治网络的闭环叫 AADE**：感知 → 分析 → **决策** → 执行 → 复盘效果。
TM Forum 的落地建议是：**初期让机器做闭环里除「决策」以外的全部环节，决策保留人在环内**。

**AH 正好落在这一格**：机器做感知、分析、执行、复盘，决策由人审批。✅

**业界把「执行前」和「执行后」拆成两份不同的文件**：

| 时点 | 业界文件 | AH 对应 |
|---|---|---|
| 执行前 | **变更单**（Change Record / RFC） | `propose_action` 的提案 |
| 执行后 | **实施后复盘**（Post-Implementation Review） | 正式报告 |

**所以「先修后报告」不是设计错误，是业界标准做法。**
报告陈述的是**已经发生并被独立验证的事实**，而不是预测——这比"先出报告再修"更好，
因为后者必然要出第二份报告，而 AH 的核心约束是「本次调查只接受一份最终答案」。

## 3. 做得好的地方（保留，不要动）

| # | 做法 | 业界评价 |
|---|---|---|
| 1 | **plan / apply 分离，且密码学绑定**：提案不可变 + 摘要校验，审批还绑定**审批当时的现场快照**，任一变化即作废 | 业界把 plan/apply 分离列为**最高杠杆的护栏**（`terraform plan` 在 `apply` 之前）。**AH 多绑了环境快照，`terraform` 只绑 plan** |

## 4. 四个洞

### H1 🔴 变更单没有举证链接 —— 会改环境的那条路，举证要求最低

**事实**（`tools.py:1049` 的入参 + `action_proposals` 表字段）：

```
propose_action 的必填项：
   action_type / target_entity_id / parameters
   justification        ← 最小长度 3 个字符
   verification_plan / rollback_plan / idempotency_key

action_proposals 表的列：
   ...investigation_id, action_type, target_entity_id, scope_json,
   parameters_json, justification, risk_level, precheck_json,
   verification_plan_json, rollback_plan_json, operating_mode, ...
                    ▲
        没有 evidence_ids，没有 hypothesis_id
```

**而报告里那段「只是文字」的建议，举证要求高得多**：

| | **动作提案**（真的改环境） | **报告建议**（只是文字） |
|---|---|---|
| 要引用证据编号 | ❌ 不要求 | ✅ 必须，且必须属于目标假设 |
| 要指向哪个假设 | ❌ 不要求 | ✅ 必须是当前领先假设 |
| 理由要求 | 3 个字符 | 前提/不确定性/预期变化/验证方法/风险/失败处理 |
| 档位够不够才准提 | ❌ 不检查 | ✅ 检查 |
| 要过成稿自审 Skill | ❌ | ✅ 必须实际跑完 |

**业界标准（ISO 27001 8.32 / ITIL 变更单）明确要求**：

> 每一份变更请求在送到审批之前，都应当**链接到相关的风险分析、回滚方案和测试证据**。

**AH 缺的就是这一条。** 表里只有 `investigation_id` 一个外键，审批者得自己跳过去翻。

**注意公平**：业界对人工审批的**最低要求**是「审查意图、目标资源、潜在影响」——
**AH 三样都有，达到了最低线。** H1 是「达标但未达最佳实践」，不是「不合格」。

### H2 🟡 举证要求没有按风险分级

**ITIL 4 变更使能的核心做法**：

> 按**风险和紧急度**给变更分类，据此分配**复核路径、审批深度和文档要求**。

**AH 有 `risk_level`，但它只驱动了一个二元判断**（`remediation.py:1797` 的
`if action["risk_level"] not in {"low","medium"}`）。
**高风险动作不会因此被要求提供更厚的举证。**

### H3 🔴 缺口字段不区分「会不会动摇根因」

**实测数据（20 次真实运维）：**

```
生效档位分布         : confirmed 12 | probable 7 | inconclusive 1
自称 confirmed 且填了缺口 : 12 / 20 —— 即「全部 confirmed」
```

看缺口原文，**12 例全部是同一类**：

> 「该 DROP 规则的注入时间线：本次未查询变更/审计类数据源」
> 「无变更记录入口可查：谁在何时添加该规则，仍属未查证事项」
> 「`query_changes`/`query_events`/`query_alarms`/`query_logs` 对本次授权范围均返回空」
> 「AH 数据库对标识域 `opsmind-twin` 的解析覆盖为 `none`」

**原因**：变更/审计数据源对实验室孪生标识域根本没有覆盖（`coverage_status=none`）。

**关键判断**：
- **根因** = 有一条 DROP 规则在丢弃 SCTP 38412 → **因果链闭合**
- **规则来源** = 谁加的、何时加的 → **溯源，不是因果**

**所以这 12 份报告的行为是对的。** 问题在于 `missing_evidence` 是一个**平铺的字符串数组**，
**看不出哪条缺口会动摇根因**。任何基于它的判据都会误杀这 12 例。

**LG 早就分了这件事**：字段叫 `blocking_evidence_gaps`（**阻断性**缺口），
检查项写着「需处理**会改变该机制判断的**阻断缺口」（`governance/evidence.py:184`）。

### H4 🟡 门只会跌到底，且判决写回答卷会破坏交付摘要

**门已经是三根杆**（强结论 / 可能 / 证据不足，三种不同高度），**但跌落只有一种**：

```python
effective = original if passed else "inconclusive"
```

**从「确认」掉下来是跌 3 级**，跳过「概然」「可能」。
一份有真实已核验证据、只是来源不够独立的报告，会被说成「我不下结论」——**失真**。

**连带的第二个问题**：门降档时会改 `conclusion_status`、`missing_evidence`、`stop_reason`
**三个被交付摘要覆盖的字段**（`formal_report_material` 只排除 `delivery_receipt` 与 `evidence_gate`），
而降档后的报告会写回 `report_json`（`harness.py:2298`）。
→ **`accepted_formal_report()` 对这份报告将返回 `None`**，系统不认自己存的报告。

**实测：0/20 发生过降档**（门 20/20 全过，独立血缘数最少 3、门只要求 2）。
**所以 H4 是一条从未被走过的路径，是陷阱不是故障。**
但它正对着后续「事实卡片」那条线：**任何基于 `accepted_formal_report()` 读历史报告的新代码，会静默丢掉每一份被降过档的报告。**

## 5. 修复方案

### F1 🔴 变更单补举证链接（修 H1）

```
   propose_action 新增必填项
   ┌────────────────────────────────────────────────────┐
   │  target_hypothesis_id    ← 针对哪个假设             │
   │                            必须是当前领先假设       │
   │  supporting_evidence_ids ← 基于哪几条证据           │
   │                            必须属于该假设，且实质有效│
   │  alternatives_considered ← 排除了哪些别的原因       │
   │  justification           ← 最小长度提高，或改结构化 │
   └────────────────────────────────────────────────────┘
   `action_proposals` 表同步加列，进 `proposal_digest` 的计算范围
```

**判据直接复用现成的**：报告建议的校验器已经在做这件事
（`target_hypothesis_id` 必须在领先假设里、`evidence_ids & target_supporting_evidence` 非空）。
**不是新发明，是把同一套判据用到更该用的那条路上。**

### F2 🟡 举证要求按风险分级（修 H2）

| 风险 | 审批 | 举证要求 |
|---|---|---|
| **低**（白名单标准变更） | 冻结授权包裁决 | 现有字段 |
| **中** | 人工审批 | **＋ F1 的举证链接** |
| **高** | 人工审批 | **＋ 举证链接 ＋ 排除的替代原因**<br>**＋ 结论档位须达概然以上** |

**最后一格的理由**：业界说「审批不应仅依赖模型置信度」——所以**不能只看档位**；
但反过来，**高风险动作配一个「证据不足」的结论应当直接拦住**。现在这条完全没有。

### F3 🔴 缺口分级（修 H3）—— **两个字段，不只 `missing_evidence`**

> **2026-09-18 订正**：本节初稿只写了报告级的 `missing_evidence`，
> **漏了按假设挂的 `unknowns`**（`tools.py:147`，也是必填）。
> **因果相关的缺口恰恰在 `unknowns` 里**——报告级那张表更多是全局性的（数据源没覆盖之类）。
> 两个字段都要标，才对得上 LG 的 `blocking_evidence_gaps`（LG 那个就是挂在假设上的）。

#### F3a 报告级 `missing_evidence`

```json
现在： ["DROP 规则的注入时间与上游变更来源超出授权可观测范围"]

改成： [{ "gap": "DROP 规则的注入时间与上游变更来源",
          "blocks_root_cause": false,
          "unavailable_reason": "out_of_authorized_scope" }]
```

| 字段 | 取值 | 判据 |
|---|---|---|
| `blocks_root_cause` | `true` / `false` | 补上这条，**会改变我对根因机制的判断吗** |
| `unavailable_reason` | `out_of_authorized_scope` 超授权<br>`no_data_source` 数据源无覆盖<br>`not_retained` 数据未保留<br>`budget_exhausted` 预算耗尽<br>**`can_be_collected` 其实能采** | 为什么现在补不上 |

#### F3b 假设级 `unknowns`（本次新增的范围）

`unknowns` 是**按假设挂的**必填字段，`cause` 的字段说明里明确要求
「未查明的细节放入 `unknowns`，不得补猜」。

```json
现在（挂在某个假设上）：
  "unknowns": ["该规则的注入时间无法确定"]

改成：
  "unknowns": [{ "gap": "该规则的注入时间",
                 "blocks_root_cause": false,
                 "unavailable_reason": "no_data_source" }]
```

**两个字段用同一套取值定义**，归一化函数共用一个。

**为什么 `unknowns` 比 `missing_evidence` 更重要**：

| | `missing_evidence`（报告级） | `unknowns`（假设级） |
|---|---|---|
| 挂在哪 | 整份报告 | **某一个具体假设** |
| 典型内容 | 数据源无覆盖、预算耗尽等**全局**情况 | **这个因果链上还差哪一环** |
| 能否判"根因闭合了吗" | ❌ 判不了，它不知道是哪个假设 | ✅ **能判** |
| 对应 LG 的什么 | 无直接对应 | ✅ **`blocking_evidence_gaps`** |

**所以 F3b 才是让 AH 具备"逐假设判定"能力的那一步**，F3a 只是让全局缺口可统计。

**`can_be_collected` 是关键取值**：它把「能补但没补」从要靠猜的事，变成**可枚举的状态**。
**一句话：不许光说「缺」，要说「为什么补不上」。填不出理由的，就是该回去补的。**

**本期只加字段与统计，判据一个字不改。** 门里新增两个统计：
`blocking_gap_count`、`collectable_gap_count`。
**理由**：现在没有任何数据支持任何判据——12 例都有缺口，但没人知道其中几例是阻断性的。
**先让字段产出这个信息，攒够真实运维再定判据。**

**兼容性**：旧格式（纯字符串）**必须继续接受**，视为 `blocks_root_cause: false`。
`missing_evidence` 是必填字段且被交付摘要覆盖，**不能硬切**。

### F4 🟡 降一档 ＋ 判决不写回答卷（修 H4）

**F4a 跌落改成沿梯子走一遍：**

```
确认 ─杆①不过─► 概然 ─杆①不过─► 可能 ─杆②不过─► 证据不足
```

**已核实不放宽任何安全控制**：`tools.py:293` 里「可能」与「证据不足」在
**能否发修复建议上是同一档**，所以降到「可能」而非「证据不足」，**权限完全不变，只有信息保真度提升**。

**F4b 判决不写回答卷（产品经理已拍板）：**

```
 ┌──────────────────────────────────────────────────────────┐
 │ report_json  ＝ 考生交的答卷                             │
 │   ❌ 门一个字都不改  →  交付摘要永久可验                  │
 ├──────────────────────────────────────────────────────────┤
 │ report_json.evidence_gate  ＝ 系统的判决                 │
 │   原档位→生效档位 / 每根杆过没过 / 缺哪条要求            │
 │   ＋ blocking_gap_count / collectable_gap_count          │
 │   ✅ 可以写  →  交付摘要【本来就不覆盖这一块】            │
 ├──────────────────────────────────────────────────────────┤
 │ 数据库 conclusion_status 列  ＝ 生效档位                 │
 │   ✅ 写生效档位 → 不在 report_json 里，不影响摘要         │
 │   对外 API 的【顶层】conclusion_status 读的就是这一列     │
 └──────────────────────────────────────────────────────────┘
```

**答卷是考生的不可变提交物；判决是系统的，放判决块里；生效档位放列里给外部读。**

**F4c 必须一起做的收尾**（否则把旧问题镜像成新问题）：

不写回之后，`report.conclusion_status` 是**自报值**，顶层才是**生效值**。
现在这两个**恰好总是相等**（门从没降过档），所以读错地方的消费方还没暴露。**改完会开始分叉。**

1. **写死文档**：`report.conclusion_status` = 考生自报；顶层 = 生效
2. **审一遍现有消费方**，凡需要生效档位的，改读顶层或 `evidence_gate.effective_conclusion_status`

### F5 🟢 并列记录一个「参考档位」（新增，零风险）

#### 为什么 AH 的档位是自报的、LG 的是算出来的

**不是哪家更严谨，是假设对象的结构不同。**

**LG 的假设是拆开的结构体**，所以代码能逐字段做布尔判断：

| LG 的假设字段 | AH 有对应吗 |
|---|---|
| `statement` 结论陈述 | ✅ `cause` |
| `supporting_evidence_ids` | ✅ 同名 |
| `contradicting_evidence_ids` | ✅ `counter_evidence_ids` |
| `status` | ✅ 同名（枚举值不同） |
| `blocking_evidence_gaps` 阻断缺口 | ⚠️ 有 `unknowns`，**但不标是否阻断**（F3b 正是补这个） |
| **`conclusion_level`** 每个假设各自的档位 | ❌ **无**。只有 `confidence` 数值，和**整份报告一个** `conclusion_status` |
| **`causal_component`** 哪个对象坏了 | ❌ **无**，揉在 `cause` 一段文字里 |
| **`causal_mechanism`** 怎么坏的 | ❌ **无**，揉在 `cause` 一段文字里 |

**所以 AH 要能算档位，差三样：**

1. **把 `cause` 拆成「哪个对象 + 什么机制」**——信息本来就在，
   `cause` 的字段说明已经要求「写明受影响对象、已查明的故障位置及机制」，**只是没拆成字段**
2. **每个假设各给一个档位**（现在只有报告级一个）
3. **给 `unknowns` 标上是否阻断根因** ← **F3b 已经在做这一步**

#### 但不建议让代码算的档位取代自报

**那会把 AH 变成 LG。**

```
   LG 的产品主张：判断权交给代码（门算档位，模型说了不算）
                          │
                          ▼  迭代
   AH 的产品主张：判断权交给模型（模型自报，代码只兜底）
```

`evidence_gate.py` 的注释就是这条主张本身：

> 这段代码可以降低确定性，**但绝不编造事实、也绝不替 Agent 选择调查路径**。

**两个产品的差别就是这一条。抹掉它，就不是两个产品了，是两份 LG。**

#### 所以走第三条路：并列记录，不生效

```
   模型自报的档位  ──────────────► 【生效，行为一个字不变】
                                        │
   代码算出的参考档位（新增）──────► 【只记录，不生效】
        用 AH 已有的信息算：                │
        证据是否实质有效、独立血缘数、       │
        反证是否解决、F3b 的阻断缺口         │
                                        ▼
                    攒几十次之后得到一张表：
                    模型自评与代码判定差多少、差在哪
```

**落在哪里**：`evidence_gate` 判决块里新增
`reference_conclusion_status` ＋ `reference_basis`（每项判据的过否）。
**判决块不进交付摘要（见 F4b），所以这是纯新增，零副作用。**

#### 三个好处

| | |
|---|---|
| **零风险** | AH 行为一个字不变，只多两个记录字段 |
| **直接量出「模型自评有多准」** | 这正是考场「校准度」维度想测的东西，**而且是从生产量的，不是考场** |
| **回答一个现在答不上的问题** | 那 12 份自称 `confirmed` 的报告，**有几份够得上 LG 的标准？现在完全不知道** |

**量完再决定要不要让它生效——那时有数据支撑，不是拍脑袋。**
**本期只记录，绝不生效。**

## 7. 实施顺序与验收标准

| 序 | 做什么 | 验收标准 |
|---|---|---|
| **1** | **F3a ＋ F3b ＋ F4b ＋ F4c** | **20 例档位分布必须一个都不变**（12/7/1），只多出统计字段；**交付摘要 100% 匹配** |
| **2** | **F5**（参考档位，只记录） | 20 例档位分布**仍然一个都不变**；判决块里多出 `reference_conclusion_status` |
| **3** | **F1** | 现有 20 例若重跑，提案必须能通过（领先假设与证据本来就存在）；缺任一新字段则提案被拒 |
| **4** | F2 | 高风险动作配「证据不足」结论时被拦住 |
| **5** | F4a | 构造一个「2 条证据但同一血缘」的用例，生效档位应为「可能」而非「证据不足」 |

**F5 紧跟第 1 步的理由**：它依赖 F3b 的 `blocks_root_cause` 字段，
而且它和第 1 步共享同一条验收标准（**行为零变化**），可以一次回归验完两步。

**第 1 步的验收标准最重要**：**如果跑完发现档位分布变了，就是改错了。**

### ⏳ 待办：回归测试时必须回答的一个问题

**「AH 修完之后会不会回到分析环节？」—— 现有数据答不了，留到回归测试回答。**

**为什么答不了**：核过那 20 次调查的全部事件类型，结果是——

```
   agent.progress 4352 / tool.* 约 8500 / decision.summary 174
   evidence.gate 20 / agent.report_submitted 19
   protocol_lab.trial_bound 40 / trial_reset 20
   agent.report_rejected 11
   ...
   ▲ 完全没有 动作 / 审批 / 执行 / 验证 类事件
```

**这 20 次全部是纯诊断，一次都没执行过修复动作。**
所以「修完之后会不会回去继续查」这个问题，这批样本**根本没走到那一步**。

（链路① 那次确实执行过动作——`action-eee910c2614b`、执行成功、业务验证通过——
但那是 **2026-09-11** 的，**不在这 20 次里**；这 20 次是 09-16/17 重新验收那批。）

**回归测试时怎么答**：跑一次**带修复动作**的链路①，看事件时间线里
**「执行成功」之后还有没有取证动作**。

| 结果 | 含义 |
|---|---|
| 有后续取证 | AH 的隐式闭环真的会回去——**和 LG 的显式回路等效** |
| 没有后续取证 | AH 修完就收口。**那就要讨论是否给提示词补一句**（对应 LG 的 `recover` 路由） |

**这一条不阻塞任何一条修复的实施**，四条修复都不依赖这个答案。

> **顺带一个新数据点**：`agent.report_rejected` 出现 **11 次**。
> 说明契约校验真的在拦人——20 次调查拦了 11 次，模型改完重提，最终 19 次提交成功。
> **「拒绝 → 改完重提」这个闭环不是理论，是天天在用的。**

---

顺序理由：F3 是后面一切的数据前提且行为零变化，最好验；F1 管的是唯一真的会改环境的那条路，
但它会改变提案契约，需要一次真实链路验证。

## 8. 边界（不越的线）

- **不动 LG，不动 EvalOS 考场判分**
- **不放宽任何安全控制**：F4a 已核实权限不变；F3 只加字段不改判据；F1/F2 是**收紧**
- **旧格式必须继续接受**（`missing_evidence` 必填且被摘要覆盖）
- **不改历史报告**：不回填、不重算已封存的证据
- **§3 那七条做得好的地方一个字不动**
