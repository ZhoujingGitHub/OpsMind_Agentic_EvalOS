**定位**：AH 与 LG 是**两套各自独立的完整平台**（各自独立前端 + 独立后端），是两个"考生"，

**外围架构原则**：轻薄、稳定、三套同构。每套配置就是一个 `server` 块。

## 2. 本轮实测确认的四个前提

1. **`sslip.io` 子域可用**（服务器侧 `getent hosts` 实测）：
   `lg.114-55-40-170.sslip.io` → `114.55.40.170`，`ah.114-55-40-170.sslip.io` → 同。
   所以两个工作台各占一个主机名的**根路径**，不需要任何路径前缀或 `sub_filter` 改写。
2. **AH 前端可以做成同源，因此不用改 CORS**。`apps/web/src/api/client.ts:1`：
   ```ts
   const API_ROOT = import.meta.env.VITE_AGENT_API ?? "http://127.0.0.1:8000";
   // 使用处：fetch(`${API_ROOT}${path}`)
   ```
   `??` 只在 null/undefined 时回落，所以**用空串构建**（`VITE_AGENT_API=`）后
   `fetch("/v2/auth/login")` 就是同源相对路径。`OPSMIND_CORS_ORIGINS` 一行不用改，
   AH 进程不用重启。
   **盘上那份 7 月 28 日的 `dist/` 不能直接用**——它烧死的是 `http://127.0.0.1:8000`，
   浏览器会去连使用者自己的笔记本，而且 https 页发 http 请求会被当混合内容拦掉。
3. **AH 是 `BrowserRouter` SPA**（`main.tsx:3`、`App.tsx:1` 用 `react-router-dom`），
   所以 nginx 必须 `try_files $uri $uri/ /index.html`，否则刷新深链接 404。
   LG 不需要（单页 `/app`，无前端路由）。
4. **产品机整机只有 22 端口对外**，`iptables -S INPUT` 无规则 → **安全组是唯一网络边界**。

## 3. 配置（每套一个 server 块）

**http 层**，`/etc/nginx/conf.d/opsmind-consoles-limit.conf`：

```nginx
limit_req_zone $binary_remote_addr zone=opsmind_lg:10m rate=20r/s;
limit_req_zone $binary_remote_addr zone=opsmind_ah:10m rate=20r/s;
```

两个考生**各自一个 zone**。共用会让一方的使用挤掉另一方的配额，
那是把两个本应独立可比的系统耦合起来。

**LG**，`/etc/nginx/sites-available/opsmind-lg`：

```nginx
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name lg.114-55-40-170.sslip.io;

    ssl_certificate     /etc/nginx/ssl/opsmind-product/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/opsmind-product/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;

    location / {
        include /etc/nginx/opsmind-lg-access.conf;      # 总开关：空=开放，deny all;=关闭
        auth_basic "OpsMind LangGraph";
        auth_basic_user_file /etc/nginx/opsmind-lg.htpasswd;
        limit_req zone=opsmind_lg burst=50 nodelay;

        proxy_pass http://127.0.0.1:8081;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout 300s;
    }
}
```

**AH**，`/etc/nginx/sites-available/opsmind-ah`：

```nginx
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name ah.114-55-40-170.sslip.io;

    ssl_certificate     /etc/nginx/ssl/opsmind-product/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/opsmind-product/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    include /etc/nginx/opsmind-ah-access.conf;          # 总开关放 server 级，两个 location 共用
    auth_basic "OpsMind Agent Harness";
    auth_basic_user_file /etc/nginx/opsmind-ah.htpasswd;

    # 前端静态：nginx 直接提供，不进镜像、不重启 AH 进程
    location / {
        root /srv/opsmind-ah-web;
        try_files $uri $uri/ /index.html;               # BrowserRouter 深链接
        limit_req zone=opsmind_ah burst=50 nodelay;
    }

    # 同源 API 反代
    location /v2/ {
        limit_req zone=opsmind_ah burst=50 nodelay;
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout 300s;
    }
}
```

**一张 SAN 证书覆盖两个名字**（acme.sh 一次 `-d lg.… -d ah.…`），省一套续期逻辑。

**不开 80。** acme.sh 用 TLS-ALPN-01（EvalOS 实测 `Le_Webroot='alpn'`），
签发与续期都只需 443；80 在大陆公网会被阿里云 ICP 拦截页替换，对浏览器也没用。

**和 EvalOS 的结构差异**：EvalOS 留了三个免认证 location（relay、presence、judge）；
产品机**一个都不需要**——relay 在产品机上是**出站**方向（产品 API 是本地回环）。
所以这两套在严格度上比现在跑着的 EvalOS 更高。

**写操作全部放行。** 发起故障根因调查、人工审批、切租户都照常走——这是完整平台演示的要求。
它们本来就在各自应用的登录与权限校验后面（AH/LG 都有自己的账号体系，审批还有
`submitter ≠ approver` 职责分离、票据有效期），不因请求来自公网而失效。

## 5. S0：EvalOS 证书续期（最急，且与开放解耦）

查证结果（Cloud Assistant 只读）：

| 查的东西 | 结果 |
|---|---|
| root `crontab -l` | **空** |
| `/etc/crontab`、`/etc/cron.d/` 含 acme/opsmind 的行 | **无** |
| systemd timer | 只有 `certbot.timer`（Ubuntu 装包自带） |
| certbot 实际管什么 | `/etc/letsencrypt/live` **不存在** → **什么都没管** |
| 真正签证书的 | **acme.sh**，`/var/lib/opsmind-acme`，`Le_Webroot='alpn'`，`Le_NextRenewTimeStr='2026-10-14T01:23:04Z'` |
| 谁跑 `renew-evalos-cert.sh` | **没有任何调度**，脚本只存在于 `/opt/opsmind-evalos/releases/*/evalos/infra/acme/` |

**后果有确定日期**：证书 `2026-11-13 09:29:22 GMT` 到期。而产品机 relay 配的是
`EVALOS_RELAY_ORIGIN=https://121-40-223-202.sslip.io`，env 里没有关闭证书校验的开关。
**证书过期 → relay TLS 校验失败 → 链路③④ 断。**

`certbot.timer` 每天在跑、看起来一切正常，这正是它危险的地方。

修法：把 renew 脚本装到 `/usr/local/sbin/`，配 systemd timer 每天跑一次（acme.sh 自己判断
续期窗口，未到就空跑，天然幂等）；停掉误导人的 `certbot.timer`；
把 `openssl x509 -checkend` 加进 `tools/check-balance.sh` 那类日常只读检查。

**待核实**：续期时脚本会 `systemctl stop nginx` 让 acme.sh 独占 443，控制台与 relay 有
秒级中断。需确认 relay 侧有重试；timer 定在低峰。

## 8. 排障须知：本机的网络环境会骗人

本轮实测，记进 RUNBOOK 坑 12：

- 这台 Windows 机跑着 **TUN 模式代理全局接管**，DNS 解析器是 `198.18.0.2`，
  所有域名都被解析成 `198.18.0.x` 的 fake-IP；**真实出口在日本东京 `188.253.123.160`**。
  `--noproxy` 绕不开，因为是网络层接管。
- 所以：**本机 `nslookup` 与 `curl` 的结果不能用来判断"线上能不能访问"**。
  实测对照：`curl https://121-40-223-202.sslip.io/` 报 schannel 握手失败，
  **但浏览器打开同一地址正常返回 401**。
- **判断可达性一律用浏览器**，或在服务器上用 `getent hosts` / `curl` 自测。
- SSH 不通的根因由此确证：安全组白名单里没有 `188.253.123.160`。
  TCP 能连上但拿不到 banner，是 TUN 接口先应答、真实握手被安全组拦掉。
