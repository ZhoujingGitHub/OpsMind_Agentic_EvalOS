## 0. 结论先行

**建议做，但要拆成两批批准，而且顺序不能反。**

- **第一批（建议立刻做，与开放前端无关）**：修 EvalOS 控制台证书的续期。
  查证结果是**没有任何调度在续它**，`2026-11-13` 到期，到期会**同时打断 relay**，
  也就是打断链路③④。这件事比开前端急，而且不修它就照抄同一套做法到产品机，
  等于把同一个缺陷复制一份。详见第 3 节。
- **第二批（本方案主体）**：产品机装 nginx、开 443、Basic 认证 + 限流，
  同源反代 AH 前端与 LG 工作台。

主体方案的核心设计是：**整个改动不碰任何应用镜像、不碰任何应用进程、不改任何应用配置。**
线上四个组件的提交号与生产标签保持不变，四条链路不需要重跑。
能做到这点靠两个选择——同源反代（免去改 CORS）和 nginx 直接提供静态前端（免去重建 AH 镜像）。

## 2. 攻击面到底变了什么

诚实列，不打折扣：

1. **产品机首次接受公网入站。** 现在连 80 都没有，只有 22 对外。这台机上有 19.8 GB 生产库、
   MySQL/Postgres/Redis（都在回环）、relay 进程、以及调用 5G 实验室的凭据。
2. **暴露的不只是页面。** AH 的 8000 和 LG 的 8081 都是**完整业务 API**，
   含 `POST /api/v1/candidates`（发起真实调查）、审批端点、租户切换。
   反代上去就等于把这些路径也摆到公网——只是前面多了 Basic 认证这一关。
3. **认证端点无锁定**（1.2 节）。Basic 认证挡住之后公网打不到登录端点；
   但这层一旦被绕过或被撤掉，应用自己没有第二道刹车。
4. **安全组是唯一边界**（1.1 节），没有宿主机防火墙兜底。
5. **爬虫会找到它。** EvalOS 已有实证：Googlebot 与苹果网段请求过账本里真实存在的
   trial URL。Basic 认证能挡住抓取，但 401 日志会变多，且**泄漏源本身仍未查清**
   （HANDOFF 遗留第 3 条）。

**不变的部分**：relay 在产品机上是**出站**方向（`EVALOS_RELAY_ORIGIN=https://121-40-223-202.sslip.io`，
产品 API 是本地 `http://127.0.0.1:8000` / `:8081`）。也就是说**产品机不需要为机器对机器通信开任何免认证入口**。
这比 EvalOS 干净——EvalOS 必须留三个免认证 location，产品机**可以做到所有路径一律要求凭据、零例外**。

## 3. 前置问题：证书续期（会同时打到现有控制台）

这是本轮核实时挖出来的，文档里没有记过。

**查证结果**：

| 查的东西 | 结果 |
|---|---|
| `crontab -l`（root） | **空** |
| `/etc/crontab`、`/etc/cron.d/` 里含 `acme`/`opsmind` 的行 | **无** |
| systemd timer | 只有 `certbot.timer`（Ubuntu 装 certbot 包自带） |
| certbot 实际管着什么 | `/etc/letsencrypt/live` **不存在** → **什么都没管** |
| 真正签发证书的 | **acme.sh**，`/var/lib/opsmind-acme`，`Le_NextRenewTimeStr='2026-10-14T01:23:04Z'` |
| 谁会去跑 `renew-evalos-cert.sh` | **没有任何调度**。该脚本只存在于 `/opt/opsmind-evalos/releases/*/evalos/infra/acme/` 里，没装到任何调度器会调用的位置 |

**后果是有日期的**：证书 `2026-11-13 09:29:22 GMT` 到期。
而产品机的 relay 配的是 `EVALOS_RELAY_ORIGIN=https://121-40-223-202.sslip.io`，
relay 的 env 里**没有** `VERIFY=false` / `INSECURE` 一类的开关，默认要校验证书。
所以证书过期不是"浏览器弹个警告点继续"，而是 **relay 的 TLS 校验直接失败 → 链路③④ 断**。

而 `certbot.timer` 每天在跑、看起来一切正常，这正是它危险的地方：
监控面上有个绿色的定时器，实际续的不是这张证书。

**建议的修法**（本方案第一批，与开前端解耦）：

1. 把 `infra/acme/renew-evalos-cert.sh` 安装到固定路径（如 `/usr/local/sbin/`），
   配 systemd timer 每天跑一次（acme.sh 自己判断是否到续期窗口，未到就空跑，天然幂等）。
2. 脚本现在 `systemctl stop nginx` → acme.sh 独占 443 → `systemctl start nginx`，
   靠 `trap restore_nginx EXIT` 保证异常也会把 nginx 拉回来。
   续期期间控制台有**秒级中断**，relay 也会短暂失败——建议把 timer 定在低峰
   并给 relay 侧确认有重试（这一条我还没查，列入待核实）。
3. 停掉或卸掉 `certbot.timer`，免得下一任继续被它误导。
4. 加一条到期检查进 `check-balance.sh` 那类日常只读检查里
   （`openssl x509 -checkend`），和余额一起看。

## 4. 方案设计（关键选择及理由）

### 4.1 同源反代 —— 为了不改 AH 配置

一个 https origin 同时提供静态前端与 API 反代：

```
https://114-55-40-170.sslip.io/            → nginx root，AH 前端 dist（静态）
https://114-55-40-170.sslip.io/v2/...      → proxy_pass http://127.0.0.1:8000   (AH API)
https://114-55-40-170.sslip.io/lg/app      → proxy_pass http://127.0.0.1:8081/app
https://114-55-40-170.sslip.io/lg/api/v1/  → proxy_pass http://127.0.0.1:8081/api/v1/
https://114-55-40-170.sslip.io/lg/assets/  → proxy_pass http://127.0.0.1:8081/assets/
```

因为前端与 API 同源，**浏览器不发跨域预检**，于是**不需要改
`OPSMIND_CORS_ORIGINS`**（现在是 `http://127.0.0.1:5173,http://localhost:5173`），
也**不需要重启 AH 容器**。这是"零应用影响"的关键。

> **待核实**：LG 的 `app.js` 里请求路径是写死的 `/api/v1/...`（绝对路径）。
> 放在 `/lg/` 前缀下会指错。三种解法：(a) 用子域 `lg-114-55-40-170.sslip.io` 让 LG 独占根路径；
> (b) nginx `sub_filter` 改写（脆，不推荐）；(c) 改 LG 前端为相对路径（要动代码，破坏"零应用改动"）。
> **推荐 (a)**：两个子域各自根路径，LG 侧完全不用改，代价是要签两张证书（或一张 SAN 证书）。
> 实施前需在机上确认 `app.js` 的实际请求前缀。

### 4.2 只开 443，不开 80

EvalOS 的 acme.sh 用的是 **TLS-ALPN-01（443）**，不需要 80。
EvalOS 配置里 80 的 `/.well-known/acme-challenge/` root 是遗留，实际没在用。
而 80 在大陆公网会被阿里云 ICP 拦截页替换，对浏览器也没用。

所以产品机**不开 80**：少一个攻击面，也不用做 301。
代价：用户漏打 `https://` 会得到"连接被拒绝"而不是跳转。这反而比撞备案页好判断——
文档里写清"必须 https"即可（RUNBOOK §0.1 已写）。

### 4.3 所有路径一律要求凭据，零例外

见第 2 节末尾：产品机的 relay 是出站方向，没有机器对机器入口需要豁免。
所以不照抄 EvalOS 的三个免认证 location，而是：

```nginx
# 每个 location 都带这三行，没有例外
include /etc/nginx/opsmind-product-access.conf;   # 总开关
auth_basic "OpsMind Product";
auth_basic_user_file /etc/nginx/opsmind-product.htpasswd;
limit_req zone=opsmind_product burst=50 nodelay;
```

另外给写入类路径加更紧的限流（单独 zone，低 rate），因为它们会真的发起调查、
真的动 5G 实验室：`POST /v2/investigation-candidates`、`POST /api/v1/candidates`、
两边的 approval 端点。

口令与 EvalOS 分开，**不复用同一个 htpasswd**（一处泄漏不应等于两处失守）。

### 4.4 nginx 直接提供 AH 前端静态，不重建镜像

`.dockerignore:9` 排除 `apps/web/dist`，AH 服务端也没有 `StaticFiles` 挂载。
不去改这两处，改由 nginx `root` 直接提供 —— 于是**线上提交 `7b1123a8` 与生产标签
`prod-agent-harness-20260915-test-isolation` 完全不动**。

前端产物需要可追溯身份，否则"线上跑的是哪版前端"会变成下一个说不清的东西。
构建后生成 `dist/BUILD.json`：源提交号、构建时间、逐文件 sha256、构建机。
随发布记录进证据目录。

### 4.5 补一层宿主机防火墙

安全组现在是唯一边界（1.1 节）。建议同时配 nftables/ufw 只放 22 + 443，
作为第二层。这条是加固、不是本方案的必要条件，可以单独批。

## 5. 实施步骤（每步可独立回滚，S0–S2 无公网暴露）

| 步 | 内容 | 公网暴露 | 可回滚性 |
|---|---|---|---|
| **S0** | 补齐待核实项：LG `app.js` 的请求前缀；relay 对 EvalOS 短暂不可用是否有重试；`sub_filter` 是否被编译进 nginx（若走方案 b 才需要） | 无 | 只读 |
| **S1** | 本机构建 `apps/web/dist` + 生成 `BUILD.json` | 无 | 本地文件 |
| **S2** | 产品机装 nginx；配置**先只监听 `127.0.0.1:8443`**；机上 `curl` 逐路径自测（含 401/403 反向验证） | 无 | `apt remove nginx` |
| **S3** | 安全组加 443（`0.0.0.0/0`），但 `opsmind-product-access.conf` 里**先写 `deny all;`** | 443 开但全拒 | 删安全组规则（秒级） |
| **S4** | acme.sh 签证书（TLS-ALPN-01 需要公网能到 443，故必须在 S3 之后）；nginx 切到监听 443 | 同上 | 同上 |
| **S5** | 装续期 systemd timer（**与第一批 EvalOS 的修法同一套**）；停 `certbot.timer` | 同上 | 停 timer |
| **S6** | 清空 `opsmind-product-access.conf` → 开放；公网走验证清单 | **真实暴露** | 写回 `deny all;` + reload（秒级） |
| **S7** | nginx 配置、renew 脚本、`BUILD.json` 生成器纳入 Git（AH 仓新建 `infra/nginx/` 与 `infra/acme/`，与 EvalOS 对称）；**同时修 EvalOS 那份配置漂移** | 无 | Git |

为什么 443 要在签证书之前开：TLS-ALPN-01 需要 Let's Encrypt 从公网连到 443。
签发时 acme.sh 独占 443（脚本会先停 nginx）。所以次序只能是"先开端口、但应用层全拒"。

## 6. 明确不动的东西

- **不改任何应用代码**（AH / LG / EvalOS / 控制器四个仓的业务代码一行不动）
- **不重建任何镜像、不动任何容器或进程** → 四个线上提交与四个生产标签保持不变
- **不改 `OPSMIND_CORS_ORIGINS`**（靠同源反代规避）
- **不动 relay 的任何配置**，不动 EvalOS 那三个机器对机器 location
- **不改评分权重、不删真实失败、不伪造根因/回滚/验证**
- **不改写 Git 历史、不 force push、不删远端分支或标签**
- **不为了跑通验收放宽安全控制**：不放行沙箱 IP、不放行共享 VPN 出口、
  不用"先开着以后再加认证"的次序
- **不动那三条已失效的 SSH `/32` 规则**（`223.104.150.16`、`49.77.227.213`、`121.229.147.13`
  已不匹配当前出口 IP）——该清，但属独立变更，另批

## 7. 回滚

按影响从大到小，三条互相独立：

1. **删安全组 443 入方向规则** —— 秒级生效，最彻底。之后公网完全回到今天的状态。
2. **`opsmind-product-access.conf` 写入 `deny all;` + `nginx -t && systemctl reload nginx`**
   —— 不动安全组，应用层全拒（403）。
3. **`systemctl stop nginx`** —— 443 变连接拒绝。

三条都**不触碰应用**，所以任何一条回滚都不影响四条链路，不需要重跑验收。

## 8. 验证清单（做完要能逐条证明，含反向验证）

正向：

1. 公网 `https://…/` 带凭据 → AH 前端登录页，能登录并看到真实租户数据
2. 公网 `https://…/`（LG 子域或 `/lg/app`）带凭据 → LG 工作台，能登录并看到真实调查
3. 证书链有效、`openssl x509 -checkend 2592000` 通过

反向（这几条更重要）：

4. **不带** Basic 凭据 → `401` + `WWW-Authenticate`，且**应用日志里没有这次请求**
   （证明应用确实没被碰到）
5. `http://…`（80 端口）→ **连接被拒绝**，不是备案页、不是 301
6. `opsmind-product-access.conf` 写 `deny all;` → `403`
7. 未登录直接打写入端点（如 `POST /v2/investigation-candidates`）→ 过了 Basic 之后
   仍被应用 `401` 拒绝（证明双层都在）
8. 连打 N 次触发 `limit_req` → `503`

不回归：

9. 四条链路 `preflight` 仍 `ready: true`、`blockers: []`
10. relay 心跳（`/api/candidate-presence`）正常，`candidate_relay_requests` 有新记录
11. 四个线上提交号与生产标签与本方案第 6 节声明一致（逐个核对）

## 9. 不推荐的替代方案

| 方案 | 为什么不推荐 |
|---|---|
| 安全组直接开 8000/8081 | 无 TLS、无认证层，而应用**没有登录失败锁定**。等于把无限次口令尝试摆到公网 |
