# 本地验收可信跑法（三仓库）

固化日期：2026-09-14
起因：四条链路修复实施期间，同一类环境问题在三个仓库各踩了一次。最严重的一条是
**Windows 上 `infra/twin` 的 39 项控制器安装器测试会一声不吭地跳过**，而下一步恰恰
要把控制器装到 Linux 实验室上。本文件记录每个仓库当前**唯一可信**的跑法与实测基线。

---

## 0. 三条通用坑

| 坑 | 现象 | 原因 |
|---|---|---|
| 会话环境变量污染 | EvalOS `DeepSeek environment keeps credentials…` 失败；AH 三个测试文件在收集期就报 `OPSMIND_MODEL_PROFILE_INVALID` | Claude Code / Codex 会话自身导出了 `ANTHROPIC_BASE_URL=https://api.anthropic.com`。被测代码按环境变量兜底，于是拿到 anthropic 而不是 deepseek 端点 |
| Git Bash 解析 git 路径 | EvalOS `deployment-installer` 21 项、LG `test_release_recovery` 3 项报 `bash.exe ENOENT` | 测试用 `where.exe git` / `shutil.which("git")` 反推 bash 路径。Git Bash 里 git 解析到 `mingw64/bin`，推出来的路径不存在。用 PowerShell 时 git 解析到 `cmd/`，推出来的路径正确 |
| Windows 缺 `fcntl` | 大量测试被 skip 而不是 fail | 平台守卫。skip 不会让套件变红，因此长期没人发现 |

**所以：跑测试前先清掉 `ANTHROPIC_BASE_URL` 和 `ANTHROPIC_MODEL`；Windows 侧一律用
PowerShell，不要用 Git Bash；凡是带 Linux 语义的用例必须在 WSL 里跑。**

---

## 1. EvalOS（Node）

```powershell
Set-Location <EvalOS>
Remove-Item Env:ANTHROPIC_BASE_URL -ErrorAction SilentlyContinue
npm test
node scripts/check-m31-architecture.mjs
node scripts/check-m31-security.mjs
node scripts/check-m31-capability-protection.mjs
```

实测基线（2026-09-14，候选 `92c4cc9`）：**238 passed / 0 failed / 0 skipped**，三项检查全过。

> 不清 `ANTHROPIC_BASE_URL` 会多 1 项失败；用 Git Bash 会多 21 项失败。两者都不是产品问题。

## 2. EvalOS 的 `infra/twin`（Python，**必须 Linux**）

Windows 上 `fcntl` 缺失，**39 项控制器安装器测试会被整类跳过**。用 WSL：

```bash
python3 -m venv ~/opsmind-venv && ~/opsmind-venv/bin/pip install pytest
rm -rf ~/twin && mkdir -p ~/twin
cp -r "/mnt/d/.../OpsMind_Agentic_EvalOS/infra/twin/." ~/twin/
rm -rf ~/twin/__pycache__
cd ~/twin && ~/opsmind-venv/bin/python -m pytest -q
```

实测基线（2026-09-15，候选 `7b1123a`/`5089258` 之后）：**196 passed / 1 skipped / 23 subtests**。

> Windows 上跑这套会**直接失败**，不再静默变绿：`InstallerCoverageTest` 会指出 39 项安装器
> 用例在本平台跑不了。要在没有安装器覆盖的情况下继续，必须显式设
> `OPSMIND_TWIN_ALLOW_SKIPPED_INSTALLER_TESTS=1`，把这个缺口记录下来。
唯一 skip：`test_harness_diagnostics.py:124`，需要 Linux + tshark 工程机。

## 3. AH（Python）

### 3.1 本仓库默认 `.venv` 已漂移，不能用来验收

| 包 | pyproject 钉的 | `.venv` 实际装的 |
|---|---|---|
| `mcp` | `1.28.1` | `2.1.1` |
| `claude-agent-sdk` | `0.2.148` | `0.2.142` |

`Server.list_tools` 在 mcp 2.x 已不存在，**32 项测试因此报
`AttributeError: 'Server' object has no attribute 'list_tools'`**。
线上镜像按 pin 构建，不受影响；这是本机环境问题。

**未修改原 `.venv`**（它可能还有别的用途）。改用按 pin 的独立环境（已加进 `.gitignore`）：

```powershell
Set-Location <OpsMind>
.\.venv\Scripts\python.exe -m venv .venv-pinned
Set-Location services\agent-service
..\..\.venv-pinned\Scripts\python.exe -m pip install -e ".[dev]"
Remove-Item Env:ANTHROPIC_BASE_URL -ErrorAction SilentlyContinue
..\..\.venv-pinned\Scripts\python.exe -m pytest -p no:warnings -o addopts="" -rs
```

实测基线（候选 `7b1123a`）：**404 passed / 3 skipped / 0 failed**。

> 2026-09-15 起 `tests/conftest.py` 会在收集前清掉 `ANTHROPIC_*`，**不再需要手工
> `Remove-Item Env:ANTHROPIC_BASE_URL`**；同时删掉了自造的 `tmp_path` 覆盖，改用 pytest
> 自带的（`--basetemp` / `TMPDIR` 是标准旋钮），WSL 里从长中文路径直跑也不再撞 AF_UNIX。

### 3.2 Linux 侧（部署目标平台，能多跑 2 项）

Windows 上有 2 项 Linux 契约测试被平台守卫跳过（per-investigation Unix socket、
POSIX owner/mode 与原子软链）。在 WSL 跑可以真正覆盖，但有一个陷阱：

> `tests/conftest.py` 把临时目录放在仓库根下。本仓库路径含中文且很深，
> 经 `/mnt/d/...` 访问时 Unix socket 路径超过 108 字节上限，
> **19 项测试会报 `OSError: AF_UNIX path too long`**。
> 这是测试夹具的路径假设，不是产品缺陷。把代码复制到短路径即可。

```bash
rm -rf ~/ah && mkdir -p ~/ah
cd "/mnt/d/.../OpsMind"
for item in services shared deploy scripts apps .gitattributes; do cp -r "$item" ~/ah/; done
find ~/ah -name __pycache__ -type d -prune -exec rm -rf {} +
python3 -m venv ~/ah-venv && ~/ah-venv/bin/pip install -e ~/ah/services/agent-service[dev]
cd ~/ah/services/agent-service && unset ANTHROPIC_BASE_URL ANTHROPIC_MODEL
~/ah-venv/bin/python -m pytest -p no:warnings -o addopts="" -rs -q
```

实测基线：**406 passed / 1 skipped**。
唯一 skip：`test_repository_investigation_reads.py:346`，需要一次性 MySQL 容器。

## 4. LG（Python）

```powershell
Set-Location <LG 候选工作树>
.\.venv\Scripts\python.exe -m ruff check src tests
.\.venv\Scripts\python.exe -m pytest --basetemp=<短路径> -p no:cacheprovider
```

实测基线（候选 `372d6dc`）：全套 0 失败，ruff 通过。

> 在 Git Bash 下跑会多 3 项 `test_release_recovery` 失败，原因见第 0 节。
> Linux（WSL）侧实测 **370 passed / 1 skipped / 1 failed**，
> 唯一失败是 `test_candidate_presence_compose_renders` 需要 `docker compose`，
> 而 WSL 发行版未开 Docker Desktop 集成；同一项在 Windows PowerShell 下通过。

## 6. 一句话总结

**"套件是绿的"必须连同"在哪个平台、用哪个环境、清没清环境变量"一起说，否则没有意义。**
本轮四条链路修复的全部本地验收，都以本文件记录的跑法与基线为准。
