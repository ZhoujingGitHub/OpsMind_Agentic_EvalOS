# EvalOS Code Grader 重设计方案（2026-09-19，第一版）

> 前置：`EvalOS_CodeGrader全局审查_20260918.md`（六个只读探针的实测结果）。
> 本文在那份体检报告之上，先调研业界做法，再出方案。**每条设计都标了出处。**
>
> 读者是 AI 产品经理，不读代码。英文术语第一次出现给中文解释。

---

## 0. 一句话

**现在的 Grader 用"对关键词"的办法判"自然语言写的因果"，而业界早就不这么干了。**
四个毛病不是四个 bug，是**同一个设计选择**的四种表现。

修法也只有一个：**让根因用机器能比对的语言表达，而不是让机器去读句子。**
好消息是——**这套语言实验室早就有了，AH 和 LG 也早就在用，只是没用在根因这一格上。**

---

## 1. 先把一个关键事实钉死：答卷是结构化的，只有根因那一格不是

产品经理问得对：考生交的是结构化 JSON，为什么还要卡关键词？我核了两个产品的契约：

| 答卷字段 | AH（`tools.py` 报告 schema） | LG（`contracts/investigation.py`） | 机器能直接比吗 |
|---|---|---|---|
| 假设编号 | `hypothesis_id` | `hypothesis_id` | 能，但自由命名 |
| **因果陈述** | **`cause`　自由文本** | **`statement`　自由文本** | **不能 ← 全部问题在这一格** |
| 置信度 | `confidence` 0~1 | `confidence` 0~1 | 能 |
| 假设状态 | `leading/possible/weakened/rejected` | `active/supported/rejected/unresolved` | 能（枚举不同但可映射） |
| **支持证据** | `supporting_evidence_ids[]` | `supporting_evidence_ids[]` | **能，两边同名同义** |
| 反证 | `counter_evidence_ids[]` | `contradicting_evidence_ids[]` | 能 |
| 证据缺口 | `unknowns[]`（已分级） | `missing_evidence[]`（字符串） | 部分 |

**除了因果陈述，每一格都是结构化的。而 Grader 判得最重的恰恰是这一格。**

所以现在的局面是：一份结构化答卷，考场把其中一格拿出来当作文批改。

---

## 2. 业界怎么做——四条证据

### 2.1 不判文字相似，判执行结果

这是目前最硬的共识。

- **SWE-bench**：考生交一个代码补丁，考场**把补丁打上去跑测试**。
  考生的写法可以和参考答案完全不同——**判的是执行，不是文本匹配**。
- **τ-bench**（Sierra 出的客服 Agent 基准）：它的做法是**把题目设计成"终局状态唯一"**，
  然后比对数据库最终状态。原文的说法是：用这种方式
  「把主观、有噪声的人工判断，换成简单客观的数据库状态比对」。

**对 EvalOS 的意义**：这一层 **EvalOS 已经有了，而且是全链路最强的一环**——
实验室侧独立重采业务是否恢复（`business_verification`）、故障链是否消失。
这是执行判定，不是文本判定。**问题不在这一层，在它旁边那层。**

### 2.2 根因不是一个标签，是四层结构化真值

这条最直接对症。RCA100（微服务故障诊断基准，103 个真实故障案例）的真值分四层：

| 层 | 内容 | 怎么判 | 权重 |
|---|---|---|---|
| 1 | **故障类别** | 对照 28 类封闭分类法 | 30% |
| 2 | **根因实体** | **比对实体 ID**，拓扑上相邻的实体给部分分 | 40% |
| 3 | **因果传播链** | 3~4 步的类型化序列，逐节点比对 | 30%（与第 4 层合计） |
| 4 | **证据检查点** | 661 个数值型观测标记，要求匹配 `>=` 这类比较符和具体数值 | 同上 |

这篇论文的核心论断，几乎是照着 EvalOS 现在的毛病写的：

> 传统基准只标注最终的根因组件——这在统计方法和因果图方法下够用，
> 但在 LLM Agent 这个范式下不够，因为它**无法区分"有证据支撑的推理"和"关键词撞对了"**。

注意方向：论文担心的是**关键词撞对（假阳性）**，而 EvalOS 现在的毛病是
**关键词没撞上（假阴性）**——答对了却判零分。但病根是同一个：**用关键词判因果。**

**第 2 层那个"拓扑相邻给部分分"，正好治我们的毛病 4**（"N2 被阻断"判零分）。

### 2.3 ABC 检查清单——逐条对照 EvalOS

Berkeley 那篇《Establishing Best Practices for Building Rigorous Agentic Benchmarks》
提出了 Agentic Benchmark Checklist（ABC，智能体基准检查清单）。
论文报告：不符合这些条目的基准，**性能高估最多可达 100%（相对值）**；
把 ABC 套用到 CVE-Bench 上，**高估减少了 33%**。

下面是清单条目和 EvalOS 的对照，**这是一次体检，不是批判**：

| 清单条目 | 要求 | EvalOS 现状 | 判定 |
|---|---|---|---|
| T.4 环境清理 | 新任务开始前旧状态必须清干净 | 每次 `manage-prepare` 强制复位基线，9 项验证全绿 | ✅ 做得好 |
| T.5 **考生与真值隔离** | 考生不能反查标准答案 | `M3-OBS-001` 特意删掉所有 `tool.result`；作答端点脱敏 | ✅ **做得很好** |
| T.6 环境可复现且冻结 | 发布时冻结 | 基线 `opsmind-m2-baseline-v1` + 内容摘要 | ✅ |
| T.9 **提供标准答案考生（Oracle Solver）** | 用它证明题目本身是对的 | **没有** | ❌ **最大缺口** |
| T.10 检查异常值 | 试跑时查离群点找实现 bug | 没有系统性做 | ⚠️ |
| O.b.1 子串匹配要处理否定词 | 「not」「negative」这类 | 处理了，但**过度处理**——把"修好了"也当成否定 | ❌ 毛病 2 |
| O.b.2/3 防止靠穷举或猜中 | 别让"全列一遍"就能过 | `exclusions` 写「天气不好」也给满分 | ❌ 毛病见审查 P1-3 |
| O.c.1 LLM 裁判要做一致性试跑 | | **不适用**——EvalOS 是纯代码裁判 | ✅ 优于多数基准 |
| O.f.2 消除不确定性 | 结果可重复 | 纯确定性代码 + `grader_digest` 冻结 | ✅ **做得很好** |
| O.g.1 **真值状态要覆盖所有能成功的写法** | | 只覆盖一种命名层级 | ❌ 毛病 4 |
| O.g.3 状态空间要够复杂，随机改动不该蒙对 | | 业务验证这一层满足 | ✅ |
| R.12-13 **要有"平凡智能体"基线** | 空答卷、随机答卷 | **从没跑过** | ❌ **第二大缺口** |

**结论：EvalOS 在"隔离"和"确定性"这两项上比多数公开基准做得好，
败在"真值只写了一种说法"和"从没用平凡基线校准过量表"。**

### 2.4 量表要靠两端锚定，不能靠假设

评分研究里有一条很朴素但我们没做：

> 量表应该**由构造锚定，而不是靠假设**——
> 用一份**空答卷**定下限，用**已发布的参考答案**定上限。

**EvalOS 两端都没锚**。这正是为什么没人发现那个 100 分制**实际只用到 90~100 这一段**：
从来没人拿空答卷去考过（那会暴露下限），也没有标准答案考生（那会暴露上限）。

## 3. 新方案

### 3.1 三条设计原则

**原则一：能执行验证的，绝不做文本判定。**（出处 2.1）
业务恢没恢复，去实验室重采；故障链在不在，去读内核规则。这一层 EvalOS 已经是最强形态，**不动**。

**原则二：必须判"考生说了什么"的地方，用受控词表，不用自然语言。**（出处 2.2）
关键是：**这套词表不用新造，实验室已经在发了，两个产品也早就在用。**

**原则三：不共用代码，共用词表。**
产品经理定过规矩：AH 和 LG 是两个独立产品，不能共用一套判断代码。
本方案**完全遵守**——新增的是一个**数据契约（字段名 + 取值词表）**，
两个产品各自用自己的方式填，考场只读这一个字段。
而且这个词表**本来就是实验室发给两边的**，不是从一个产品搬到另一个。

### 3.2 判定架构（四层）

```
┌─ 第 0 层：执行验证（已有，最强，不动）───────────────────────────┐
│   实验室侧重新采样：UE 能不能上网、SCTP 关联进没进 ESTAB          │
│   内核里那条 DROP 规则还在不在                                   │
│   → 这是 SWE-bench / τ-bench 那一层，是整套体系的地基             │
└─────────────────────────────────────────────────────────────┘
                              │
┌─ 第 1 层：根因判定（重做）────────────────────────────────────┐
│   现在：拿 root_cause 那句话去对关键词                          │
│   改成：比对「故障事实引用」集合                                 │
│                                                              │
│     真值   {policy:sctp:38412:drop-rule-present}              │
│     考生   {policy:sctp:38412:drop-rule-present}   → 命中      │
│     考生   {n2}（只说到接口层）                     → 部分命中   │
│     考生   {process:amf-inactive}                  → 未命中     │
│                                                              │
│   一个中文字都不用读。中英文一视同仁。                            │
└─────────────────────────────────────────────────────────────┘
                              │
┌─ 第 2 层：证据链判定（加强）──────────────────────────────────┐
│   已有：引用的证据能不能溯源（精确率）、必需证据引全没有（召回率）    │
│   新增：被提名为根因的那条事实，**有没有被这个假设的证据支撑**       │
│        （防"撞对关键词"，出处 2.2）                              │
└─────────────────────────────────────────────────────────────┘
                              │
┌─ 第 3 层：自由文本（降级为不判定）─────────────────────────────┐
│   `cause` / `statement` 那句话继续要求写、继续存档、继续给人读，     │
│   **但不再参与任何判定**。                                       │
│   理由：它的作用是让人能复核，不是让机器能打分。                    │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 第 1 层具体怎么做（这是方案的核心）

#### 那套"机器能比对的语言"是什么

实验室的只读诊断工具，返回的不是散文，是**规范事实引用**：

```
process:amf-healthy                      AMF 进程是活的
pcap:sctp-observed                       抓包里看到了 SCTP 帧
policy:sctp:38412:drop-rule-present      内核里有一条丢弃 sctp/38412 的规则
```

最后那条是**从内核实时读出来的 iptables 规则现算的**（协议 + 端口 + 动作），
考生**不看就拿不到这个引用**。这一点极关键：它天然就是"有证据才能说"。

**Grader 已经在用这套词表判证据了**（`required_evidence`）。只是根因那一格没用。

#### 三处改动

**① 题库侧：标出"判别性事实"**

每道题的 `required_evidence` 里，有一条是**只有这个故障才会出现**的。把它单独标出来：

```
现在： required_evidence: [process:amf-healthy, pcap:sctp-observed,
                          policy:sctp:38412:drop-rule-present]

新增： root_cause_fact_refs: [policy:sctp:38412:drop-rule-present]
       root_cause_entity:    {resource_type: service, resource_id: amf}
```

工作量：80 道题各标一次。**不需要写新代码，是标注工作。**

**② 考生侧：假设里加一个字段**

AH 和 LG 各自在自己的假设结构里加同名字段（**各写各的代码**）：

```
AH  hypotheses[].root_cause_fact_refs: ["policy:sctp:38412:drop-rule-present"]
LG  Hypothesis.root_cause_fact_refs:   ["policy:sctp:38412:drop-rule-present"]
```

语义：**在我引用的所有证据里，哪一条（或哪几条）是"故障本身"，而不只是"症状"。**

这个区分本身就是诊断能力的核心——分得清症状和病因。现在两边都只能用散文表达它。

**③ 判定改成集合比对**

```
命中     考生的 fact_refs  ==  真值的 fact_refs
部分命中 考生指的是真值实体在拓扑上的上层（如 n2 之于 sctp/38412）
未命中   其余
```

**"拓扑相邻给部分分"这条出处是 RCA100 的第 2 层。**
而 EvalOS 的实验室**已经把拓扑发给考生了**——今天那次 prepare 返回的资源清单里
就有 `{resource_type: network_path, resource_id: n2}`。所以"n2 是 amf/38412 的上层"
这个关系是现成的，不用新造。

#### 这一改，四个毛病同时消失

| 毛病 | 为什么消失 |
|---|---|
| 1　中文错答全漏 | 不再比对中文字符串。错答会指向 `process:amf-inactive`，而真值是 `policy:...`，集合不等 → 判否。**中英文完全一致** |
| 2　汇报修好了反被判矛盾 | 不再做否定词检测。考生指的是哪条事实，和他怎么描述修复过程无关 |
| 3　括注连累主句 | 不再切句子 |
| 4　换个说法不认 | "N2 被阻断"会指向 `n2` → 拓扑相邻 → **部分给分**，而不是零分 |

**四个毛病都不需要单独修——它们是同一个设计换掉之后的副产品。**

### 3.4 第 2 层：防"撞对"

第 1 层解决了假阴性（答对被判错），但会引入假阳性风险：
考生可以**把所有事实引用都列一遍**，总有一个撞上。这正是 Berkeley 在 τ-bench 里发现的
「把整个数据库倒出来就能通过」那类漏洞（出处 2.3 的 O.b.2/3）。

三道防线：

1. **要精确率，不只要召回率**：`fact_refs` 必须**恰好**等于真值集合，多列就扣。
2. **提名的事实必须被本假设的证据支撑**：`root_cause_fact_refs` ⊆ `supporting_evidence_ids`
   所指向的事实。指了一条自己没取证的事实 → 判否。
3. **领先假设唯一**：只看 `status == leading`（AH）/ `supported`（LG）那一个，
   不许并列一堆等着蒙。

### 3.5 分数体系：从"一个数字"改成"一张能力画像"

体检报告已经量过：**现在的 100 分制实际只用到 90~100 这 9.6 分**，
及格线 75 是空条件。继续维护一个不参与判定的数字没有意义。

改成三样东西：

**① 通过与否 —— 由硬门决定，照旧。** 把空条件 `total >= 75` 从判定里删掉，
契约里写清「通过与否完全由不可补偿的硬门决定」。

**② 能力画像 —— 代替单一总分。** 对外报的不是「92.14 分」，是：

```
执行层    业务恢复   ✅ 实验室独立复测通过
          最小变更   ✅ 1 次写操作（上限 1）
根因层    事实定位   ✅ 精确命中（非拓扑近似）
          实体定位   ✅ service/amf
证据层    可溯源     ✅ 100%（引用的每条都在账本里）
          完整性     ⚠️ 3 条必需证据引了 2 条
过程层    排除竞争   ✅ 4 个备选各带证据
          缺口披露   ✅ 声明 6 个，阻断 0 个
```

**理由**：现在两个产品都通过时分差最多 9.64 分，而且差在"有没有写排除项"
这种格式细节上，**不反映诊断能力差距**。画像能反映，单一数字不能。

**③ 稳定性 —— 引入 pass^k。** 出处：τ-bench。

定义：**同一道题独立跑 k 次，k 次全过才算这道题过。**
论文给的数字很说明问题：**pass@1 是 90% 的模型，k=8 时 pass^k 只有 57%。**

对我们尤其重要——memory 里记着「AH 也会摆动」。
**一次跑过不代表稳定，而运维产品最怕的就是不稳定。**
建议起步 k=3（和清单里那三个种子对齐）。

### 3.6 必须补的两条基线（ABC 清单 T.9 + R.12-13）

这两条是**成本最低、收益最大**的，而且**现在就能做，不用改任何产品代码**。

**① 空答卷考生（null agent）：** 什么都不做、交一份空报告。**它必须 0 分、必须挂。**
如果它能过任何一道门，那道门就是坏的。

**② 标准答案考生（oracle solver）：** 直接按真值填一份完美答卷。**它必须满分。**
如果它拿不到满分，**是考卷有问题，不是考生有问题**。

> **这一条如果早就有，今天审查出的四个毛病会在第一天就暴露。**
> 一个用中文写标准答案的 oracle，会立刻发现「中文禁止主张全漏」和「换个说法不认」。

**③ 顺带补第三个：复读机考生（dump agent）：** 把所有观测到的事实引用全部列为根因。
**它必须挂**（被 3.4 的精确率防线拦住）。

## 4. 迁移路径：不破坏历史，不逼两个产品改架构

| 阶段 | 做什么 | 风险 |
|---|---|---|
| A | 建三个基线考生（空/标准答案/复读机），拿它们去考现有 Grader | **零风险**，纯只读，不改任何代码 |
| B | 修两个纯缺陷（中文归一化、括注切句），补 10 条回归测试 | 低。改法唯一，有测试兜底 |
| C | 题库标注 `root_cause_fact_refs`（80 道） | 低。纯标注，不改代码。用 oracle 逐题验证标对了 |
| D | Grader 新增事实引用判定，**与现有文本判定并行跑、只记录不判定** | **零风险**。这是影子模式，用来量两者差异 |
| E | 看 D 的差异数据，确认新判据不引入假阳性后，切换为正式判据；文本判定降级 | 中。**这一步需要产品经理批** |
| F | AH / LG 各自加 `root_cause_fact_refs` 字段（可选填，老数据不受影响） | 低。加字段是可选的，不填就退回拓扑近似判定 |

**关键是 D 这一步的影子模式**：新老两套判据同时算，只记录不生效。
跑够样本、确认新判据不会放过错答之后再切。**这是唯一能安全换判据的方式。**

### 已澄清、不要再纠结的一个疑问

> 「实验室把根因编号给考生了，是不是等于给答案？」

**不是。** 实验室返回的是**内核里所有 DROP 规则**，每条生成一个编号，
并且代码强制 `record.causal_conclusion == "not_computed"`，否则整条记录作废。
源码注释原话：「规则存在是一个**观测**，不是它导致了这次故障的**证明**」。

**但**在 `sctp-blocked` + 公开基线这道题上，因为基线干净、只注入一个故障，
「整张表里唯一那条异常 ≈ 答案」**确实成立**。
这是**题库的问题**（`hidden-benign-noise` 那 20 道题就是为了破解这个捷径），
**不是判据的问题**——而且今天的体系也一样泄露，甚至更糟：
今天既要求引用它（硬门），又要求用特定中文措辞再描述一遍。
