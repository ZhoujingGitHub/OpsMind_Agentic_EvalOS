# LG 外围整改方案二次客观评估

基于 e34773b 代码、direct-04 原始证据与前次架构审查。此次仅只读复核和文档，不修改产品或启动验收。

结论：存在结构性合同错误，但不等于整个框架应重写。原方案方向正确，尚不足以称最优；本次优先最小端到端纠偏，而非通用多动作计划引擎。

## 对前次方案的修正

1. 不支持异构整包计划本身不是已证实缺陷。本轮证据支持“首个动作后需继续调查”，不支持“预先一定应知道两个修复”。保留现有单动作申请及调查循环，允许多个先后审批的动作即可。不能把未实现通用规划当作必修技术债；已承诺的跨层多次动作能力则必须实现。
2. 不是所有拒绝都应自动回调查。方案过时、目标已满足或证据冲突，可关闭该申请并反馈后继续授权内只读调查；明确结束、全局停止、无安全只读条件须停止。未知写入先对账。不得对同一被拒提案无新依据反复申请，不设固定调查步数上限。
3. 整体成功标准不能替代每步效果标准。动作效果检查当前目标，任务验证检查被冻结的用户可见业务要求；模型可以提出建议，不得自行降低最终验收条件。场景打分规则不得反馈成行动前提或所谓物理健康。
4. 共享控制器有问题不意味着本次必须重写共享核心。优先由LG专属适配与验证路径使用真实观测；若共享入口确实阻塞必要第二次动作，再做边界明确的变更。不能保留错误 task_success 作为新路径回退。AH不改；EvalOS结果接收若合同变更须同步，但不改评分权重或历史。
5. 代码行数和节点数不是复杂度证据。审计、快照、执行票据分别承担取证、新鲜度、幂等用途，应保留；应删除的是多个成功含义互相替代及重复推算。

## 最小完整方案

A. 先验证实验室健康基线：在无注入故障、同一终端/隧道/服务目标下证明业务可达；核实NAT/回程假设。源端探测选错接口与真实隧道失败分开，不把实验室自身问题算Agent能力不足。下一轮有变更前依原授权流程核对准确版本和范围。

B. 在现有验证/证据存储中形成可审计的业务观测：目标、来源接口、采样时间、判据版本、通过/失败/不可用、证据引用。动作是否执行、目标是否达到、任务是否恢复分别表达。无需另建通用问题管理或计划数据库。

发现的补充缺口：actions/safety.py verify() 的新读取结果计算 after_digest，但 VerificationReport.evidence_ids 使用 snapshot.evidence_ids，即执行前证据引用；protocol_lab.read_state 虽记录新回执，外层验证报告没有直接提供清晰的逐项新业务证据关联。不能只给Agent一个effective和一句成功说明。

C. 修正连接规则和结果投影：审批按具体目标当前状态；动作完成或拒绝关闭该申请，允许适当继续调查；任务结果基于最后一次实际改变之后的业务验证与更新的反证，不能取最后提案，也不能取任意一次成功。UI与EvalOS使用一致的结果合同；EvalOS继续独立验证身份、版本、证据和顺序，不盲信LG布尔值。诊断确定性与恢复状态分别展示。

## 方案取舍

- 只删 fault_still_present 分支：改动小，但错误观测和汇总仍在，可能放行无意义写入，不选。
- 立即实现任意多步骤整包审批：引入依赖、部分执行、审批过时、重试/取消等组合，当前收益未证实，不作为本次必要范围。
- 全面重写LG框架：无法据现有证据证明必要，风险最高，不选。
- 沿用已有单动作事务与调查循环，替换错误验证合同、修正控制流和投影：当前最合理候选，仍需测试证明，不能保证全局最优或零缺陷。

## 验收需证明

同一最终候选通过 LG→5G 与 LG→EvalOS→5G；覆盖局部成功但业务失败、先失败后恢复、新提案未执行不覆盖历史、冲突回只读调查、未知写入先对账、两次必要动作不因次数判失败。正常环境不应被探测误报；被拒相同动作无新依据不循环申请；业务不可用与业务失败分开。代码检查、模拟与真实端到端结果分开记录。评测的安全/最小变更维度与实际业务恢复分开，不通过改评分或隐藏失败达到验收。
