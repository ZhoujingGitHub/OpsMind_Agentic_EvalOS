## 一、已确证的结论（面试叙事的地基，可直接引用）

### 1.1 本质是两种编排方式的对比

**LG = workflow 编排（准确说是 agentic workflow）；AH = agent 编排。**
两者都在用大模型，差别不在"有没有用 agent"，在**谁决定下一步**。

**LG 的模型接口**（`src/opsmind_langgraph/graph/agent.py`）：

```python
decide(AgentTurn) -> AgentDecision
AgentTurn.stage: AgentStage                        # 引擎告诉模型它在哪个阶段
AgentDecision.quality_decision: QualityDecision    # 模型对路径的唯一发言权
```

`QualityDecision` 只有 4 个值：`continue` / `propose_action` / `finalize` / `insufficient_evidence`。
`AgentStage` 只有 6 个：`initialize` / `reason` / `revise` / `adjudicate` / `finalize` / `action_proposal`。

图本身是 **27 个节点 + 固定边**（`builder.py:2310-2476`）。条件边一律是
`lambda state: state["<某个枚举字段>"]` 加一个**固定的目标节点字典**。

所以：**模型读的是一份菜单，不是一张地图。** 它能影响走哪条边，但边和目标都在编码期写死；
它甚至不知道自己在整体流程的哪一步——`stage` 是引擎喂给它的。

**AH 没有这个接口，因为没有节点。** `ClaudeSDKClient` 原生 agent loop，模型直接生成下一个
工具调用。`max_turns`（= `max_model_calls`）和 `max_budget_usd` 是**熔断丝，不是路径**。

| | LG | AH |
|---|---|---|
| 智能在哪 | **节点内部**（局部） | **循环本身**（全局） |
| 路径谁定 | 编码期，工程师 | 运行期，模型 |
| 边界谁定 | 编码期，工程师 | 编码期，工程师 |
| 一句话 | **局部自由、全局固定** | **全局自由、边界固定** |

### 1.2 工具数量不是差异，种类才是

数出来的真实数字：

| | MCP 工具 | 其他 |
|---|---|---|
| LG | **约 30 个**（协议诊断 14、清单 7、观测 7、历史/续读 2） | 无 |
| AH | **39 个**（`TOOL_SPECS` 37 域 + 2 协议） | **10 个 SDK 原生工具** + **21 个领域 Skill** |

数量同一量级。**差异是种类**：AH 的 `NATIVE_TOOLS` 含
`Read/Glob/Grep/Write/Edit/Bash/WebSearch/WebFetch/Skill/ToolSearch`，LG 一个都没有。

### 1.3 AH 的优势（五条，均可指到代码）

1. **下一步不必预先枚举。** "先回头把第二个假设的那条证据重新核一遍，再决定要不要扩大范围"
   ——这个意图在 4 个枚举值里表达不出来，只能压缩成 `continue` 回到选工具节点重来。
   **故障调查的假设空间无法穷举，这是 workflow 的结构性天花板。**
2. **工具集不封闭——这是"开放世界"的实质。** AH 能现场写脚本把几份已授权证据交叉比对；
   LG 只能调预定义只读工具，做不到"事先没预见到的分析"。
3. **外部知识入口。** AH 有 `WebSearch`/`WebFetch`，LG 无。
4. **方法论由模型按需取。** AH 的 21 个 Skill 由模型自己决定调哪个；
   LG 的 `AgentTurn.knowledge` 是 `tuple[str, ...]`，塞什么由引擎代码决定。
5. **工具目录可增长而不撑爆上下文。** AH 的 MCP 工具是 deferred 的，靠 `ToolSearch` 按需发现，
   只有 2 个协议工具 `alwaysLoad`。这是能力目录往上堆的前提。

#### 1.4.1 查实的机制：Evidence Gate 的唯一升级手段是"停"（面试可直接讲这一段）

链路②（LG 直连、不经 EvalOS）复现了链路④ 的完全同一形态，所以**排除了"EvalOS 那条路上的偶发"**。
`public_events` 重建出的节点路径（事件 80–86）：

```
80 release_action_lease
81 investigation.reopened          ← 动作验证有效后，图确实回头了（不是"图回不去"）
82 resume_investigation
83 revise_hypotheses      qd=finalize                 ← 模型说：查完了，发布
84 quality_gate           qd=continue → adjudicate    ← 引擎推翻，强制复核一次
85 adjudicate_hypotheses  qd=finalize                 ← 模型又说：发布
86 quality_gate           qd=insufficient_evidence    ← 引擎再次推翻，判停
```

代码在 `src/opsmind_langgraph/graph/builder.py:1197` `quality_gate` 的最后一个 `else`：
Gate 不过且假设摘要已复核过 → 强制 `INSUFFICIENT_EVIDENCE`
（`gate_override_reason = "evidence_gate.publication_blocked_after_review"`）。
而 `INSUFFICIENT_EVIDENCE` 在 `builder.py:2359` 的路由表里**只有一个出口**：`finalize_and_learn` → END。

**Gate 的判断本身没错**：`network.restore_policy` 对 n2 的动作顺带重启了无线运行时，
所以"业务恢复"不足以独证"只有 DROP 规则移除起效"——这是对的，也是诚实的。
错的是 **Gate 能说"不行"、能说"再复核一遍"，但说不出"去补 X"**。

判停那一刻，引擎在同一个节点里算好并写进 state 的 `remaining_evidence_opportunities`
第一项就是 **`capture_protocol_summary`**——正是 Gate 自己点名要的"动作后 SCTP 关联与 NGAP 原始帧"。
LG 自己写在 `unresolved_questions` 第一条：
> 动作后未重新采集 SCTP 关联与 NGAP 原始帧，阻断将 h3 升级为 confirmed。

**所以差的不是智力，是词汇量。** 模型对路径的唯一发言权是 4 个枚举值；Gate 与模型不一致时
Gate 赢，而 Gate 赢的那个枚举值通向出口。模型两次说"发布"，两次被改判，然后被送出门。
AH 没有 Gate 节点、没有枚举、没有改判——读到同一个缺口就再调一次采集工具，
同一道故障发布了 confidence 0.92 的根因、17 条聚焦证据、并逐条否证了竞争假设。

> **"开放调查"的实质，在这条 trace 里具象成了一件很小的事：能不能说出"我还想再看一眼"。**

边界：这**不能**反过来证明 AH 更稳，两边各只有 2 个样本。详见 §3.1。
完整验收记录见 `四条链路重新验收_20260916.md`。
2. **成本不可控**：LG 的模型调用次数天然有上界（节点数 × 循环数）；AH 必须靠熔断。
3. **难定位**：LG 能说"卡在 `execute_rollout_step`"；AH 只能说"停在某个工具调用上"。
4. **会用错自由**：RUNBOOK 坑 10 实证——AH 的 Agent 自己跑 `sleep` 等审批，撞 30 秒看门狗 fail-closed。

### 1.5 LG 的双模型机制（讲第一幕时用）

`deepseek-v4-flash`（常规）/ `deepseek-v4-pro`（`thinking` 开启），按 stage 自动切换：
`DELIBERATIVE_STAGES = (REVISE, ADJUDICATE, FINALIZE, ACTION_PROPOSAL)` 用 pro，其余用 flash。
AH 是单模型 + `effort` 参数。

### 1.6 迭代故事六幕

1. **LG**：把专家排障流程固化成 27 节点的图，每步可预测、可审计、可定位；节点内部用双模型
   做局部判断。**它不是规则引擎，是 agentic workflow。**
2. **撞天花板**：图能表达的是已知套路；真实故障的下一步不总在 4 个出口里，
   而节点只能调预定义工具。**问题不是不够聪明，是编排方式限制了智能能落在哪里。**
3. **AH**：控制权交给模型，边界交给工程。模型可选假设/工具/停止时机；
   不可选种子、预算、隔离、安全门、盲审身份、评分器、账本。动作永远走
   提案→预检→独立审批→执行→验证→回滚，**Agent 无权自批**。
4. **EvalOS**：不可变账本、确定性评分、硬门、业务真值独立验证。对照实验证明评分不放水。
5. **5G 数字孪生实验室**：可复现故障、单一物理租约、断电隔离、可复位。
6. **当前诚实结论**（2026-09-16 复验后改写）：这道封闭故障题上，**AH 两次都是 96.43**，
   **LG 一次 100、一次 39.29**。满分 70 制。LG 那次 39.29 不是能力回归——它修好了、
   业务真值也过了，扣分在"根因没写进结构化字段 + 结论报成 inconclusive"这两处契约上。
   所以当前能讲的是：**两套架构都能把这类明确故障查清并修好，但 LG 的报告契约合规性
   在逐次之间会摆动**；而"哪种编排更适应真实千变万化的故障"这道题，**一道封闭题四次运行
   仍然回答不了**。
   **这道题测不出两种编排方式的差异。**

## 二、为什么现在测不出差异（两个原因叠加）

### 2.1 考卷不考

当前 Case（`M3-OBS-001@3.2.0`）把 9 个维度中 4 个声明为不适用并从满分剔除，实际满分 70：

| 维度 | 权重 | 本 Case |
|---|---|---|
| task_success | 25 | 适用 |
| rca_quality | 15 | 适用 |
| evidence_quality | 15 | 适用 |
| trajectory_quality | 15 | 适用 |
| engineering_agility | 5 | 不适用 |
| **open_world** | **15** | **不适用** |
| **proactive_capability** | **5** | **不适用** |
| resource_cost | 5 | 不适用 |
| recommendation_quality | 0 | 仅资格信号 |

而且 `open_world` 实际考的**不是**开放调查。看 `grader.mjs:355-356`：

```js
openWorldApplicable = recoveryRequired || expectedStatus === "inconclusive";
openWorldScore      = openWorldApplicable ? (recoveryPassed && statusHit ? 1 : 0) : null;
```

`recoveryRequired = caseSpec.ground_truth.requires_tool_recovery`，
`recoveryPassed = !recoveryRequired || (recovery.failureCount > 0 && recovered)`。

翻成人话：它考的是**韧性与诚实**——故意埋工具故障，看能否自己缓过来；或真值本身是
"查不出来"，看敢不敢如实说。**"开放调查能力"在现有 9 个维度里根本没有对应考题。**

### 2.2 AH 自己的手还没铺开

| 17–23 | 业务、报文与诊断可靠性调查 | **待开始** |

## 三、待办项

### 3.1 批量故障评测（产品经理 2026-09-16 明确方向）

> "要对比 AH 和 LG 哪个更好、更适应真实千变万化的网络故障，**不是几道 case 能说明问题的，
> 需要制造不同类别的故障批量测试。**"

当前样本量是 **1**：一道题（`M3-OBS-001`）、一个场景（`sctp-blocked`）、
一个种子（`2026081601`）、`repetitions: 1`。在这个样本上比较两种编排方式，结论不成立。

**待办 A：故障分类学（先做这个，它决定其余一切）**
按 5G 端到端分层列出故障类别，每类给出可在数字孪生实验室复现的注入方式：
终端/CPE、RAN 无线、承载 IP、5GC 控制面、5GC 用户面、切片与 QoS、MEC 应用与业务、
DNS 与寻址、配置与变更、容量与趋势、可观测性盲区。
每类再分：**边界清楚的封闭题** / **需要自己定边界的开放题** / **真值是"查不出来"的题** /
**多因叠加题** / **误导性症状题（相关但非因果）**。

**待办 B：让 `open_world` 与 `proactive_capability` 真正生效的考题**
- `open_world` 生效条件已知：`requires_tool_recovery = true` 或 `expected_status = inconclusive`
- `proactive_capability` 生效条件：`visible.trigger_type = "proactive"` 或 `ground_truth.proactive_expected`
- 这两个开关现在是**可用但没用**。先做只改 Case 契约、不改评分权重的考题
- **注意边界：不改评分权重。** 要新增维度必须单独审批

**待办 C：批量运行的工程条件**
- `repetitions > 1` + 多 `environment_seeds`，用于把"逐次波动"和"能力差异"分开
  （③ 的 96.43 就是波动，不是回归）
- **单一物理租约是批量测试的瓶颈**：实验室一次只能有一个租约，批量跑必然串行。
  跑 N 类 × M 重复 × 2 考生的总时长要先估（AH 约 5 分钟/次，LG 约 20–30 分钟/次）
- 成本要先估：上一轮实测 AH 单次约 4.72 美元
- 结论口径：**按类别出分布，不出单一总分**。"哪个更好"要变成"哪类故障上谁更好"

**待办 D：AH 的 23 项采集能力**
不做这个，开放题上 AH 也只有上一代 37 个工具。但**它排在 A/B 之后**——
先知道要考什么，再决定补哪些手。
