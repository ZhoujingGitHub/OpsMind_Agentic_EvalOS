## 2. 实测数据，以及它推翻了什么

### 2.1 原始数据（线上 20 次真实运维）

```
A 生效档位分布       : confirmed 12 | probable 7 | inconclusive 1
B 门的判决            : 判过 20 | 判不过 0
C 领先假设的独立血缘数 : 3→2例  4→7例  5→6例  6→2例  7→3例   （门只要求 >=2）
D 建议 kind 分布      : remediation 13 | no_change 16 | collect_evidence 23
E 自称 confirmed 且自己列了缺口 : 12 / 20   ← 也就是「全部 confirmed」
```

### 2.2 被推翻的那条：`missing_evidence` 不能直接当判据

我原来提的第四根杆是：

> `confirmed` + `missing_evidence` 非空 → 降为 `probable`

**实测 E 行：12 个 `confirmed` 全部都填了缺口。**

**所以这条规则的实际效果是：AH 从此再也不可能输出 `confirmed`。**
那不是「防过度自信」，那是**全面禁用 `confirmed`**。

### 2.3 为什么全都有缺口——看真实的缺口内容

12 例的缺口高度一致，全部是同一类：

| 真实缺口原文（节选） |
|---|
| 该 DROP 规则的注入时间线：本次未查询变更/审计类数据源，因此规则的安装时间、操作主体与变更单均无证据 |
| 无变更记录入口可查：谁在何时添加该规则，仍属未查证事项 |
| 策略变更来源缺口：`query_changes`、`query_events`、`query_alarms`、`query_logs` 对本次授权范围均返回空 |
| AH 数据库对标识域 `opsmind-twin` 的解析覆盖为 `none` |
| DROP 规则的注入时间与上游变更来源**超出授权可观测范围** |

**全部是「这条规则是谁、什么时候加的」——而答案是：变更/审计数据源对实验室孪生标识域根本没有覆盖（`coverage_status=none`）。**

### 2.4 关键：规则来源不属于根因

- **根因** = 有一条 DROP 规则在丢弃 SCTP 38412 报文 → **因果链是闭合的**
- **规则来源** = 谁加的、什么时候加的 → 这是**溯源**，不是**因果**

**所以这 12 份报告的行为是对的**：确认了根因，同时如实披露溯源查不到。
**我的规则会因为一个与根因无关的缺口，去否决一个成立的根因结论。**

### 2.5 LG 早就区分了这件事

LG 的门用的字段叫 **`blocking_evidence_gaps`**——**阻断性**缺口。
它的检查项说明写得很清楚（`governance/evidence.py:184`）：

> 可信观测不等于因果确认：需明确结论层级，并处理**会改变该机制判断的**阻断缺口。

**LG 分「会不会动摇根因」；AH 的 `missing_evidence` 是一个平铺列表，不分。**

**这就是 P0 的全部理由。**

## 3. P0 · 给 `missing_evidence` 分级

### 3.1 现状

```json
"missing_evidence": [
  "DROP 规则的注入时间与上游变更来源超出授权可观测范围",
  "恢复后 N2/SCTP 关联的协议级抓包复检未留存"
]
```

一个字符串数组。**看不出这两条里哪一条会动摇根因**（答案：都不会）。

### 3.2 改成

```json
"missing_evidence": [
  {
    "gap": "DROP 规则的注入时间与上游变更来源",
    "blocks_root_cause": false,
    "unavailable_reason": "out_of_authorized_scope"
  },
  {
    "gap": "恢复后 N2/SCTP 关联的协议级抓包复检",
    "blocks_root_cause": false,
    "unavailable_reason": "not_retained"
  }
]
```

**两个新字段，含义都很窄：**

| 字段 | 取值 | 判据 |
|---|---|---|
| `blocks_root_cause` | `true` / `false` | **补上这条，会改变我对根因机制的判断吗** |
| `unavailable_reason` | `out_of_authorized_scope` 超授权<br>`no_data_source` 数据源无覆盖<br>`not_retained` 数据未保留<br>`budget_exhausted` 预算耗尽<br>**`can_be_collected` 其实能采** | 为什么现在补不上 |

### 3.3 `can_be_collected` 是整个设计的关键

它让「能补但没补」**变成一个可枚举的状态**，而不是靠猜：

- 填了 `can_be_collected` → **那就该回去采**（这时 §5 那种推迟机制才有意义）
- 填了另外四个 → **补不上，如实披露即可**

**一句话：不许光说「缺」，要说「为什么补不上」。填不出理由的，就是该回去补的。**

### 3.4 兼容性

- **旧格式必须继续接受**（纯字符串）→ 视为 `blocks_root_cause: false`、`unavailable_reason: null`
- 理由：`missing_evidence` 是 `required` 字段（`tools.py:185`），且**被交付摘要覆盖**，不能硬切

### 3.5 改动清单

| 文件 | 改什么 |
|---|---|
| `tools.py:150` | `missing_evidence` 的 schema 加 `oneOf`：字符串 **或** 上面那个对象 |
| `harness.py:131` 提示词 | 说明两个新字段，并明确「与根因无关的溯源缺口应填 `blocks_root_cause: false`」 |
| `contracts.py` | 归一化函数：旧格式 → 新格式，供门与下游统一消费 |
| `evidence_gate.py` | **本期不改判据**，只在 `gate` 里增加两个统计：`blocking_gap_count`、`collectable_gap_count` |

### 3.6 为什么 P0 只做「分级 + 统计」，不动判据

**因为现在没有数据支持任何判据。**

12 例全部有缺口，但**没人知道其中几例是阻断性的**——`missing_evidence` 不带这个信息。

**先让字段产出这个信息，攒几次真实运维，再决定判据。**
这和轨道 A 的做法一致：**先量，再改。**

## 4. P2 · 降一档，而不是一律降到底

### 4.1 问题（逻辑不一致，仍然成立）

`evidence_gate.py` 的门**已经是三根杆**：

```python
if original in _STRONG_CONCLUSIONS:   passed = 编号真 and 2条证据 and 2个独立血缘   # 杆①
elif original == "possible":          passed = 编号真 and 至少1条有效证据           # 杆②
else:                                 passed = True                                 # 无杆
```

**但跌落只有一种：**

```python
effective = original if passed else "inconclusive"
```

**从「确认」掉下来是跌 3 级**，跳过了「概然」和「可能」。
一份有真实已核验证据、只是来源不够独立的报告，会被说成「我不下结论」——**失真**。

### 4.2 改成沿梯子走一遍

```
确认 ── 杆① 不过 ─► 概然 ── 杆① 不过 ─► 可能 ── 杆② 不过 ─► 证据不足
```

（本期 `confirmed` 与 `probable` 仍共用杆①，所以第一步是直通；
等 P0 攒够数据、确定判据之后，这一步才会有实际区分。）

### 4.3 不会放宽任何安全控制（已核实）

`tools.py:293`：

```python
if conclusion in {"possible", "inconclusive"}:
    errors.append("unconfirmed_report_cannot_publish_remediation")
```

**「可能」和「证据不足」在"能不能发修复建议"上是同一档。**
所以降到「可能」而不是「证据不足」，**权限完全不变，只有信息保真度提升**。

### 4.4 为什么是 P2

**门 20/20 全过，而且余量充足**——独立血缘数最少是 3，门只要求 2。
**这条修的是一条从未被走过的路径。** 逻辑该修，但不紧急。

## 5. P2 · 门降档后复查修复建议（原疑点的结论）

### 5.1 疑点查清了：机制成立，但从未发生

**机制（代码层已确证）：**

1. 模型提交报告 → 校验（`tools.py:291-294`，**按模型自报的档位判**）→ 通过 → **落库 + 发交付回执**
2. SDK 流结束 → **门才跑**（`harness.py:2256`）→ 降档只改内存里的 `report` 字典
3. `update_investigation_fields(..., report_json=report)`（`harness.py:2298`）→ **降档后的报告写回库**

**所以一旦发生降档，会同时产生两个后果：**

| 后果 | 说明 |
|---|---|
| **A. 违反 AH 自己的规则** | 落库报告是 `inconclusive`，却仍带着 `kind=remediation` 的建议。**同一份报告若一开始就填 `inconclusive` 提交，会被 `tools.py:293` 拒绝** |
| **B. 交付摘要不再匹配** | 门改了 `conclusion_status`、`missing_evidence`、`stop_reason` **三个被摘要覆盖的字段**（`formal_report_material` 只排除 `delivery_receipt` 与 `evidence_gate`）→ `accepted_formal_report()` 对这份报告将返回 `None` |

**实测：0/20 发生过降档。所以这是一条没被走过的路径，不是正在发生的故障。**

**但摘要机制本身被实测证实了**：20 例判过的报告抽查 5 例，摘要**全部 MATCH**——
因为判过时 `effective == original`，三个字段一个没改。
**这正好从反面印证了「降档会导致 MISMATCH」。**

### 5.2 后果 B 目前不会爆，但是个陷阱

`accepted_formal_report()` 只在 `interrupted_investigations()` 恢复路径上跑（`harness.py:256`）。
而两条写回路径**都在同一次调用里把状态置为终态**，所以降档后的行不会再被恢复路径捞到。
对外 API 与导出路径**直接读 `report_json`，不校验摘要**。

**所以这是一个陷阱，不是一个故障。** 而它正对着轨道 C 的「事实卡片」：
**任何基于 `accepted_formal_report()` 去读历史报告的新代码，会静默丢掉每一份被降过档的报告。**

### 5.3 改法

| 后果 | 改法 |
|---|---|
| **A** | 门降档后**复查建议**：若生效档位是 `possible`/`inconclusive` 而报告仍带 `remediation`，把该建议降级为 `collect_evidence` 或移入 `human_follow_up`，并在 `gate` 里记录这次降级 |
| **B** | **二选一，需要拍板**：<br>**①** 门的降档结果**不写回** `report_json`（只留在 `evidence_gate` 块与事件里）→ 摘要永远匹配，但「生效档位」要从 gate 块读<br>**②** 降档后**重算并更新回执摘要**，同时保留原摘要 → 回执变成两段：as_submitted / as_effective |

**我倾向 ①**：交付回执的语义应当是「Agent 交了什么」，那是不可变的事实；
「系统判定生效什么」是另一件事，**本来就该放在 gate 块里，而它已经在那儿了**
（`evidence_gate.original_conclusion_status` / `effective_conclusion_status`）。
① 只需要停止写回，改动更小，而且让「回执 = 不可变提交物」这个语义变干净。

## 6. 与考场那边的关系：P0 顺带修掉考场的 `pending` 问题

提案第八部分（8.2）记录了考场的一个必改项：

> `grader.mjs:109` 的 `pending` 正则（`是否|待查|尚未确认|unconfirmed`）命中即判「根因未成立」→ **35 分归零**。
> 所以一句「很可能是 X，尚未确认哪条规则」会被判答错。

**P0 做完之后，考场就不必再去正则匹配散文了：**

| | 考场现在怎么判「结论是否闭合」 | P0 之后可以怎么判 |
|---|---|---|
| 依据 | **正则扫报告正文的措辞** | **读 `blocks_root_cause` 字段** |
| 性质 | 措辞（可改写、可规避） | **行为**（结构化声明） |
| 后果 | 保守型 Agent 被双重惩罚 | 犹豫扣校准度，**不扣根因** |

**一个字段，同时解决产品侧（AH 无法区分阻断缺口）和考场侧（拿措辞当判据）。**
这也是 8.2 给出的修法方向（「看缺口，不看措辞」）第一次有了落地载体。

## 7. 边界与验证

### 边界（不越的线）

- **不动 LG，不动 EvalOS 考场判分**
- **不放宽任何安全控制**：§4.3 已核实权限不变；§3 只加字段、不改判据
- **旧格式必须继续接受**（`missing_evidence` 是必填且被摘要覆盖）
- **不改历史报告**：不回填、不重算已封存的证据

### 验证

| 阶段 | 怎么验 | 成本 |
|---|---|---|
| 单测 | 新旧格式并存、归一化、门的两个新统计、§5.3 的建议降级 | 零 |
| 回归 | AH 现有测试全过 | 零 |
| 真实 | 跑一次链路①，确认 20 例的行为**一个都没变**（P0 不改判据，应完全一致） | 一次链路 |
| 攒数据 | 之后每次运维读 `blocking_gap_count`，攒够了再谈判据 | 随常规运维 |

**P0 的验收标准是「行为零变化 + 多出两个统计字段」**——
**如果跑完发现档位分布变了，说明改错了。**
