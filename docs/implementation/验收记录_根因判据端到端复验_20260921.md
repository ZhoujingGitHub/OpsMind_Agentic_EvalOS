## 第五张图：两个产品栽在哪，栽法还不一样

新判据的核心是「**恰好命中一条**」。八道里七道没做到，但失败方式分两种：

```
【考生乙的毛病】 指得太笼统
    它写「有一条丢包规则」这类描述  ──► 对上 2 条 / 6 条 ──► 判没指准
    （隐藏噪声那道题里本来就有两条丢包规则，这正是那道题要考的）

【考生甲的毛病】 指的东西根本找不到
    它写的字段在它自己引用的那条证据里  ──► 一条都对不上 ──► 判指不明
```

两边还都犯过同一个错：**把自己查询的元数据当成观测字段交上来**——
比如"匹配到几条""扫了哪些表""数据来源总数"。那些是它查询动作的描述，
不是现场那条记录的内容。

**这不是判据的问题，是两个产品的提示词没把"要缩窄到唯一一条"讲透。**
判据这边反而全部按设计动作：该分开的分开、该判否的判否、该兜底的兜底。

## 第七节：我自己拍的板 + 一个要你定的点

### 已拍的（延续昨晚那六条，这里只说新增的）

**① 登记要改三份配置，不是手册说的"重新登记考生版本"一件事。**
冻结清单、签名报到的预期版本、实测部署身份——少改一份，全套检查就报
"实测提交与冻结版本不一致"。已写进提交信息。

**② 考场发版后必须确认服务真的换了目录。**
第二次安装后指针翻了、`maint status` 也报新版本，但**进程还跑在上一个 release 的目录里**，
所以新冻结源没生成、开考检查一直拦。`ls -l /proc/<pid>/cwd` 一看就露馅。
**所有状态输出都显示"已升级"，只有这一处说真话。** 重启后才真正切过去。

**③ 没跑那两道直连对照链路。** 理由见最后一节，不是忘了。

### 要你定的一个点

**「东西不见了」那一类指认，现在完全不校验。**

判据规定：标成"缺失"的指认不去记录里查（因为东西已经没了，没得查），
直接拿考生写的内容和真值比。代价是——**考生可以在这一栏写任何东西**，
写错了只会被当成"多指了一条"扣分，不会被判为格式错误。

真跑里两个产品都用这一栏塞过查询元数据。两种改法：

| 做法 | 结果 |
|---|---|
| **保持现状**（我现在这样） | 乱写只扣分，不额外判错。简单，但那一栏等于没有门槛 |
| **加字段名校验** | 写的字段名必须是那类观测真有的，否则这条指认直接不算数 |

第二种更严，但它改的是考试标准，**我不替你定**。说一句就改，改动很小。

## 唯一没做完的：两道直连对照链路

**没做的原因不是技术问题，是时间窗口。**

直连链路要走产品机，而产品机只能用阿里云云助手进，那套凭据是**人的登录凭据、
有效期只有 3 小时**，当时只剩 50 分钟。而直连一道要：手动准备实验室 → 提交调查 →
等它跑到审批点 → 以独立裁判身份审批 → 等完成 → 封存 → 复位。

**中途凭据断掉的话，实验室租约会悬在那里，挡住下一轮所有实验。**
这个代价比"少一组对照"大得多，所以我停在这里。

### 补做方法

```bash
# 1. 先重新授权（浏览器扫码，约 1 分钟）
& "D:\...\OpsMind\.tools\aliyuncli\aliyun.exe" configure --profile opsmind-main-oauth --mode OAuth --oauth-site-type CN

# 2. 两道直连，口径与 2026-09-18 那轮一致
_work/claude-takeover-20260911/tools/ah-direct-submit.sh
_work/claude-takeover-20260911/tools/lg-direct-submit.sh
```

### 根治办法（建议下一轮先做）

把产品机和实验室的凭据从 OAuth 换成 **AccessKey 或 RamRoleArn**——长期有效、
没有任何人工步骤。今晚为了这个凭据反复中断了好几次。
考场那台机已经不受影响（走 WireGuard 隧道，密钥长期有效）。
