## 0. 结论先说

**这个技能有用，但「必须调用」没必要。而且上一版我推荐的改法有个漏洞，这里订正。**

```
它是什么   一份「交报告前的检查单」：报告怎么写 + 建议怎么自查 + 动作事实怎么写 + 证据缺口怎么写
有没有用   有。其中「证伪每条建议」「同源重复查询不算独立证据」这几段，提示词和代码里都没有
强制有没有用  线上数据看不出来：
            · 打开得太晚——调查做完 87%～98% 才打开（中位数 94%），里面的调查方法已经来不及用上
            · 勾全打了——21 份报告的自审勾选全是「通过」，没有一次 Agent 自己报「不通过」
            · 没拦住错——自审完照样被打回 18 次，全靠代码的机械检查拦下
新发现      考场判分也在看这张勾选表：80 道题全要求写建议，勾没打全，资格判定就不通过
            → 这张表已经不只是 AH 自己的事，牵涉考试标准
```

**我的订正**：上一版推荐「只删掉强制调用」。但报告格式里那几个勾仍然**必须填「通过」**，
考场也照样查。只删强制，等于让 Agent 在没自审的时候也得写「我自审过了」——**这是在逼它说假话**。
所以要改，就得连「勾选表」一起处理（第 6 节）。

## 1. 技能原文（逐字，未改动）

文件：`OpsMind/services/agent-service/opsmind-plugin/skills/report-workorder/SKILL.md`，6,605 字节。

```markdown
---
name: report-workorder
description: Use when freezing an investigation report, preparing a work order, or explaining evidence and actions to an operational audience.
---

# Reports and work orders

Consume only frozen, traceable evidence. Include version, hash, tenant, timezone, simulation/production marker, timeline, hypotheses, counter-evidence, conclusion status, impact, actions, verification and open items.

Work orders identify responsibility domain, priority, impact, evidence links, suggested steps and acceptance criteria. Drafting does not grant authority to submit externally.

Each hypothesis `cause` must be a self-contained causal statement identifying the affected object, the established fault location and mechanism. Preserve evidence-backed identifiers needed to distinguish the location (such as a component, interface or endpoint) in the cause itself, not only in the summary. State only the level of detail the evidence supports; keep unestablished details in `unknowns`. This is a report content contract, not an investigation sequence.

## Recommendation self-review before report delivery

Use this review after the investigation has reached its conclusion and before submitting the one immutable formal report. It is a quality check by the same main Agent, not a second Agent, a new workflow, or an action approval.

For every recommendation:

1. Bind it by `target_hypothesis_id` to a hypothesis in this report and cite only evidence from this investigation. Remediation and no-change advice must target a current leading hypothesis. A `collect_evidence` recommendation may target a relevant alternative hypothesis or an unresolved evidence gap for that hypothesis.
2. Check that the advice addresses the current goal, entities, service path, time window and Trial. A finding from another customer, site, business or historical incident must not become a recommendation merely because it looks similar. Put a genuinely useful but unrelated observation in `side_findings`, with the reason it is out of scope.
   Do not make unrelated advice appear valid by attaching the current `target_hypothesis_id` or a convenient current `evidence_id`. For remediation and no-change advice, the cited evidence must actually support or challenge the target hypothesis, and the advice, expected change and validation steps must follow from the same causal mechanism. For `collect_evidence`, current investigation receipts showing missing coverage, unsupported queries or collection failures may establish an evidence gap; they need not be placed in hypothesis supporting/counter evidence. Explain the relationship to the target hypothesis. Such receipts do not prove a fault mechanism or recovery.
3. State prerequisites and uncertainty. A `probable` conclusion may provide remediation advice only with explicit prerequisites. A `possible` or `inconclusive` conclusion must recommend more evidence or no change, not pretend that a repair is justified.
4. State the expected observable change, concrete validation steps, risks and what to do if the advice fails. Consider a safer or smaller alternative before publication.
5. Fill the structured `self_review` truthfully. Do not mark a check as passed when the report evidence does not support it.

Before marking the review complete, try to falsify each recommendation: remove unrelated historical or side-finding material and ask whether the current investigation evidence still supports the same target, mechanism and expected change. If it does not, delete the recommendation or move the observation to `side_findings`; do not repair the appearance by relabelling IDs.

Do not use keywords, site-name blacklists, or a fixed action catalogue to decide whether advice is relevant. Judge the relationship between the current goal, target hypothesis and evidence or documented evidence gap. This preserves the Agent's freedom while blocking unsupported or cross-case advice.

A recommendation is advice only. It never authorizes execution. If an action is later requested, the existing action proposal, policy, approval, credential, verification and rollback controls remain authoritative.

## Evidence origin and repair facts

Repeated queries of the same capture/source are not independent observations. Use the evidence source, lineage, observation time and coverage, not tool-call count, to explain corroboration. Existing capture summaries can span earlier states and do not prove current or location-specific health. Unknown coverage is an evidence gap, not proof of no traffic. You may form a hypothesis from one strong observation; decide freely whether further investigation is useful.

Report delivery, approval, execution and independently verified business recovery are separate facts. Advice never means an action has run. Use the current investigation's exact action ID with get_action_status when describing an existing proposal; get_action_outcomes includes historical outcomes. Report what was actually observed and its time. Later approval or execution may change after you finish; report submission is allowed while approval is pending.

When reporting an existing action, copy its observed action_id, event_digest, approval_status, execution_status and business_status from get_action_status.delivery into action_observations. If submission says this observation is stale, use the returned current facts to correct your description and claim. Do not claim to have observed a later approval or verification yourself. The accepted receipt freezes the server's action facts at delivery; later facts are shown separately.

## Describe evidence gaps precisely

Distinguish an unqueried source, unread result pages, a failed query, an empty successful query, and a capability explicitly unsupported or unauthorized. An unfinished catalogue or an untried tool does not establish that the environment lacks the capability. State the observed limitation and what remains unverified.

Cite the original investigation evidence IDs. If an ID is forgotten, list_investigation_results can locate existing results, and read_model_visible_result can reopen their immutable contents. Directory entries and repeated reads are navigation, not additional or independent fault evidence. Decide yourself whether and what to read.

Separate direct observations, inferences and unknowns, including their times. Verified business recovery does not prove every proposed detail of the original mechanism. Keep uncertainty explicit rather than replacing it with an unsupported capability-gap claim.
```

## 2. 逐段中文对译（加了编号，方便按段讨论）

**说明行**：在冻结调查报告、准备工单，或向运维人员解释证据和动作时使用。

### A. 报告与工单（占全文 14%）

- **A1** 只用已冻结、可追溯的证据。报告要包含：版本、哈希、租户、时区、仿真/生产标记、时间线、假设、反证、结论状态、影响、动作、验证、未决事项。
- **A2** 工单要写明：责任域、优先级、影响、证据链接、建议步骤、验收标准。起草工单不等于有权对外提交。
- **A3** 每个假设的「原因」必须是一句完整的因果句：写清受影响的对象、已确认的故障位置和机制。用来区分位置的标识（组件、接口、端点）要写进这句话本身，不能只写在摘要里。证据支撑到哪一层就写到哪一层，没确认的细节放进「未知」。这是报告内容的约定，不是调查顺序。

### B. 交报告前的建议自审（占 48%，是主体）

- **B0** 调查已经得出结论之后、提交那份唯一且不可改的正式报告之前做这次自审。它是同一个主 Agent 做的质量检查，不是第二个 Agent，不是新工作流，也不是动作审批。

对每一条建议：

- **B1** 用「目标假设编号」把它绑到本报告里的某个假设上，只引用本次调查的证据。修复类、不变更类建议必须指向当前的领先假设；补证类建议可以指向相关的备选假设，或那个假设还没解决的证据缺口。
- **B2** 检查建议是否针对当前的目标、对象、业务路径、时间窗和这次实验。别的客户、站点、业务或历史事件的发现，不能只因为看着像就变成建议。真正有用但无关的观察放进「旁路发现」，并写明为什么超出范围。
- **B2′** 不要靠挂上当前的假设编号、或者顺手挑一个当前的证据编号，让无关建议看起来合规。修复和不变更建议引用的证据，必须真的支持或挑战目标假设；建议、预期变化、验证步骤必须出自同一个因果机制。补证建议可以拿「覆盖缺失、查询不被支持、采集失败」的回执来证明存在缺口，这些回执不必放进假设的支持或反证里，但要说明它和目标假设的关系；它们证明不了故障机制，也证明不了已经恢复。
- **B3** 写明前提和不确定性。结论是「很可能」时，只有写明前提才能给修复建议；结论是「可能」或「不确定」时，只能建议补证或不变更，不能假装修复有依据。
- **B4** 写明预期能看到的变化、具体验证步骤、风险，以及建议失败时怎么办。发布前先想想有没有更安全、更小的做法。
- **B5** 如实填写结构化的「自审」字段。报告证据不支持的检查项，不要标成通过。
- **B6** 标记自审完成之前，试着推翻每一条建议：拿掉无关的历史材料和旁路发现，问一句「只靠本次调查的证据，还能撑住同一个目标、机制和预期变化吗？」撑不住，就删掉这条建议或挪进「旁路发现」，不要靠改标签、换编号来修饰外观。
- **B7** 不要用关键词、站点名黑名单或固定动作清单来判断建议相不相关，要判断当前目标、目标假设和证据（或有记录的证据缺口）之间的关系。这样既保住 Agent 的自由，又挡住没依据的、跨案例的建议。
- **B8** 建议只是建议，永远不代表授权执行。之后若要执行，现有的动作提案、策略、审批、凭证、验证和回滚管控依然说了算。

### C. 证据来源与修复事实（占 23%）

- **C1** 对同一份抓包、同一个来源反复查询，不算相互独立的观察。说「互相印证」时，要看证据的来源、血缘、观测时间和覆盖范围，而不是工具调了几次。已有的抓包摘要可能覆盖了更早的状态，证明不了现在或某个具体位置是健康的。覆盖范围未知是证据缺口，不能当成「没有流量」。一条强观察就可以形成假设，要不要继续查由你自己决定。
- **C2** 报告交付、审批、执行、经独立验证的业务恢复，是四件不同的事实。建议从来不等于动作已经执行。描述已有提案时，要用本次调查准确的动作编号去查动作状态；查动作结果的工具会混进历史结果。只报告实际看到的内容和看到的时间。你收尾之后，审批或执行状态还可能变；审批没决定时也可以交报告。
- **C3** 报告里提到已有动作时，把动作状态里看到的动作编号、事件指纹、审批状态、执行状态、业务状态**原样抄进**「动作观察」字段。交报告时如果提示这份观察已过期，就用返回的最新事实修正描述和结论。不要声称自己看到了之后的审批或验证。报告被接收的那一刻，服务端会把动作事实冻结下来，之后的事实另行展示。

### D. 精确描述证据缺口（占 15%）

- **D1** 要分清：没查过的来源、没读完的结果页、查询失败、查询成功但结果为空、能力明确不支持或没授权。目录没翻完、工具没试过，证明不了环境里没有这个能力。写清观察到的限制，以及哪些还没核实。
- **D2** 引用原始的调查证据编号。忘了编号，可以用「列出本次结果」找到已有结果，用「重新打开结果」读回不可变的原文。目录条目和重复读取只是导航，不是新的或独立的故障证据。读不读、读什么，你自己决定。
- **D3** 把直接观察、推断和未知分开写，并写明各自的时间。业务恢复验证通过，不代表当初提出的机制每个细节都对。不确定的地方要明说，不要拿一句没依据的「能力缺失」去搪塞。

## 3. 它到底是干什么的

名字叫「报告工单」，**真正讲工单的只有 A2 一段**。它其实是四样东西打包在一起：

```
① 报告怎么写    A1 A3 D3        写作要求：因果句怎么写、观察/推断/未知分开
② 建议怎么自查  B0～B8          占一半篇幅：绑假设、不许跨案例套建议、证伪、填勾
③ 动作事实怎么写 C2 C3           交付 ≠ 审批 ≠ 执行 ≠ 业务恢复；动作状态原样抄
④ 证据怎么算数  C1 D1 D2        同源重复不算独立；缺口分五种；忘了编号怎么找回
```

打个比方：它像**飞行员起飞前的检查单**，再加上一页「报告书写规范」。

## 6. 有没有必要强制调用

### 支持强制的理由（要公平地摆出来）

- **检查单思维**：飞行员、外科医生起飞前、开刀前都过检查单，不是因为不会，是因为人会漏。
  模型在写报告前把规矩重读一遍，可能真的少犯一些错——**但我们没有数据证明这一点，待确认**
- **成本很低**：约占一次调查 1% 的输入
- **最初的起因是有针对性的**：09-01 加自审时，项目记录里点名要挡住的，是别的客户的历史线索
  （「宁德 MTU」「北京 AGV 无线遮挡」）混进本次建议（当时是否真的混进过正式报告，记录里没写，待确认）。
  09-02 又加了一条测试，专门防止「报告里说自审了、其实没打开技能」

### 反对强制的理由

1. **违背黄金提示词**：「先做 A 才能做 B」是在规定步骤，代码只该管权限、预算、安全、证据、审计
2. **时机太晚**：调查方法类的内容在 94% 处才读到，用不上
3. **勾选表不含信息**：21/21 全打「通过」，代码和考场都只能看勾，验证不了 Agent 是不是真想过
4. **没拦住常见错误**：自审完照样被打回 18 次，真正起作用的是代码的机械检查
5. **最初那个跨客户问题，现在有三道防线**：提示词第 93、126 行明令禁止；代码要求建议引用的证据必须在目标假设名下；
   证据充分性检查会把证据不足的结论降级。自审是第四道，而且是唯一一道验证不了的

### 我的判断

**强制调用没必要，但这个技能不能扔，要「拆开放对地方」：**

```
① 调查方法（C1、D1）        → 挪进系统提示词，各压成一两句，让它在查的过程中就起作用
② 判断题（B2、B6、B7）       → 留在技能里，不强制；B6「证伪每条建议」最好也在提示词里点一句
③ 写作要求（A3、C2、D3）     → 留在技能里
④ 已被代码管住的（B1、B3…）   → 代码检查一条不动；技能里的重复段落可以删，也可以先不动
⑤ 勾选表（B5 和那几个勾）     → 改成可选，代码和考场都不再拿它判对错
```

## 7. 订正：上一版推荐的「只删强制」有漏洞

```
【上一版推荐】 删掉「必须调过技能」的检查，提示词「必须」改「可以」
【漏洞】       报告格式仍然要求每条建议填 5 个勾、且必须全是「通过」
              考场判分也照样看这几个勾（80 道题全都要求写建议）
              → Agent 没自审时也得写「我自审过了，全部通过」
              → 等于制度化地要求它说假话
```

所以「去掉强制」和「处理勾选表」必须一起做，而勾选表牵涉考场判分，**属于考试标准，要你定**。

## 9. 可以接着讨论的几个点

1. **检查单思维你认不认？** 如果你认为「交报告前过一遍检查单」本身就是该有的运维纪律，丙就站得住；
   如果你认为这属于「代码替 Agent 安排步骤」，就选甲
2. **考场该不该给「自审勾」计分？** 我的看法是不该：它是 Agent 的自我声明，考场核验不了。
   这和「考场不能自造考生看不见的词表」是同一类问题——考了一样它其实量不出来的东西
3. **C1、D1 挪进系统提示词**，提示词会再长几行。你介意提示词变长吗？
4. **LG 那边也有同样一张勾选表**，这次不动 LG，只让考场不再看它。要不要下一轮一起清理？
