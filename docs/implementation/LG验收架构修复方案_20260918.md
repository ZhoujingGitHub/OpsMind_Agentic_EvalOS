## 1. LG 的 27 个节点，按 AADE 归位

**TM Forum 自治网络的闭环叫 AADE**：感知 Awareness → 分析 Analysis → 决策 Decision →
执行 Execution → 复盘效果，然后回环。

```
 ┌─ 准入 ────────────────────────────────────────────────────────┐
 │ ingest_candidate → admission_governance → hydrate_context     │
 │ → initialize_plan                                             │
 └───────────────────────────────┬───────────────────────────────┘
                                 ▼
 ┌─ 感知 Awareness ──────────────────────────────────────────────┐
 │ execute_read_tools → normalize_evidence                       │
 └───────────────────────────────┬───────────────────────────────┘
                                 ▼
 ┌─ 分析 Analysis ───────────────────────────────────────────────┐
 │ reason_and_select_tools                                       │
 │ revise_hypotheses                                             │
 │ adjudicate_hypotheses      ← 专门的「裁决假设」节点            │
 └───────────────────────────────┬───────────────────────────────┘
                                 ▼
 ┌─ 决策 Decision（两级）────────────────────────────────────────┐
 │ ① quality_gate ── 机器决策：选下一条调查路径                  │
 │      ├─ CONTINUE ─────────────► reason_and_select_tools  ↑分析 │
 │      ├─ CONTINUE + 已选工具 ──► execute_read_tools       ↑感知 │
 │      ├─ adjudicate ───────────► adjudicate_hypotheses          │
 │      ├─ PROPOSE_ACTION ───────► action_proposal                │
 │      └─ FINALIZE / 证据不足 ──► finalize_and_learn             │
 │                                                                │
 │ ② action_proposal → capture_environment_snapshot              │
 │    → autonomy_policy_decision → human_interrupt                │
 │      ── 人决策：批不批这个动作                                 │
 │      · 绑定 proposal_digest ＋ 绑定 snapshot_digest             │
 │      · approval.scope_snapshot_id 与提案不一致即拒              │
 └───────────────────────────────┬───────────────────────────────┘
                                 ▼
 ┌─ 执行 Execution（三段式票据）─────────────────────────────────┐
 │ issue_execution_ticket → claim_execution_ticket               │
 │ → execute_rollout_step                                        │
 └───────────────────────────────┬───────────────────────────────┘
                                 ▼
 ┌─ 复盘效果 Review Effects ─────────────────────────────────────┐
 │ verify_effect（实验室侧独立验证，消费侧四道守卫）             │
 │      ├─ 有效 EFFECTIVE ──────► rollout_decision                │
 │      ├─ 无效 INEFFECTIVE ────► decide_rollback_safety          │
 │      └─ 不确定 INCONCLUSIVE ─► safe_stop                       │
 │ rollback_action → verify_rollback                              │
 └───────────────────────────────┬───────────────────────────────┘
                                 ▼
 ┌─ 闭环回路（★ 环在这里闭上）───────────────────────────────────┐
 │ release_action_lease，按 post_release_route 路由：             │
 │   · recover   → resume_investigation → revise_hypotheses ─┐   │
 │   · next_step → issue_execution_ticket（多步动作）         │   │
 │   · reopen / finalize → finalize_and_learn → END           │   │
 └────────────────────────────────────────────────────────────┼───┘
                                                              │
                         回到分析环节 ─────────────────────────┘

 ┌─ 升级与熔断（ETSI ZSM 009-1 要求的 escalation）───────────────┐
 │ safe_stop   → escalate(proposal, reason)                      │
 │               ＋ status = "human_takeover"                     │
 │               ＋ escalation_reason 落账                        │
 │ open_circuit → release_action_lease                            │
 └───────────────────────────────────────────────────────────────┘
```

### 一处需要订正的初读错误

初看 `verify_effect` 的三条出边（有效→收口 / 无效→回滚 / 不确定→安全停止），
会以为**环在「复盘效果」这一步断了**。

**查了 `post_release_route` 的全部设置点，这个判断是错的**：

| 设置点 | 值 | 去向 |
|---|---|---|
| `rollout_decision`（修复有效） | `next_step` 或 **`recover`** | 还有步骤则继续，否则**回分析** |
| `decide_rollback_safety`（不许回滚） | **`recover`** | **回分析** |
| `verify_rollback`（回滚完成） | **`recover`** | **回分析** |
| `safe_stop` / `open_circuit` | `reopen` | 收口 |

**LG 的 AADE 闭环是真闭合的。**

## 2. 对照业界：LG 的骨架符合度很高

| AADE / ZSM 要求 | LG |
|---|---|
| 感知 → 分析 → 决策 → 执行 → 复盘效果 | ✅ **五个环节都有专属节点** |
| **闭环要真的闭合** | ✅ **回路是图上一条真实的边** |
| TM Forum：初期机器做除「决策」外全部，**决策留人** | ✅ 动作决策走 `human_interrupt`；机器只决定**调查路径** |
| **ETSI ZSM 009-1：闭环之间要有协调、委派、升级** | ✅ `safe_stop` 显式调用 `escalate()` 并置 `human_takeover` |
| 需要熔断 | ✅ `open_circuit` |
| plan/apply 分离（业界称最高杠杆护栏） | ✅ `proposal_digest` ＋ **`snapshot_digest`** 双绑定 |
| 执行后用不同数据路径验证 | ✅ 实验室侧重采 UE→MEC 业务请求 |
| 变更单须链接风险分析、回滚方案、**测试证据** | ⚠️ **前两项有，第三项缺**（见 L1） |
| 变更单须有回滚/退出方案（ISO 27001 8.32） | ❌ **`rollback_plan` 是可选的**（见 L2） |
| 审批深度与举证要求按风险分级（ITIL 4） | ❌ **无**（见 L3） |

## 3. 做得好的地方（保留，不要动）

| # | 做法 | 说明 |
|---|---|---|
| 1 | **闭环是显式的** | 五个 AADE 环节在图上都有节点，回路是真实的边。**AH 的循环是隐式的（下一步由模型自己想），架构上无法保证闭环——这是 LG 的结构性优势** |
| 2 | **升级是显式动作** | `escalate()` 被真的调用，`status="human_takeover"`，`escalation_reason` 落账。不是"写个字段等人看" |
| 3 | **档位是算出来的，不接受自报** | 5 档由 6 项检查计算得出。**所以 LG 天然没有 AH 的"过度自信没人管"和"一律降到底"两个问题** |
| 4 | **缺口分阻断性** | `blocking_evidence_gaps`，检查项写着「需处理**会改变该机制判断的**阻断缺口」。**这是 AH 要向 LG 学的** |
| 5 | **五档含义互不重叠** | `被反证` / `被数据阻断` / `证据不足` —— 三种"不发"的原因是分开的，可诊断 |
| 6 | **判它的规则可追溯** | `policy_version` 随判决落账 |
| 7 | **审批双绑定** | 绑 `proposal_digest` ＋ 绑 `snapshot_digest`，且校验 `scope_snapshot_id` 一致 |
| 8 | **快照是独立节点** | `capture_environment_snapshot` 是图上一个节点，不是执行路径里的一段内联代码 |
| 9 | **执行三段式票据** | 签发 → 领取 → 执行，比单段执行更可审计、更抗重复执行 |
| 10 | **影响范围声明丰富** | `responsibility_domain`、`affected_tenant_ids`、`site_id`、`network_profile`、`service_ids` |
| 11 | **独立验证消费侧四道守卫** | 独立验证者身份、`trial_id` 绑定（**防重放**）、契约版本校验、缺字段即报错；失败 `raise ConnectionError` 而非降级 |

**这十一条不在本次改动范围内，一个字不动。**

## 4. 四个洞

### L1 🔴 动作提案没有举证链接

**事实**（`contracts/actions.py:122` 的 `ActionProposal` 全部字段）：

```
  action_id / investigation_id / action_type / risk_level / status
  execution_mode / target_ids / parameters
  impact_summary / verification_plan / rollback_plan
  idempotency_key / proposal_version / proposal_digest / proposer_id
  action_catalog_version / connector_profile
  site_id / network_profile / resource_type / service_ids
  responsibility_domain / affected_tenant_ids
                       ▲
           没有 hypothesis_id，没有 evidence_ids
```

**业界标准（ISO 27001 8.32 / ITIL 变更单）要求**：

> 每一份变更请求在送到审批之前，都应当**链接到相关的风险分析、回滚方案和测试证据**。

**而 LG 这个洞比 AH 更刺眼**，因为 LG 的整个证据门就是围绕「假设—证据」建起来的：

| LG 的证据门要求（`governance/evidence.py`） | 动作提案要求 |
|---|---|
| 假设必须**具体到故障对象和因果机制** | ❌ 不要求提及任何假设 |
| 必须有**直接验证**或 **≥2 个来源相互印证** | ❌ 不要求引用任何证据 |
| 必须**处理掉未解决的反证** | ❌ 不检查 |
| 必须处理**会改变机制判断的阻断缺口** | ❌ 不检查 |

**同一个产品：判「能不能发结论」时要求假设与证据齐备；判「能不能动手改环境」时一个都不要。**

**公平起见**：业界对人工审批的**最低要求**是「审查意图、目标资源、潜在影响」——
LG 三样都有（`action_type`/`parameters`、`target_ids`、`impact_summary` + 丰富的范围字段），
**达到了最低线**。L1 属「达标但未达最佳实践」，不是「不合格」。

### L2 🟡 `rollback_plan` 是可选的 —— 这一条 LG 弱于 AH

```python
rollback_plan: str | None = Field(default=None, max_length=4000)
                  ▲ 可以是 None
```

**AH 的 `rollback_plan` 是必填项。** ISO 27001 8.32 与 ITIL 变更单均要求必须有回滚/退出方案。

**这是 LG 单方面弱于 AH 的一处。**

注意 LG 有 `capture_environment_snapshot` 和 `rollback_action`/`verify_rollback` 节点——
**回滚能力是有的**，缺的是**提案阶段必须写清回滚方案**这个契约要求。

### L3 🟡 举证要求没有按风险分级

**ITIL 4 变更使能的核心做法**：

> 按**风险和紧急度**给变更分类，据此分配**复核路径、审批深度和文档要求**。

`ActionProposal` 有 `risk_level` 字段，但**它不驱动任何举证要求的差异**。
高风险动作和低风险动作填的是同一张表。

### L4 ⚪ 命名误导（零风险，建议顺手改）

```python
lambda state: state.get("post_release_route", "reopen")   ← 默认值是 reopen
{
  "reopen":   "finalize_and_learn",     ← 叫「重新打开」，指向「收口并学习」
  "recover":  "resume_investigation",   ← 真正「重新打开」的是这个键
  "next_step":"issue_execution_ticket",
  "finalize": "finalize_and_learn",
}
```

**`"reopen"` 指向收口；真正回去继续查的键叫 `"recover"`。而默认值是 `"reopen"`。**

**不是 bug**——所有实际设置点都是对的。**但读代码的人会反着理解**（本次审查第一遍就读反了，
一度误判"闭环断了"）。既然 `"finalize"` 键已经存在且指向同一个节点，
**`"reopen"` 这个键可以直接删掉或改名**。

## 5. 一个 AADE 视角的观察（是取舍，不是洞）

**`quality_gate` 同时承担两个职责：判定证据够不够 ＋ 决定下一个节点。**

ETSI ZSM 009-1 把「治理」（闭环的创建、执行、生命周期管理、行为操控）
与「决策」分开描述。合在一个节点里意味着——**改判据就会改流程。**

**这个耦合已经被踩过了：**

- F1/F2 本质是「该发的结论没发」这个**发布**问题，但修的时候**不得不动路由节点**
- F4b 是引擎侧的路由改动，**两次真实运行一次都没触发**——真正起作用的是 F4a 那句提示词

**这是 LG「图决定一切」这一产品主张的必然代价，不是缺陷。**
但必须写下来作为纪律：**LG 的任何判据改动，都要当成流程改动来做回归。**

## 6. 修复方案

### F-L1 🔴 提案补举证链接（修 L1）

```
   ActionProposal 新增必填字段
   ┌──────────────────────────────────────────────────────┐
   │  target_hypothesis_id      ← 针对哪个假设             │
   │                              必须是当前受支撑的假设   │
   │  supporting_evidence_ids   ← 基于哪几条证据           │
   │                              必须属于该假设，且实质有效│
   │  alternatives_considered   ← 已排除哪些替代机制       │
   └──────────────────────────────────────────────────────┘
   · 三个字段进 proposal_digest 的计算范围（否则审批绑定不覆盖它们）
   · 在 action_proposal 节点做校验，不通过则走 action_draft_route 的拒绝分支
```

**判据直接复用证据门现成的那套**，不用新发明：

| 复用哪一条 | 来自 |
|---|---|
| 假设必须具体到**故障对象 + 因果机制** | `root_cause_supported` 的 `causal_component` / `causal_mechanism` 检查 |
| 证据必须**实质有效** | `substantive_by_id` 的判定 |
| 不得存在**未解决的反证** | `contradicting_evidence_ids` 的校验 |

**这是把 LG 已经用于"发结论"的判据，用到更该用的"动手改环境"那条路上。**

### F-L2 🟡 `rollback_plan` 改必填（修 L2）

```python
rollback_plan: str = Field(min_length=1, max_length=4000)   # 去掉 | None
```

**风险提示**：这是**收紧**契约，会拒掉不带回滚方案的提案。
**必须跑一次真实链路回归**，确认现有行为路径都能通过。

**若发现某类动作确实不需要回滚**（例如纯读取型或幂等复位），
**不要退回可选**，而是要求显式声明：`rollback_plan: "不适用：<理由>"`。
**"不需要"和"没写"必须能分开。**

### F-L3 🟡 举证要求按 `risk_level` 分级（修 L3）

| 风险 | 审批 | 举证要求 |
|---|---|---|
| **低** | 冻结授权包裁决 | 现有字段 |
| **中** | 人工审批 | **＋ F-L1 的举证链接** |
| **高** | 人工审批 | **＋ 举证链接 ＋ 已排除的替代机制**<br>**＋ 证据门档位须达 `probable` 以上** |

**最后一格的理由**：业界原话「审批不应仅依赖模型的置信度」——所以**不能只看档位**；
但反过来，**高风险动作配一个 `insufficient_evidence` / `contradicted` 的判定应当直接拦住**。
**LG 有这个档位（算出来的，比自报可信），却没用在这里。**

### F-L4 ⚪ 删掉或改名 `"reopen"` 键（修 L4）

`"finalize"` 键已存在且指向同一节点，`"reopen"` 可直接删除，
把三处设置 `"reopen"` 的地方改成 `"finalize"`。**零行为变化，纯可读性。**

## 8. 与 AH 的协同：格式共享，代码不共享

**L1 与 AH 的 F1 是同一个洞，建议同一轮做**，否则会出现两边契约不一致的窗口期。

```
        共享的是【格式】——提案必须带：
        目标假设 ＋ 支撑证据 ＋ 已排除的替代机制
                        │
        ┌───────────────┴───────────────┐
        ▼                               ▼
   AH 自己实现                     LG 自己实现
   改 tools.py 的 propose_action    改 contracts/actions.py 的
   入参 ＋ action_proposals 表      ActionProposal ＋ action_proposal 节点
        │                               │
        └── 代码互不依赖，改一边不影响另一边 ──┘
```

**这是既定原则：共享格式，不共享代码。** 两个产品独立发布、独立仓，
共享一份判定库会制造跨仓锁步升级的永久成本。

## 9. 实施顺序与验收标准

| 序 | 做什么 | 验收标准 |
|---|---|---|
| **1** | **F-L4**（删 `"reopen"` 键） | 单测全过；**零行为变化**，图的可达性不变 |
| **2** | **F-L1**（举证链接） | 现有链路②④ 若重跑，提案必须能通过（受支撑假设与证据本来就存在）；**缺任一新字段则提案被拒**；`proposal_digest` 覆盖新字段 |
| **3** | **F-L2**（回滚必填） | 真实链路回归通过；构造一个无回滚方案的提案，必须被拒 |
| **4** | **F-L3**（风险分级） | 构造「高风险动作 + `insufficient_evidence` 档位」，必须被拦住 |

**顺序理由**：F-L4 零风险先清掉可读性债；F-L1 是核心且与 AH 同步；
F-L2 是收紧契约，需要真实回归；F-L3 依赖 F-L1 的字段。

**§5 的纪律适用于全部四条：LG 的任何判据改动都要当流程改动做回归**——
F1/F2/F4 那一轮已经证明，判定与路由在这个架构里是耦合的。

## 10. 边界（不越的线）

- **不动 AH，不动 EvalOS 考场判分**
- **不放宽任何安全控制**：F-L1 / F-L2 / F-L3 **全部是收紧**；F-L4 零行为变化
- **不改证据门的 6 项检查与 5 档判定逻辑**（本方案一个字不碰 `governance/evidence.py` 的判据）
- **不改独立验证的消费侧四道守卫**
- **§3 那十一条做得好的地方一个字不动**
- 已封存的证据与历史提案**不回填、不重算**
