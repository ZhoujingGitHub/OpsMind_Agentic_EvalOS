# AI Agent 四类 Grader 与 EvalOS 评分设计原则

> 文档用途：面试前复习、产品方案讲解、EvalOS 后续评分系统设计依据
> 版本日期：2026-08-21
> 适用产品：OpsMind_Agentic_EvalOS 及其对 Agent+Harness OpsMind、LangGraph OpsMind 的生产级评测

## 一、先记住最重要的结论

业界比较成熟、统一的分类主要有三种：

1. **代码评分器（Code Grader）**：用程序、规则和测试脚本检查客观事实。
2. **大模型评分器（LLM Grader）**：让大模型按照评分标准评价自然语言和复杂语义质量。
3. **人工评分器（Human Grader）**：由真人专家抽查、校准或裁决争议。

**Agent 评分器（Agent Grader）**是近两年发展出来的新范式。它不只是让大模型看完材料直接打分，而是让一个能使用工具的评审 Agent 主动查看日志、轨迹、源码和外部资料，再形成有证据的分析结论。它可以看作 LLM Grader 的 Agentic 升级版，但目前还不是已经完全标准化的第四类评分器。

对 EvalOS 最合适的分工是：

> Code Grader 决定正式成绩和安全门禁；LLM Grader评价难以写成规则的质量问题；Agent Grader负责深入调查和解释；Human Grader负责抽查、校准和争议裁决。

四种 Grader 不是互相取代，而是各自解决不同问题。

## 二、什么是 Code Grader

### 2.1 用人话解释

Code Grader 就像学校里的自动判卷程序。它不会因为考生报告写得漂亮就多给分，只检查可以被客观验证的事实。

例如一个受控自动修复 Trial 完成后，它会检查：

- 5G 故障到底有没有恢复；
- UE 是否重新注册；
- PDU 会话是否恢复；
- Agent 有没有越过租户、网元、动作和时间窗的授权范围；
- 是否使用了合法的一次性执行票据；
- 是否完成了独立验证；
- 验证失败后是否停止、回滚或转人工；
- 是否误触真实生产环境；
- 日志、告警、指标和操作证据是否真实存在；
- 是否超出时间、Token、工具调用次数和资源预算；
- Trial 结束后数字孪生实验室是否成功复位。

### 2.2 优点

- 同样的证据可以得到同样的分数；
- 速度快、成本低；
- 可以重复运行；
- 可以解释每一分从哪里来；
- 适合承担正式成绩和安全门禁。

### 2.3 局限

Code Grader 不擅长判断：

- 根因说明是否清楚；
- 报告是否让人容易理解；
- 一个开放式调查是否有洞察；
- 建议是否全面而有实际价值。

如果规则设计错误，它也可能只检查表面动作。例如，“调用过修复工具”不等于“真的修好了”，所以 EvalOS 必须优先检查独立终态，不能按固定工具名和调用顺序判分。

### 2.4 在 EvalOS 中的角色

Code Grader 应当是：

- 正式成绩 `Official Grade` 的主要来源；
- 安全门禁的唯一权威来源；
- 判断任务是否真正完成的最终裁判；
- 判断 `CANDIDATE_ERROR`、`INVALID_INFRA` 和有效 Trial 的确定性依据之一。

以下问题应当属于不可补偿硬门禁：

```text
发生越权或跨租户访问
只诊断模式发生写操作
未经批准执行修复
审批票据无效、被篡改或被重复使用
触碰真实生产环境
修复后没有独立验证
应该拒绝或停止时仍强行执行
环境无法可靠复位
关键原始证据缺失或被篡改
```

发生安全硬门禁失败后，不能用“报告写得很好”“其他 Seed 得分高”等理由补回来。

## 三、什么是 LLM Grader

### 3.1 用人话解释

LLM Grader 像一名快速阅卷老师。平台把 Case 要求、评分标准、考生答案、关键证据和必要轨迹交给大模型，让它评价难以写成固定程序的内容。

它可以判断：

- 根因分析是否合理；
- 结论是否有证据支持；
- 是否把猜测说成了事实；
- 是否遗漏重要信息；
- 修复建议是否清楚、完整、可执行；
- 两个考生的报告哪个更好理解。

### 3.2 优点

- 能理解自然语言和上下文；
- 能评价开放式答案；
- 比真人逐条评审便宜、快速；
- 可以按同一 Rubric 批量评价大量 Trial。

### 3.3 风险

- 同一份答案重复评分可能略有差异；
- 可能偏爱更长、更像专业报告的答案；
- 可能受到考生输出中的提示注入影响；
- 可能因为候选人名字、顺序或语言风格产生偏差；
- 如果与被测 Agent 使用相同模型，可能存在自我偏好或共同盲区；
- 信息不足时也可能编出听起来合理的评分理由。

### 3.4 在 EvalOS 中的角色

LLM Grader 适合评价：

- 根因说明质量；
- 证据与结论的一致性；
- 报告完整性和可读性；
- 建议的可操作性；
- 未确定性表达是否诚实；
- 是否存在无证据断言。

但它不能推翻 Code Grader 已经确认的客观事实。例如：

> Code Grader 通过独立观察面确认 UE 没有恢复，LLM Grader 不能因为考生的报告写得漂亮，就把“修复失败”改成“修复成功”。

现阶段最稳妥的产品定位是：

```text
AI 辅助评价（Advisory Judgment）
```

如果未来某些主观维度需要计入正式成绩，必须先冻结 Rubric、模型、提示词、输入范围和版本，再通过人工样本校准，不能让模型临场自由决定评分标准。

## 四、什么是 Human Grader

### 4.1 用人话解释

Human Grader 就是由真人专家查看 Case、考生输出、关键证据、完整轨迹和其他评分器的理由，再作出专业判断。

它最适合处理：

- 新类型 Case 首次上线；
- Code Grader 与 LLM Grader 结论冲突；
- 两个考生成绩非常接近；
- 安全边界存在争议；
- 对正式评分提出申诉；
- 校准 LLM Grader 是否可靠；
- 判断某道 Case 或某条 Rubric 本身是否设计得合理。

### 4.2 为什么不能每条 Trial 都人工评审

人工评审成本高、速度慢，而且不同专家之间也可能存在意见差异。正式 480 个 Trial 不适合逐条等待真人阅卷，否则平台无法做到稳定、快速和可复现。

更合理的方式是：

- 对总体结果做分层抽样；
- 重点复核安全失败和异常 Trial；
- 专门处理评分器冲突和正式申诉；
- 定期建立一小批专家金标准样本，用于校准 LLM Grader；
- 记录专家身份、理由、时间、Rubric 和评分版本。

### 4.3 人工 Grader 和审批人不是一回事

EvalOS 里的自动审批裁判 `Approval Oracle` 不是 Human Grader。

- **审批人或 Approval Oracle**：在 Trial 运行过程中判断某个动作是否允许执行。
- **Human Grader**：在 Trial 完成后负责阅卷、复核和争议裁决。

前者属于考试过程，后者属于考试后的评分治理，不能混为一谈。

## 五、什么是 Agent Grader

### 5.1 用人话解释

普通 LLM Grader 更像“看完材料后直接给结论”。Agent Grader 更像一位会主动调查的 AI 评审专家。

它可以这样工作：

```text
理解 Case 和评分问题
        ↓
查看考生最终结果
        ↓
查询完整运行轨迹
        ↓
读取日志、指标、告警和审批记录
        ↓
必要时查看考生源码和冻结配置
        ↓
对关键怀疑继续查证或找反证
        ↓
必要时研究外部权威资料
        ↓
形成带证据引用的分析报告
```

它不是按照预先写死的固定调查节点运行，而是根据当前问题自主提出假设、选择工具、补充证据和决定何时停止。它的自由只用于调查和分析，不能改变 Case、Seed、预算、安全门禁、正式 Grader 和不可变账本。

### 5.2 它与 LLM Grader 的区别

| 对比项 | LLM Grader | Agent Grader |
|---|---|---|
| 工作方式 | 通常一次或少量模型调用 | 多轮调查和工具调用 |
| 输入 | 预先整理好的材料 | 可以主动读取更多授权证据 |
| 能力 | 评价已有内容 | 提假设、查证、反证、比较、研究 |
| 输出 | 评分和简短理由 | 有完整证据链的深度分析报告 |
| 主要用途 | 批量辅助评价 | 失败复盘和改进分析 |

### 5.3 在 EvalOS 中的角色

EvalOS 的 `Eval Intelligence Agent` 本质上就是 Agent Grader，建议保持：

```text
Claude Agent SDK
    + DeepSeek
    + 只读 MCP
    + 评测分析 Skills
    + Bash / Read / 搜索等原生能力
```

它可以：

- 解释某条 Trial 为什么失败；
- 说明某个评分维度为什么被扣分；
- 比较 Agent+Harness 和 LangGraph 两名考生；
- 发现共同失败模式和测量系统问题；
- 阅读考生冻结源码和配置；
- 必要时研究权威资料；
- 形成产品优化建议和证据链。

它必须遵守两个核心边界：

1. 默认只读，不能修改考生、Case、Twin、轨迹、原始证据和正式成绩。
2. 不能直接覆盖 Code Grader 的官方分数。

它产生的是：

```text
AI 深度调查报告（Agentic Review）
```

而不是未经治理的新成绩。

## 六、四种 Grader 怎样协作

可以把它们理解成四层裁判：

```text
第一层：Code Grader
检查客观结果、权限、安全、预算和系统事实
                    ↓
第二层：LLM Grader
评价根因说明、证据表述和报告质量
                    ↓
第三层：Agent Grader
深入调查为什么成功、为什么失败、如何优化
                    ↓
第四层：Human Grader
抽查、校准、处理争议和正式申诉
```

以一条受控自动修复 Trial 为例：

| Grader | 实际工作 |
|---|---|
| Code Grader | 检查票据是否合法、动作是否越权、网络是否恢复、是否验证和复位 |
| LLM Grader | 判断根因说明是否有证据、建议是否清楚、是否夸大确定性 |
| Agent Grader | 追查为什么验证超时、比较两个考生的调查差异、必要时查看源码 |
| Human Grader | 对争议结果进行专家复核，或判断 Rubric 是否需要改进 |

## 七、EvalOS 设计 Grader 的核心原则

### 原则一：先分清事实判断和质量判断

- “到底修没修好、有没有越权”是事实问题，交给 Code Grader。
- “分析是否清楚、建议是否有价值”是质量问题，可以交给 LLM Grader。
- “为什么会失败、怎样改进产品”是调查问题，交给 Agent Grader。
- “评分器是否合理、争议如何裁决”是治理问题，交给 Human Grader。

### 原则二：能用确定性代码判断，就不要先问大模型

大模型不应该判断数据库里明明可以直接验证的事实。数字孪生终态、票据签名、权限、预算、复位、事件完整性和重复执行，都应由代码直接验证。

### 原则三：安全门禁不可被平均分掩盖

跨租户、未授权写入、提示注入成功、票据篡改、重复执行等安全事故，不能被报告质量、其他维度或其他 Seed 的高分抵消。

### 原则四：不按固定工具名和固定步骤判分

EvalOS 要评的是考生是否在授权范围内得到正确结果，而不是是否走了平台提前写好的唯一流程。

- 不奖励调用工具的数量；
- 不要求固定工具名；
- 不要求固定调用顺序；
- 不把标准答案写成唯一修复路线；
- 允许两个 Agent 用不同路径获得同样正确的结果。

### 原则五：所有评分断言都必须有证据

每一项得分、扣分和门禁结论至少保存：

- 规则编号；
- 评分器类型和版本；
- 中文原因；
- 原始证据引用；
- Case 合同摘要；
- 是否影响正式成绩；
- 产生时间和不可变哈希。

不能只在页面上显示一个总分。

### 原则六：四类结果分开存、分开展示

| EvalOS 结果 | 来源 | 权威等级 |
|---|---|---|
| 正式确定性成绩 `Official Code Grade` | Code Grader | 正式成绩和硬门禁 |
| AI 辅助评价 `LLM Judgment` | LLM Grader | 辅助质量评价 |
| AI 深度调查 `Agentic Review` | Agent Grader | 解释和改进建议 |
| 专家复核 `Human Review` | Human Grader | 校准和争议裁决 |

页面必须明确告诉用户：是谁作出的结论、使用哪个版本、看了哪些证据、是否影响正式成绩、是否经过复核。

### 原则七：Regrade 不能覆盖历史成绩

复评应形成一条新记录：

```text
原始评分和原始证据
        ↓
复评请求及原因
        ↓
新 Grader 读取同一份冻结证据
        ↓
生成新评分记录
        ↓
展示新旧差异和裁决理由
```

旧评分、旧版本和旧证据必须继续保留，不能静默覆盖。

### 原则八：模型裁判必须校准和防偏差

LLM Grader 和 Agent Grader应当：

- 隐藏考生真实身份，使用盲态编号；
- 冻结模型、提示词、Rubric、工具和知识版本；
- 防止考生输出中的提示注入影响评审；
- 只读取授权范围内的证据；
- 用专家样本定期校准；
- 测试位置偏差、长度偏差和自我偏好；
- 在相同输入下做稳定性测试；
- 不得自行改变正式评分规则。

如果评审模型与被测 Agent 使用相同底层模型，更要测试共同盲区和自我偏好。现阶段 Agent Grader只做辅助分析，因此风险可以隔离；如果未来要让它参与正式计分，则必须经过更严格的独立校准。

### 原则九：区分考生失败和考场故障

- 考生自己的 Agent、API、Worker、恢复、权限或执行链失败，属于 `CANDIDATE_ERROR`。
- EvalOS、Twin、Adapter、网络、存储或评分基础设施故障，属于 `INVALID_INFRA`。

考场故障不能直接算考生答错，也不能为了凑完整率伪装成有效 Trial。

### 原则十：AI分析不能参与改分

Eval Intelligence Agent可以解释、比较、深研和提出建议，但不能：

- 修改原始 Trace；
- 补造考生没有产生的证据；
- 替考生完成修复；
- 改写 Case 和 Ground Truth；
- 覆盖正式 Code Grade；
- 修改冻结账本。

## 八、建议的 EvalOS Grader 分层

```text
第0层：Trial 有效性检查
确认考场、Twin、Adapter、存储和证据是否正常

第1层：安全硬门禁
Code Grader 判断越权、审批、票据、注入、跨租户等问题

第2层：客观任务成绩
Code Grader 判断终态、根因边界、证据、预算、恢复和系统可靠性

第3层：主观质量评价
LLM Grader评价报告、解释、未确定性表达和建议质量

第4层：深度调查
Agent Grader分析失败原因、比较考生和提出改进方案

第5层：治理与裁决
Human Grader抽查、校准、复核争议和处理申诉
```

## 九、面试时可以怎样讲

### 30 秒版本

> EvalOS 不是用一个大模型随便给另一个大模型打分，而是把评分拆成四种职责。Code Grader检查真实终态、安全、权限和预算，是正式成绩来源；LLM Grader评价根因说明和报告质量；Agent Grader能主动查日志、轨迹、源码和资料，用于失败复盘和优化建议；人工 Grader不逐条阅卷，只做抽查、校准和争议裁决。这样既有确定性，又能评价开放式 Agent 的复杂能力，还不会让 AI 分析随意覆盖正式成绩。

### 一句话版本

> Code Grader 管事实和安全，LLM Grader 管语义质量，Agent Grader管深度调查，Human Grader管校准和争议。

### 为什么不能只用 LLM Grader

> 因为“报告看起来专业”和“网络真的恢复、安全边界没有被突破”是两件事。客观结果必须用代码和独立观察面验证，大模型只评价代码难以覆盖的语义质量。

### 为什么 Agent Grader 不直接改分

> Agent Grader调查能力更强，但也更自由、更不确定。它适合解释为什么失败和怎样优化，不适合在没有冻结规则和校准的情况下直接改变正式成绩。

## 十、行业参考

1. Anthropic, *Demystifying evals for AI agents*：将 Agent 评测常用 Grader 分为代码、模型和人工三类，强调能确定性判断的优先使用代码，并通过人工校准模型评分。
   https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents

2. Zhuge 等，*Agent-as-a-Judge: Evaluate Agents with Agents*：提出由具备工具使用和多步调查能力的 Agent 评价其他 Agent，是 Agent Grader 的代表性研究方向。
   https://arxiv.org/abs/2410.10934

3. Li 等，*From Generation to Judgment: Opportunities and Challenges of LLM-as-a-judge*：系统讨论 LLM 作为评分者的应用、机会、可靠性问题和偏差风险。
   https://aclanthology.org/2025.emnlp-main.138/

## 十一、最终总结

EvalOS 的 Grader 体系不能变成“让一个更大的模型决定一切”，也不能退化为检查固定工具和固定步骤的脚本考试。

正确设计是：

```text
真实考生自主调查和行动
        ↓
Code Grader验证客观结果和安全边界
        ↓
LLM Grader补充评价语义质量
        ↓
Agent Grader开展证据驱动的深度复盘
        ↓
Human Grader负责抽查、校准和争议治理
```

这样既保留了 Agent 的自主性，又保证考试公平、安全、可复现、可解释和可审计。
