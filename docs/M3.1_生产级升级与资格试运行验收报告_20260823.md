## 一、先说结论

本轮已经完成 EvalOS M3.1 的代码升级、全量自动测试、云上原子部署、真实外部考生接入和 16 条不计分资格 Trial。

当前结论分成两部分：

1. **EvalOS 平台升级通过技术验收。** 两名真实考生均通过外部身份与版本冻结检查；每条 Trial 都有独立环境、不可变 Attempt 记录、轨迹哈希、失败隔离、复位结果和确定性 Code Grader。16 条资格 Trial 的环境复位与清洁检查全部成功，没有把上一题的故障带到下一题。
2. **两名考生均未通过资格门禁。** Agent+Harness 考生 8 条全部运行失败；LangGraph 考生 8 条均能结束运行，但没有一条达到通过条件。因此 **24～48 条容量 Trial 不得启动，480 条正式 Trial 继续禁止**。

这不是平台“跑崩了”，而是平台正确地把考生当前问题暴露出来，并在失败后完成隔离、等待、复位和审计。

## 二、本轮升级解决了什么问题

### 2.1 不再在 EvalOS 内部创建“考生分身”

EvalOS 现在只通过冻结的外部评测合同调用两个真实产品：

- `agent-harness-v2`：Claude Agent SDK + Harness 架构的 OpsMind；
- `langgraph-v1`：LangGraph 架构的 OpsMind。

EvalOS 不复制两套考生的 Agent、MCP、Skill 或故障处理逻辑，也不替考生决定调查路径。两套考生继续使用自己的大脑和内部工具完成同一道题，EvalOS 只负责出题、隔离考场、保留证据和评分。

本轮没有修改两个考生仓库的任何代码。

### 2.2 外部考生失败后不会污染下一条 Trial

旧问题是：外部考生超时或报错后，如果考生后台还在运行，EvalOS 过早复位并开始下一题，可能造成两条 Trial 串场。

现在的处理是：

1. 外部考生超时或异常；
2. EvalOS 请求取消并把本条 Trial 放入隔离；
3. 等待考生后台真正进入终态；
4. 保存失败现场和审计证据；
5. 复位数字孪生环境并检查是否干净；
6. 只有隔离已经解除且复位成功，才允许下一条 Trial 开始；
7. 如果考生一直不结束或环境无法复位，立即停止队列，不冒险继续跑。

### 2.3 失败现场丢失也不能阻止环境复位

失败后的“保存现场”和“复位环境”已经解耦。即使现场快照保存失败，EvalOS 仍会继续复位环境，并分别记录快照错误、复位结果、环境是否干净、是否需要隔离以及隔离是否解除。

### 2.4 每次尝试都有不可篡改的成绩底稿

新增 `trial_attempt_results` 不可变审计记录。每一次 Trial 尝试都会留下 Attempt 编号、状态、错误原因、用量和预算、轨迹哈希、结果哈希以及快照、隔离和复位结果。

SQLite 通过禁止更新和删除的触发器保证这些记录只能追加，不能事后覆盖。

### 2.5 Grader 升级到 5.1

Grader 5.1 解决了真实外部考生证据编号与 EvalOS 标准证据编号不一致的问题。

人话解释：考生可能把一条真实日志保存成自己的编号，EvalOS 不再要求这个编号必须长得和标准答案一样，而是检查这条被保存的真实证据内部究竟指向哪份日志、告警或指标。只要证据真实、完整、能支持结论，就能正确参与评分。

评分仍然坚持：

- 看最终任务效果、真实证据、根因质量、安全边界、轨迹质量和资源成本；
- 不因为考生使用某个固定工具名而加分；
- 不要求考生按照预先写死的工具顺序做题；
- 安全门禁和 L2 环境任务成功属于不可用其他分数补偿的硬门禁；
- AI 分析只能解释成绩和给出改进建议，不能修改 Code Grader 正式结果。

## 七、为什么不能继续跑容量 Trial

容量 Trial 是在资格通过后验证并发、队列、数据库锁、模型限流、环境复位和中断恢复。当前两个考生都未通过资格门禁，直接跑 24～48 条只会把已知问题放大并浪费资源，无法得出可信容量结论。

正确顺序是：

1. 保留本次 16 条 Trial 的全部原始证据；
2. Agent+Harness 团队修复超时、终态和外部评测接口可靠性；
3. LangGraph 团队根据 Grader 5.1 明细提升证据、根因、闭环和安全能力；
4. 冻结新版本后重新跑 12～20 条资格 Trial；
5. 两名考生都通过后，再运行 24～48 条不计分容量 Trial；
6. 容量门禁通过后，再共同评审 480 条正式 Trial 方案。
