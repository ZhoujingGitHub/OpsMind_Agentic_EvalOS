## 0. 已确认的产品决策：旧外围允许彻底 Breaking Change

产品经理已于 2026-08-31 明确确认：

- 本文开发期 MVP 架构方向合理；
- 如果旧外围阻碍三条链路稳定跑通，允许 Breaking Change；
- 不接受为了兼容旧外围而长期保留技术债。
- 两套 OpsMind 必须获得充分的 Token 和调查时间；正常资源差异不作为成绩或排名依据。

本项目对“不要留技术债”的执行口径是：

1. 新路径通过验证后，旧入口、旧服务、旧定时器、旧状态文件、旧凭据和旧配置必须从活动环境删除；
2. 不保留永久双读、双写、双协议、自动回退或“先放着以后再删”的兼容分支；
3. 一次性转换脚本只能在切换时使用，完成后退出活动运行路径；
4. Git 历史和历史 HANDOFF 继续保留作审计，不等于继续支持旧架构；
5. 旧镜像只允许在切换验证期间作为紧急回滚保险；三条链路验收通过后，活动回滚版本也必须属于新外围架构，旧架构镜像不得继续作为日常回滚入口；
6. 删除旧外围前必须先确认精确目标和回滚条件，不能用“清技术债”为理由误删数据库、证据、Ledger、用户未提交文件或任何核心能力；
7. 如果某项旧组件暂时不能删除，必须停止收口并向产品经理说明具体原因、影响和最晚删除条件，不能悄悄留 TODO。

外围 Breaking Change 的对象仍仅限外围。本次新增的“修复建议质量闭环”是产品经理在发现真实缺口后提出的窄范围产品输出补强：允许修改建议形成、建议自审、报告合同和 EvalOS 评分，但不允许借机改造两套 OpsMind 的调查核心、增加第二调查 Agent、增加固定故障流程或扩大自动执行权限。四套系统的核心保护范围仍以本文第2节为最高红线。

## 1. 一句话目标

不建设最终商用高并发平台，不重做四套系统；只修它们之间最少的外围连接和运行问题，尽快让下面三条真实链路依次跑通：

1. LangGraph OpsMind + 真实5G实验室；
2. Agent+Harness OpsMind + 真实5G实验室；
3. EvalOS + 真实5G实验室，依次评测 LangGraph OpsMind 和 Agent+Harness OpsMind。

这里的“依次”非常重要：当前只有一个真实物理实验环境，同一时间只允许一条链路使用。开发期不做并发 Trial、多槽位调度、多机高可用或自动扩容。

三条链路跑通的含义不是“接口返回正常”，而是各自完成一次真实端到端过程：准备实验环境、产品自主调查、获取真实证据、形成真实报告或评测结果、结束任务、复位实验环境并证明环境干净。

新增补充标准：只要题目明确要求修复建议，产品报告还必须说明“建议做什么、依据什么、有哪些前提和不确定性、如何验证、失败时怎样安全停止或回退”，并留下产品自身的建议自审结果。直连模式不经过 EvalOS，因此两套 OpsMind 自己必须完成这项交付；EvalOS 只在评测模式下独立评价它，不能替产品补写建议。

## 2. 绝对不能简化或改动的核心

开发期 MVP 只适用于外围。下面四套系统的核心都按真实商用架构保留。

### 2.1 LangGraph OpsMind

必须原样保留：

- 现有调查 Graph 和 State；
- Flash/Pro 双模型分工；
- Agent 自主判断和 MCP 工具调用；
- Evidence Gate；
- Checkpoint、Interrupt 和恢复；
- Knowledge、报告、审批和动作安全；
- 现有业务数据库语义。

外围修复不得改变它如何调查、如何取证、如何决策、如何恢复和如何审批动作。

### 2.2 Agent+Harness OpsMind

必须原样保留：

- 官方 Claude Agent SDK；
- 有状态 ClaudeSDKClient；
- DeepSeek V4 Flash Thinking；
- 单 Agent 自主调查；
- MCP、Skills、ToolSearch、SDK 原生工具和 Bash 安全边界；
- Agent 自主提出假设、选择工具、调整路径和决定停止；
- Harness、Hook、Evidence Gate、报告交付和动作安全。

外围修复不得增加第二个调查 Agent，不得把调查改成固定流程，也不得用模拟结果冒充真实模型调查。

### 2.3 EvalOS

必须原样保留：

- 真实 Trial 独立命名空间和隔离；
- Case、Seed、资源记账、高位安全熔断和盲身份；
- 真实5G Twin 的准备、租约、快照、复位和清洁验证；
- 完整、只追加的调查 Trace 和证据；
- 不可变 Ledger；
- 确定性 Code Grader，继续作为唯一官方成绩来源；
- Outcome、Evidence、Trajectory 三路 AI Judge；
- AI 调查员 / Eval Intelligence Agent；
- 可选人工专家复核和 Judge 校准；
- 自动审批裁判、重试规则和正式评测公平性。

必须明确：EvalOS 的 AI 评测能力没有被删除或降级。AI Judge 和 AI 调查员负责评价、解释和发现异常；它们不能覆盖确定性 Code Grader 的官方分数。两类能力同时保留，各自承担原有职责。

三路 AI Judge 和 AI 调查员是否在某一个 Trial 中实际运行，继续服从 EvalOS 已冻结的评测配置和按需触发规则。外围改造不能擅自把可选能力改成强制成绩，也不能因为某次没有触发就宣称能力已经删除。验收时必须同时证明：该运行的 AI 评测按配置运行并留下记录；按需能力没有运行时，原因和配置可以核对。

EvalOS 的生产模型执行仍遵守项目根目录 AGENTS.md：使用 Claude Agent SDK，通过 DeepSeek 的 Anthropic 兼容端点调用 DeepSeek V4 Flash；模型可以选择调查思路、工具和停止时间，但不能自行篡改 Seed、资源记账与安全熔断、隔离、安全门禁、盲身份、评分器和账本内容。

### 2.4 真实5G实验室

必须原样保留：

- Open5GS、UERANSIM 和真实协议交互；
- 真实故障注入、抓包、指标、日志和证据；
- 产品各自已有的 MCP 和动作安全；
- 实验准备、快照、复位和清洁验证；
- 单物理实验环境、串行使用的真实约束。

零模型冒烟、模拟器和 Replay 只能用于提前发现外围错误，不能作为上述三条真实链路跑通的证明。

### 2.5 开放资源：不拿 Token、时长和调用量限制 Agent

老师意见对应的产品原则是：

> 不要因为担心 Agent 变慢、变贵，就先把它限制到无法正常调查。架构合理时，2分钟、5分钟或15分钟完成都可能正常；应该给它足够的 Token 和时间空间。

在 EvalOS 中必须按以下口径执行：

- 不规定“正常 Agent 必须在多少 Token、多少工具调用、多少模型调用、多少钱或多少分钟内完成”；
- 2–15分钟只是正常任务可能出现的时间范围示例，不是15分钟硬截止线；超过15分钟也不能自动判低分；
- LangGraph 和 Agent+Harness 架构不同，不要求两者使用相同 Token、时间、调用次数或费用；
- 每个产品获得自己公开声明的最大可用资源，EvalOS 不得为了表面公平而静默压缩；
- Token、耗时、模型调用、工具调用、费用和存储用量继续完整记录，便于成本核算和事后优化；
- 上述资源数据不进入确定性 Code Grader，不影响正式成绩和排名；
- 效率分析只能写成“事实和优化建议”，不能反过来规定固定调查步骤、固定轮数或固定工具顺序；
- Agent 仍然自主决定调查路径和停止时间。

“不限制正常调查”不等于允许程序无限失控。EvalOS 仍必须保留明显高于正常任务需要的安全熔断，例如：

- 长期没有任何可观察进展，疑似卡死或无限循环；
- 费用、输出或存储持续无界增长；
- Trial 租约丢失、隔离失效或已结束后仍继续请求；
- 触碰生产写入、秘密、隐藏 Case 或另一考生数据；
- 无法归档、复位或释放真实5G实验环境。

安全熔断类似空气开关，只在系统可能失控时断开，不是日常业务上限。触发熔断时必须记录真实原因，不能自动解释成“Agent 能力差”，更不能仅因 Token 多或耗时长扣分。

这一原则同时适用于资格验证 Trial 和正式计分 Trial，并继续遵守 EvalOS 已有的 Manifest 8.0 开放资源合同。

### 2.6 新增产品输出质量红线：建议可以开放，执行必须受控

本节是本次增补方案的核心。它解决的是“产品已经找到根因，却没有建议，或者建议看起来完整但没有经过认真自审”的真实缺口，不是新建一套外围监督平台。

#### 统一原则

- 两套 OpsMind 仍由自己的原有 Agent 自主形成建议；不得由 EvalOS、外围脚本或固定模板替它补写答案；
- “修复建议”不受固定动作目录限制。Agent 可以自由提出继续调查、人工检查、配置修改、代码修改、流程改进、监控补强或暂不修复等任何有证据的建议；
- 只有当 Agent 要求系统真正改变外部状态时，才必须使用产品已经登记、可校验、可审批、可验证和可回滚的动作目录；动作目录是机器执行安全边界，不是 Agent 的思考边界；
- 只要题目要求修复建议，最终“建议交付”就绝不能是空字段、空列表或只写一句“转人工”；无论根因置信度如何，都必须至少交付一条对用户有用、可执行验证的建议；
- 根因为 `confirmed` 时，必须给出至少一条有证据的修复建议；如果当前没有安全动作，建议本身必须明确写成“暂不执行变更”，并说明原因、人工处理方向和重新判断的条件；
- 根因为 `probable` 时，必须给出“满足哪些前提后再做什么”的有条件修复建议，不得把尚未查清的判断包装成确定修复；
- 根因为 `possible` 或 `inconclusive` 时，仍必须输出建议，但允许建议内容是“当前不要修复，先补哪些证据、补到什么程度再决定”；不得为了填满字段而编造动作；
- 报告必须明确区分“本次主问题”和“旁路线索”。修复建议必须绑定本次报告中的领先假设；产品现有 Evidence Gate 通过后，才可以把修复类建议标成“证据支持”。Evidence Gate 未通过时，只能公开交付“暂不变更/继续调查”类建议，并绑定当前领先假设以及为了验证或反驳它确实需要补的证据。不能把一个无关告警自行改名为“证据缺口”后混进建议；以下称为“本次主问题绑定规则”；
- 每条建议必须能回答：针对什么主根因或相关证据缺口、引用哪些本次证据、执行前提是什么、预期变化是什么、怎样验证、主要风险是什么、失败后停止还是回退；不规定固定话术、固定工具顺序或唯一答案；
- 产品输出必须区分“Agent 自审通过”“硬事实和安全边界通过”“独立审批通过”“执行后验证有效”。同一个 DeepSeek 使用 Skill 自审不能冒充独立审批；
- 只诊断模式永远只能交付结论和建议，不得因为建议质量通过就获得执行权限。

#### Agent+Harness OpsMind 的最小实现

- 不增加第二个 Agent、subAgent、模型评审服务或固定调查工作流；
- 扩展现有 `report-workorder` Skill，把“寻找反证、检查根因匹配、比较更安全替代方案、披露不确定性、定义验证和失败处理”提炼为最终建议自审方法；这是同一个主 Agent 的专业自审，不宣传为独立审批；
- 最终报告从自由字符串建议升级为可审计的结构化建议，并保存自审结论；题目要求建议时不能用空列表假装完成；
- Harness 在正式接收报告前只检查机器能够确定的硬事实：建议交付是否非空、绑定的领先假设是否存在、证据编号是否存在并属于本次调查和 Scope、是否把未执行写成已修复、是否泄密或越权、是否绕过动作审批；Harness 不使用关键词判断技术方案对不对，也不复制或提前取代现有 Evidence Gate；
- 不符合“本次主问题绑定规则”、但偶然在同一租户 Scope 中发现的告警，只能进入单独的“旁路线索”区域，不能混入本次修复建议；这一条明确用于修复上一轮 Agent+Harness 直连报告把“宁德 MTU”和“北京 AGV 无线遮挡”两条历史模拟告警写进本次建议的问题；
- 自审或提交前硬边界不通过时，正式报告不得入库；原报告工具把明确问题返回给同一个主 Agent，由它在当前 Claude Agent SDK 会话内修正后重新提交，不启动第二调查 Agent。只有通过后才正式保存一次。仍不合格时由现有 Harness 失败收尾如实标记“修复建议未通过产品自审/发布检查”，不得生成第二份正式报告或用万能建议补齐；
- 如果建议进一步转成机器执行动作，继续走现有动作目录、审批、票据、独立验证和回滚，不改变现有安全架构。

#### LangGraph OpsMind 的最小实现

- 不增加 Graph 节点，不增加模型，不改变 Flash/Pro 双模型职责、调查 Graph、Evidence Gate、Checkpoint 或动作安全；
- **废弃旧写法：**不得让所有调查结果绕入现有 `ACTION_PROPOSAL`。真实代码中的该节点是机器动作入口，后接动作目录、现场快照、策略、审批、票据、执行、验证和回滚；普通文字建议进入该节点会混淆“告诉用户怎么修”和“系统申请真正动手”；
- Case 明确要求建议时，由现有 Pro 推理模型在现有 `FINALIZE` / `finalize_and_learn` 最终报告阶段形成并自审开放式建议；Evidence Gate 已通过时可以形成有证据的修复建议，Gate 未通过时只能形成“暂不变更/继续补证”的建议；
- 建议只写入现有最终报告的 `terminal_result`，不新增 Graph 节点或连线，不新增 Graph State 顶层字段，不改变 Checkpoint 恢复语义；现有 `ACTION_PROPOSAL` 继续只负责请求机器执行的动作；
- 建议自审沿用与 Agent+Harness 相同的问题，但实现仍属于 LangGraph 自己的 FINALIZE Prompt/Knowledge 和最终报告合同，不引入跨产品共享运行服务；
- 现有确定性校验只核对证据引用、Scope、结构和执行安全，不用固定关键词、固定动作名或隐藏故障树限制建议内容；
- 题目要求建议时，LangGraph 最终建议交付同样不得为空；证据不足时必须交付“暂不变更、优先补证”的安全建议，不能再次以 `recommendations=[]` 直接结束。第一次输出只存在合同字段错误时，允许同一个 Pro 在同一个 FINALIZE 节点内最多纠正一次；仍不合格就如实标记建议交付失败，不增加 Graph 自循环或调查轮次；
- 只诊断模式在建议形成并保存后直接结束，绝不进入执行；人机协同和受控模式仍只有在调查核心原本决定形成真实机器动作提案时，才进入原有 `ACTION_PROPOSAL`、快照、策略、审批、票据、执行、独立验证和回滚链。

#### 同模型偏差的诚实边界

两套产品底层都使用 DeepSeek V4。同一模型按 Skill 或阶段提示复核自己的建议，能够减少遗漏，但仍可能维护自己的原判断、忽略共同盲点。因此开发期不把自审写成“独立 AI 批准”，也不为了制造表面独立性再增加一个同模型 subAgent。

直接模式下，产品负责给出“已自审、可发布 / 有条件可发布 / 建议未通过”的诚实状态；任何状态变更继续依赖现有独立审批和执行后验证。EvalOS 模式下，再由现有三路 AI Judge 提供独立会话的辅助第二意见，但它们同样是 DeepSeek 系列，只能提示风险，不能覆盖确定性 Code Grader 或授权执行。

## 3. 最终开发期架构

只保留一个真实5G实验环境和三个互斥的使用模式：

| 使用模式 | 谁准备和占用实验环境 | 谁执行调查 | 谁评分 | 结束后谁负责复位 |
|---|---|---|---|---|
| LangGraph 直连 | 现有实验控制入口 | LangGraph OpsMind | 不经过 EvalOS | 保留 LangGraph 现有责任语义：外围控制方复位，产品验证状态 |
| Agent+Harness 直连 | 现有实验控制入口 | Agent+Harness OpsMind | 不经过 EvalOS | 保留 Agent+Harness 现有自动复位语义，外围再验证干净 |
| EvalOS 评测路径 | EvalOS | 被测 OpsMind | EvalOS Code Grader + AI Judge/AI调查 | EvalOS 复位并验证干净 |

两套产品直接运行时，不需要经过 EvalOS。

直连不等于没有质量边界：LangGraph 在现有 `FINALIZE` 最终报告阶段完成开放式建议自审，Agent+Harness 使用现有 `report-workorder` Skill 完成建议自审；两套产品自己的报告边界只核对证据真实性、第2.6节“本次主问题绑定规则”、Scope 和执行安全。它们不得把同模型自审包装成独立审批。真正请求改变环境时，继续由各自现有审批、安全策略和执行后独立验证负责。

EvalOS 评测时，不替被测产品调查，也不替它调用产品 MCP。EvalOS 只负责考场、考务、预算、安全、证据汇总、评分和复位；LangGraph 或 Agent+Harness 仍用自己的真实核心完成调查。

EvalOS 评测两个产品时，必须串行执行：

1. 为第一个产品准备实验环境；
2. 运行一个 Trial；
3. 复位并证明实验环境干净；
4. 再为第二个产品准备实验环境；
5. 运行第二个 Trial；
6. 再次复位并证明干净。

不允许两个产品同时认为自己拥有实验环境。

## 4. 外围只做四项修复

除了下面四项，不新增外围平台。

### 修复一：给唯一实验环境加一个明确的“当前使用者”

#### 人话解释

现在最大风险不是实验室不能启动，而是 LangGraph、Agent+Harness 和 EvalOS 可能各自保存一份“我正在使用实验室”的状态。三份状态一旦不一致，就可能串场、误复位或把上一场的证据带进下一场。

修复后，最底层实验控制器是唯一裁判，只认一个物理租约。租约增加以下公开信息：

- 当前模式：LANGGRAPH_DIRECT、AGENT_HARNESS_DIRECT 或 EVALOS；
- 当前产品；
- Trial 标识；
- 租约标识和到期时间；
- 主机本次开机标识；
- 当前状态：空闲、使用中或隔离待处理。

产品已有的薄适配器可以保留，但它们只能转交请求，不能各自创造第二个物理槽位或第二份占用事实。

#### 断电处理

如果实验室主机在使用中断电，重启后本次开机标识会改变。系统不得猜测上一个 Trial 可以继续，也不得自动把环境交给下一场；必须把实验室标为“隔离待处理”，由明确的复位动作清场并验证干净后才能再次使用。

这会牺牲自动恢复速度，但可以避免带着脏环境继续评测。

### 修复二：把“是否可以评测”拆成前后两次检查

#### 当前问题

现有顺序存在死结：

1. EvalOS 启动 Trial 前要求产品已经绑定本次 Trial；
2. 但 EvalOS 只有在启动 Trial、准备实验环境后，才能生成并交付这次绑定。

也就是“没有开场不能绑定，没有绑定又不让开场”。

#### 修复后的顺序

第一次检查发生在准备实验环境之前，只确认：

- 产品服务正常；
- 产品版本和能力合同符合要求；
- 产品报到通道正常；
- 实验环境当前空闲；
- 此时尚未绑定 Trial 是正常状态。

通过后，EvalOS 才准备实验环境并创建唯一租约。

第二次检查发生在实验环境准备和绑定之后、第一次真实模型调用之前，必须逐项核对：

- 产品身份正确；
- 当前模式是 EVALOS；
- Trial 标识完全一致；
- 租约标识完全一致；
- 绑定没有过期；
- 产品确实可以访问本 Trial 范围内的 MCP 和证据。

第二次检查不通过，就不能让模型开始调查，EvalOS 立即收场并复位实验环境。

### 修复三：统一“被测系统报到与 Trial 绑定确认通道”

英文旧名 Candidate Observation。新版文档优先使用中文名，避免把它误解成调查或取证系统。

#### 它是什么

它只是被评测的 OpsMind 向 EvalOS 报到的一条小通道，用来回答：

- 我是哪套 OpsMind；
- 我运行的是什么版本；
- 我是否在线；
- 我支持哪些公开能力；
- 我是否已经绑定到 EvalOS 刚准备的那个 Trial 和租约。

它不传输调查思路、报告、5G证据、Case、Seed、评分规则或答案；不替代 MCP；不控制实验室；不参与产品直接运行。只有经过 EvalOS 评测时才使用。

#### 最小实现

- 复用 EvalOS 现有 Control API，不创建 Candidate 独立服务；
- 两套产品使用同一种签名 HTTPS 报到格式；
- 每个产品使用自己的 Ed25519 私钥，私钥只留在自己的主机；
- EvalOS 只保存对应公钥，两个产品不能互相冒充；
- 每次报到都签署时间、产品身份、版本和消息摘要；过期时间、重复随机号或正文被改动都拒绝；
- 产品约每60秒报到一次；
- 开发期 EvalOS Control API 保持现有单实例运行，不为这条通道增加多实例同步组件；
- EvalOS 只在内存中保存最近一次有效状态，并设置约180秒有效期；
- EvalOS 重启后先视为“不确定”，等待下一次报到再恢复 ready；
- 防重放 nonce 只保存到短期、自动过期的内存缓存，不把每分钟心跳永久追加到数据库；
- 评测所需的正式绑定和 Trial 证据仍进入原有 Trace/Ledger，不把心跳缓存当正式账本。

#### 一次性切换

新通道在本地和非 Trial 场景验证通过后，一次性替换：

- Agent+Harness 的短期 Candidate Bearer 路径；
- LangGraph 的 Candidate SSH 路径。

切换完成后删除活动代码中的旧入口，不长期保留双协议兼容。Git 历史负责追溯。

### 修复四：停止建设自研部署平台，只保留手工可控的版本切换

#### LangGraph

- 保留现有一个 Compose project；
- PostgreSQL、Redis、API、Worker 继续按现有产品结构运行；
- 普通发布只替换 API/Worker，不重建 PostgreSQL/Redis；
- 不再让 systemd 和 Docker 同时监督 API/Worker；
- Relay 和凭据续期保持独立，不跟随应用发布重装。

#### Agent+Harness

- 保留已有 Data Compose 和 App Compose；
- 普通发布只替换 Agent Service，不重建 MySQL/Redis；
- Relay 和三角色续期保持独立；
- 续期器不再依赖读取 Agent 容器名字来寻找数据库配置；
- 统一现有运行用户和 Secret 读取权限，但不放宽 Secret 权限。

#### 两套产品共同规则

- 在可信环境构建一次镜像；
- 用不可变镜像摘要标识版本；
- 每个产品只保留 current 和 previous 两个可切换版本；
- 激活失败时手工切回 previous；
- 不建设发布事务状态机、自动协调器、独立注册中心、Kubernetes、服务网格、Vault 或镜像平台；
- 本轮不修改业务数据库结构；
- 应用回滚只切镜像，不自动回滚数据库；
- 数据库版本不兼容时在切换前阻断，不能先上线再赌自动恢复。

## 6. 共享主机和凭据的最小安全规则

开发期允许继续使用现有主机布局，不为了“看起来商用”立即拆机器。任何两套系统只要位于同一台主机，就必须做到：

- 使用不同的目录、Compose project、运行账号和 Secret；
- 普通部署账号不能加入可以控制全主机容器的 Docker 管理组；否则“分账号”只是表面隔离；
- 每个部署账号只允许调用本产品少量、固定、由 root 保护的 status、deploy、rollback 命令；命令内部写死允许的目录和 Compose project，不接受任意路径；
- 部署包在可信环境完成构建和校验，服务器只接收已固定的版本；禁止把用户上传的任意脚本或安装命令直接以 root 执行；
- 每个部署账号不允许扫描、停止或修改另一产品；
- 普通自动化不得长期使用 root；
- Candidate 报到密钥、Relay 密钥、管理身份和三角色凭据互不复用；
- Candidate 报到密钥只允许“报到和确认绑定”，不能调用 observe、MCP、prepare、reset 或任何管理动作；
- Secret 只从环境变量或现有受控 Secret 文件装载，不写进源码、Trace、快照、报告和构建产物；
- 日志只记录 key_id、时间和结果，不记录 Token、私钥、密码或完整请求头；
- 长期机器密钥必须能单独吊销和替换，吊销一个产品不能影响另一个产品；
- 日常运维继续走现有固定管理网络，不依赖浏览器扫码登录。

这里不追求正式商用多租户隔离，但必须防止一次普通部署误伤另一套产品。

## 7. 三条链路怎样才算真正跑通

每次端到端运行必须留下六类凭证。缺任何一类，都不能说“已经跑通”。

1. 版本凭证：产品 commit、镜像摘要、公开能力合同；
2. 准备凭证：实验环境准备成功，唯一模式和租约正确；
3. 绑定凭证：产品、Trial、租约、MCP 范围完全一致；
4. 核心运行凭证：真实模型、真实核心、真实工具调用和证据；
5. 结束凭证：产品报告、非空的建议交付、产品建议自审结果和任务终态；题目要求建议且模型已经正常形成最终报告时，空列表、`null` 或只有“转人工”不算完成。服务中断、模型失败或安全熔断时必须如实标记“建议未交付”并判资格不通过，不得由外围补写万能建议。EvalOS 路径还必须包含建议质量确定性检查、Code Grader、Ledger，以及按冻结配置应当产生的 AI Judge/AI调查记录或明确的未触发说明；
6. 清场凭证：实验环境复位成功且验证干净。

具体标准如下。

### 7.1 LangGraph + 5G实验室

- 使用真实 LangGraph Graph、双模型、MCP、Evidence Gate 和 Checkpoint；
- 对真实故障完成自主调查；
- 产生可核对的证据、非空建议和报告；根因只有 `probable` 时必须给出有前提的建议，证据不足时必须给出“暂不变更、优先补证”的建议；
- 复用现有 FINALIZE 最终报告阶段完成开放式自审；普通人工建议不受动作目录限制，只有调查核心原本决定真正请求机器执行时才进入现有 ACTION_PROPOSAL、动作目录和审批；
- 动作继续遵守审批与安全门；
- 结束后按 LangGraph 现有责任语义完成外部复位并验证干净；
- 不经过 EvalOS，不使用 Candidate 报到通道。

### 7.2 Agent+Harness + 5G实验室

- 使用真实 Claude Agent SDK、DeepSeek、单 Agent、MCP、Skills、ToolSearch 和 Harness；
- 对真实故障完成自主调查；
- 产生可核对的证据、非空建议和报告；使用升级后的 `report-workorder` Skill 完成建议自审，但不得声称这是独立审批；
- 每条建议必须符合第2.6节“本次主问题绑定规则”；同一 Scope 中偶然发现的旁路告警只能单列，不能再次把“宁德 MTU”和“北京 AGV 无线遮挡”这类无关事项混入本次修复建议；
- 动作继续遵守 Hook、Evidence Gate 和安全边界；
- 保留产品现有自动复位语义，外围再验证干净；
- 不经过 EvalOS，不使用 Candidate 报到通道。

### 7.3 EvalOS 依次评测两个 OpsMind

- EvalOS 真实创建独立 Trial，并控制 Seed、资源记账、高位安全熔断、盲身份和安全门禁；
- EvalOS 准备并绑定真实5G实验环境；
- 被测产品使用自己的真实核心和 MCP 调查；
- EvalOS 原样保存产品的结构化建议和产品自审结果，不替产品生成、改写或补齐建议；
- EvalOS 保存完整 Trace、证据、成本、审批和终态；
- 确定性 Code Grader 对题目是否交付建议、证据和 Scope 绑定、验证与安全完整性作机器判定；不得靠关键词、固定动作名、Token、耗时或工具顺序评分；
- 现有三路 AI Judge 复用原有三次调用：Outcome 检查建议是否针对根因，Evidence 检查建议证据，Trajectory 检查是否过早或冒险提出动作；不增加第四 Judge，AI 结论仍为辅助意见；
- 结果写入不可变 Ledger；
- 每个 Trial 后复位并验证干净；
- 两个产品使用同一 Case/Seed/裁判基线时必须串行，且中间完成清场。

第一轮只做每个产品一个真实资格验证 Trial，但不计入正式成绩和排名。确认考场、接入和评分链完整后，再由产品经理单独批准是否进入正式计分。

## 8. 失败时怎样快速判断是谁的问题

| 失败位置 | 优先归属 |
|---|---|
| 实验环境还没准备就失败 | 外围部署、网络、Secret 或实验控制 |
| 实验环境准备成功，但产品不能精确绑定 | Candidate 报到/绑定外围 |
| 已绑定，但第一次真实模型调用都没发生 | 产品运行环境、模型接入或外围配置 |
| 真实模型已经开始，但调查、取证或报告失败 | 对应产品真实核心问题，需要单独诊断，不能用外围兼容层掩盖 |
| 根因已经通过 Evidence Gate，但建议为空或直接跳过建议阶段 | 对应产品建议交付合同问题；不得由 EvalOS 或外围补写 |
| 建议引用本次 Scope 内、但不符合第2.6节“本次主问题绑定规则”的旁路告警 | 对应产品建议自审和报告发布边界问题；必须单列旁路线索，不能进入本次修复建议 |
| 产品完成，但 EvalOS 没有 Trace、评分或 Ledger | EvalOS 评测链问题 |
| 冻结配置要求 AI Judge 运行，但记录缺失 | EvalOS AI 评测链问题，不能把评测说成完整 |
| 结束后实验环境没有恢复干净 | 实验室控制问题，立即隔离，禁止下一场 |
| 主机重启后旧租约仍显示可用 | 断电恢复问题，立即隔离，禁止自动续跑 |

每次只修失败归属范围内的问题，不用新增跨系统监督器来“兜底”。

## 9. 明确不做

- 不改两套 OpsMind 的调查核心；
- 不新增第二调查 Agent、建议审核 subAgent、第四 AI Judge 或独立建议审核服务；
- 不把同一个 DeepSeek 的 Skill 自审包装成独立 AI 审批；

## 10. 开发期仍然接受的风险

这份 MVP 追求尽快跑通，不假装已经达到最终商用高可用。

| 风险 | 开发期处理方式 |
|---|---|
| 一个物理实验环境是单点 | 接受串行；任何异常先隔离，不自动切到“第二槽位” |
| EvalOS Control API 是单实例 | 接受短暂停顿；重启后等待下一次报到，旧 ready 不恢复 |
| 两套产品可能仍共享主机 | 用目录、账号、固定命令、Secret 和 Compose project 隔离；整机故障仍可能同时影响两者 |
| Candidate 机器私钥长期存在 | 权限只限报到、每产品独立、可单独吊销；开发期采用人工换钥，正式商用前再设计自动轮换 |
| 应用回滚依赖人工决定 | 只保留 previous 镜像这一条路径；不建设自动事务引擎 |
| 数据库不能随应用自动倒退 | 本轮禁止改结构；首次切换前用现有能力做一次可恢复备份，正常回滚不恢复数据库 |
| 抓包、Trace 和日志可能占满磁盘 | 每次运行前检查空间，沿用现有单 Trial 限额和清理规则，不新增存储平台 |
| 两套产品核心可能暴露真实缺陷 | 停在对应链路如实诊断；未经单独审核，不以外围改造名义改核心 |
| DeepSeek 自审可能维护自己的原判断 | 明确标为“Agent 自审”而非独立批准；硬事实由程序校验，任何变更继续走独立审批和执行后验证，EvalOS AI Judge 只提供辅助第二意见 |

这些是明确接受的开发期限制，不得在汇报中写成“已经解决”。

## 15. 三个平台与5G实验室统一版本维护原则

> 状态：产品经理已于2026-09-01明确批准。该原则约束 LangGraph OpsMind、Agent+Harness OpsMind、EvalOS 和5G数字孪生实验室后续全部版本工作。

LangGraph OpsMind、Agent+Harness OpsMind、EvalOS 和5G数字孪生实验室统一执行以下版本维护原则：三个平台各自的 `main` 是唯一稳定主线，5G实验室源码继续由 EvalOS 仓库管理，但必须拥有独立的控制器版本和生产标签；任何新需求只能从上一版已经真实验收、已经上线且标签明确的准确 `main` 版本开始，禁止从旧分支、临时分支、废弃分支或人工拼装的代码开始开发。修改代码、配置、分支、构建、部署或真实验收前，必须先向产品经理列清当前稳定版本、现存问题、准备修改的内容、明确不动的核心、拟用分支名称、测试方法、部署和回滚方法，获得本任务明确批准后才能执行。功能分支、临时分支和废弃分支必须使用一眼能看懂的“产品＋用途＋日期”名称；废弃和临时分支必须明确标注 `abandoned` 或 `temporary`，不得合并、构建或部署。历史提交号是已经验收和部署证据的一部分，不重写、不变基、不强制推送；对产品经理统一使用“中文版本名称＋短提交号”，为稳定版本建立可读、不可变的生产标签，今后的提交说明必须直接写清修改了什么。候选版本验收通过后，必须先收回 `main`、推送 `origin/main`、建立生产标签并核对线上准确版本，完成这四项后才能开始下一项需求；较早提交的端到端结果和最终提交的局部测试只能称为组合证据，不能冒充最终提交已经完成真实端到端验收。工作区中用户已有修改、临时补丁、构建产物、运行证据和未跟踪文件必须先清点并隔离，只允许提交本任务文件，Secret、Token、密码和私钥永远不得进入 Git。EvalOS 发布包必须记录准确 Git 版本和内容摘要；5G实验室控制器必须另有版本身份证、组件清单摘要和 `current/previous` 两代回滚，只保留一个权威打包与安装入口，陈旧压缩包和隐蔽兼容路径必须废弃。未经产品经理单独批准，不删除远端分支或标签、不重写历史、不自动回滚数据库、不部署、不运行 Trial、不操作5G实验室，也不得借版本纠偏改变 LangGraph 的 Graph 与双模型核心、Agent+Harness 的 Claude Agent SDK 单 Agent核心、EvalOS 的评测与账本核心或5G实验室的场景、复位和安全核心。
