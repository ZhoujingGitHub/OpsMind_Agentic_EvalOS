# OpsMind 三产品能力边界与商用迭代方向（截至 2026-08-17，EvalOS M3.0 阶段基线）

> 文档状态：当前能力边界基线  
> 更新时间：2026-08-17  
> 适用产品：Agent+Harness OpsMind、LangGraph OpsMind、OpsMind Agentic EvalOS  
> 用途：作为产品对外表述、EvalOS 评测设计、后续研发排期和商用验收的共同参考。

## 一、先说结论

当前三款产品的关系可以用一句话说明：

> 两套 OpsMind 是参加考试的智能运维产品，EvalOS 是负责出题、提供隔离考场、记录过程和评分的评测平台。

两套 OpsMind 当前都能完成智能调查、证据收集、根因判断和修复建议，但都没有正式开放“受控自动修复生产网络”的商用能力。

因此，EvalOS 可以在数字孪生实验室中给它们临时授予有限的仿真修复权限，测试未来的闭环潜力；但这种实验室能力不能直接表述为“产品已经能够在客户生产网络自动修复”。

当前存在的主要问题不是产品架构冲突，而是评测口径需要进一步对齐：

- 两套 OpsMind 当前正式产品的主要工作模式是只诊断，或者人工审批后的仿真执行。
- EvalOS 当前 M3 题目却把“证据充分时自动执行一次处置并验证恢复”设成了大多数 Case 的统一要求。
- 如果不区分工作模式，EvalOS 可能把“没有自动修复”误判成“产品能力失败”。

所以后续评测必须明确区分：只诊断、人机协同、受控自动修复三种模式，并按照考生实际支持的模式评分。

## 二、三个产品分别是什么

| 产品 | 用人话解释 | 当前核心价值 |
| --- | --- | --- |
| Agent+Harness OpsMind | 以 Claude Agent SDK 为核心的智能运维 Agent。Agent 自己判断需要查什么、形成什么假设、什么时候停止；Harness 负责权限、安全、审批和记录。 | 灵活调查、开放式推理、按需调用 MCP/Skill，并形成有证据的运维结论。 |
| LangGraph OpsMind | 使用 LangGraph 把调查、证据质量检查、动作提案、审批、执行和收口组织成可持久恢复的状态图。 | 调查过程结构清晰，任务可以暂停、恢复、持久化和审计。 |
| OpsMind Agentic EvalOS | 独立于两套 OpsMind 的评测平台，相当于考场、考务系统和评分系统。 | 冻结试卷、Seed、预算和评分标准，在数字孪生环境中公平比较两套架构，并保留完整证据。 |

数字孪生实验室不是第三名考生。它是 EvalOS 的“仿真考场”，通过 Open5GS/UERANSIM 等组件制造可复现的 5G 运维故障，让两套 OpsMind 在不触碰客户真实网络的前提下接受测试。

## 三、“闭环”到底是什么意思

“闭环”不是只有“自动修复”这一种。智能运维产品至少存在四种不同层次的闭环：

| 闭环类型 | 用人话解释 | 当前两套 OpsMind 的状态 |
| --- | --- | --- |
| 调查闭环 | 从告警出发，查询日志、指标和状态，形成有证据的根因结论。 | 两套均已具备。 |
| 建议闭环 | 不直接修改网络，但输出修复建议、影响、验证方案和回滚方案。 | 两套基本具备。 |
| 人机协同闭环 | Agent 提方案，真人批准后执行，再验证；失败时回滚。 | 两套都有骨架，但尚未连接真实生产动作。 |
| 自动修复闭环 | Agent 在企业预先批准的小范围内自动执行低风险修复。 | 两套都没有形成正式商用能力。 |

因此，后续说“OpsMind 已经完成闭环”时，必须说清楚是哪一种闭环。不能把“调查闭环”说成“生产自动修复闭环”，也不能因为产品没有自动修改客户网络，就否定其商用价值。

### 4.1 Agent+Harness OpsMind 的准确定位

当前可以准确表述为：

> Agent+Harness OpsMind 已经完成“只读智能调查 + 人工审批动作闭环 + 受控仿真执行”的安全底座，但尚未将只诊断、人机协同和受控自动修复做成租户级、由后台统一强制执行的三种正式产品模式。

已经具备：

- Claude Agent SDK 单主 Agent 的开放式调查能力；
- MCP、Skill 和 SDK 原生 Read、Write、Edit、Bash、代码执行能力；
- 动作提案、预检、审批、执行、验证和回滚状态链；
- Agent 不能自己批准自己的动作；
- 权限、租户范围、审计和幂等基础。

尚未具备：

- 统一工作模式开关；
- 真实生产动作连接器；
- 企业低风险动作白名单；
- 根据 `autonomy_level` 自动审批、自动执行和自动降级的正式策略。

### 4.2 LangGraph OpsMind 的准确定位

当前可以准确表述为：

> LangGraph OpsMind 当前生产环境默认运行在只诊断模式；人机协同所需的动作提案、审批暂停、恢复、验证、回滚和幂等框架已经具备，但真实动作尚未接入；受控自动修复将在企业动作白名单和安全策略完成后开放。

已经具备：

- 正式的只读生产调查能力；
- 调查过程持久化、Checkpoint、暂停和恢复；
- 动作提案、策略预检、人工审批记录；
- 执行、验证、失败回滚和幂等骨架。

尚未具备：

- 真实生产动作处理器；
- 租户级工作模式；
- 企业动作白名单；
- 人机协同模式下“所有修改必须审批”的统一后台策略；
- 正式受控自动修复产品能力。

## 五、EvalOS 当前评测能力边界

| EvalOS 当前能力 | 实际在测什么 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 数字孪生 Case | 在隔离的 Open5GS/UERANSIM 环境制造可复现故障。 | Agent 能否面对接近真实协议状态进行调查。 | 不能证明产品已经安全接入客户生产网。 |
| Agent 能力通道 | 给两名考生相同模型预算、Case、Seed 和 Twin MCP 工具。 | Agent 的调查、证据、根因、安全停止和实验室处置能力。 | 不能证明完整商用产品已经通过验收。 |
| 实验室动作授权 | Harness 允许每个 Trial 最多执行一次受控 Twin 写入，不需要真人审批。 | Agent 是否能在隔离实验室选择最小动作并验证恢复。 | 不能证明产品已具备商用自动修复模式。 |
| 确定性评分器 | 检查根因、证据、终态、安全、恢复和预算。 | 任务是否真的恢复、证据是否可追溯。 | 不能代替企业审批、变更管理和生产风险评估。 |
| Product E2E 通道 | 计划检查真实 API、队列、Worker、恢复、持久化、审计和归档。 | 接通后可以验证完整商用产品链路。 | 两套产品当前端点尚未配置，因此还没有真正跑通。 |
| 生产安全边界 | EvalOS 明确禁止写入真实生产环境。 | EvalOS 评测不会修改客户生产网络。 | 不表示考生产品已经拥有真实生产连接器。 |

### 5.1 当前 M3 题目与产品模式的冲突

当前 80 个 M3 正式 Case 中：

- 76 个要求证据充分时执行处置并恢复；
- 4 个要求信息不足时安全停止；
- 每个 Trial 最多允许一次数字孪生写操作；
- 不要求真人审批；
- “环境是否恢复”是确定性评分硬门禁。

这套合同实际评测的是：

> 两种 Agent 架构在 EvalOS 临时授予一次数字孪生修复权限的条件下，自主完成调查、处置和验证的能力。

它不能直接代表：

> 两套 OpsMind 当前正式商用版本在各自真实工作模式下的完整产品能力。

### 5.2 为什么适配器会让考生拥有额外的实验室能力

Agent 能力通道不是从两套产品的正式生产入口提交任务：

- Agent+Harness 由 EvalOS 直接启动 Claude Agent SDK，并挂载 EvalOS 提供的 Twin MCP 工具；
- LangGraph Adapter 会为本次 Case 临时注册连接到 Harness 的动作处理器；
- 最终真正修改的是隔离数字孪生环境，不是客户网络；
- 写入许可来自 EvalOS 冻结的实验室策略，而不是产品租户的商业工作模式。

因此，当前成绩应这样解释：

| 结果 | 正确解释 | 不能这样解释 |
| --- | --- | --- |
| Agent+Harness 8/8 | 在 EvalOS Twin 临时授权下，表现出较好的实验室自主闭环能力。 | 商用自动修复已经上线。 |
| LangGraph 3/8 | 在同样实验室授权下，调查和自主处置稳定性仍不足。 | 当前只诊断产品完全不可用。 |
| LangGraph 剩余失败 | 证据召回、工具恢复和状态判断失败仍是真实问题；仅因未执行处置导致的失败属于模式口径不匹配。 | 所有失败都属于商用产品缺陷。 |

现有 Trial 证据仍然有价值，不需要删除。但必须重新标注为“实验室 Agent 能力资格证据”，不能冒充当前商用自动修复验收结果。

## 六、EvalOS 后续应如何调整评测口径

EvalOS 应在每个实验中冻结明确的工作模式，并按照不同模式评分。

| 评测模式 | 写入权限 | 正确通过条件 | 当前是否可公平比较 |
| --- | ---: | --- | --- |
| 只诊断（Diagnosis Only） | 0 | 找到根因、证据充分、给出安全建议；任何写入都判失败。 | 可以立即比较两套产品。 |
| 人机协同（Human in the Loop） | 审批后允许 | 提案、预检、暂停、审批、恢复、执行、验证或回滚全部正确。 | 框架可以测，但应先完成 Product Adapter。 |
| 受控自动修复（Controlled Autonomy） | 企业白名单内有限写入 | 自动选择最小动作，修复并验证；失败时回滚或降级人工。 | 目前只能作为实验室未来能力赛道。 |

建议进行以下设计调整：

1. 在实验 Manifest 增加冻结字段 `operation_mode`。
2. Case 的正确行为改成“根据工作模式决定”，不再让 76 道题统一要求自动修复。
3. 评分器按照模式判断：
   - 只诊断模式：不写入是正确行为，重点评分根因、证据和建议；
   - 人机协同模式：未经审批写入属于安全硬失败；
   - 受控自动修复模式：应该修却没有修才属于环境任务失败。
4. Agent 能力通道继续评测 Agent 大脑，但必须标记为实验室能力。
5. Product E2E 通道必须从两套产品真实 API 提交任务，验证排队、Worker、恢复、持久化、审计和归档。
6. 原 M3.0 设计冻结需要生成新的模式化版本；已有证据保留，但正式 480 Trial 应在新资格试运行通过后再启动。

## 七、真实商用还需要补足什么（人话版）

简单说，**商用不等于必须自动修复**。可以分三步建设：

1. 先把“只诊断版”做成可靠的商用产品；
2. 再开放“人工批准后修复”；
3. 最后才考虑“低风险自动修复”。

### 第一阶段：先把只诊断版做成商用产品

这一阶段最安全，也最符合两套 OpsMind 当前能力。

| 需要补什么 | 用人话解释 |
| --- | --- |
| 正式的“只诊断”总开关 | 不是靠大家自觉不点执行，而是后台从根上禁止所有修改客户网络的操作。即使管理员、Agent 或者接口误调用，也改不了网络。 |
| 每个客户相互隔离 | A 客户的 Agent 只能看到 A 客户的数据，绝对不能查到 B 客户的告警、日志和设备。 |
| 企业登录和权限 | 普通运维人员、审批人、管理员分别能做什么必须明确，不能所有人都是超级管理员。 |
| 稳定的任务系统 | 用户提交调查任务后，即使页面关闭、服务重启或者网络闪断，任务也不能丢，恢复后还能继续。 |
| 完整记录 | Agent 查了什么、看到了什么证据、为什么得出这个结论、谁操作过，都要能追查。 |
| 报告和证据归档 | 调查完成后，要形成正式报告，并保存引用的告警、日志、指标和运行轨迹。 |
| 商用端到端评测接口 | EvalOS 不能只在程序内部调用 Agent，还要从产品真实入口提交任务，验证排队、Worker 执行、断点恢复、数据库保存和报告归档。 |
| 运行稳定性 | 要验证高并发、超时、模型限流、数据库故障、服务重启后是否还能正常工作。 |

完成这些以后，就可以对外说：

> OpsMind 是一个可商用的智能诊断产品，能够自主调查、定位根因、给出修复建议，但不会修改客户网络。

这个定位已经具有明确的商业价值，不需要等自动修复完成。

### 第二阶段：开放“人工批准后修复”

这一阶段的关键是：**Agent 可以提建议，但不能自己批准自己。**

完整过程应该是：

```text
Agent 发现故障
  ↓
提出修复方案
  ↓
系统检查目标、参数和风险
  ↓
真人查看影响范围并批准
  ↓
系统执行
  ↓
重新查询网络，确认是否恢复
  ↓
失败则回滚，并重新打开调查
```

需要补充的能力如下：

| 需要补什么 | 用人话解释 |
| --- | --- |
| 正式工作模式开关 | 客户明确选择“人机协同”，系统才能进入修复流程；默认仍然是只诊断。 |
| 可执行动作目录 | 企业要提前定义允许执行什么，例如重启某个测试服务、恢复某条路由。不能让 Agent 临时发明生产命令。 |
| 真实操作连接器 | 目前两套产品主要操作仿真环境。未来要通过受控接口连接真实网管系统、云平台或网元。 |
| 人工审批页面 | 审批人要看到修什么、为什么修、影响谁、如何验证、失败怎么恢复，然后选择批准或拒绝。 |
| 审批不能绕过 | 无论从网页、API 还是 Agent 调用，只要没有有效审批记录，后台都必须拒绝执行。 |
| 执行前再次检查 | 批准以后还要确认网络状态没有发生变化，避免拿着半小时前的审批去修改已经变化的网络。 |
| 修复后验证 | 不能以“接口返回成功”作为修好，必须重新检查告警、日志、指标和业务状态。 |
| 真实回滚 | 修复无效或造成新问题时，能够恢复原来的配置，而不是只在数据库中写一句“已回滚”。 |

#### 两套产品分别还差什么

**Agent+Harness OpsMind：**

- 已有“提案→预检→审批→执行→验证→回滚”链路；
- 但目前执行的是仿真环境；
- 需要接入真实受控连接器；
- 需要增加正式工作模式总开关；
- 要保证任何入口都不能绕开审批。

**LangGraph OpsMind：**

- 已有暂停等待审批、批准后恢复、验证和回滚框架；
- 但生产环境现在只注册了查询工具，没有真实修复程序；
- 需要接入经过批准的动作处理器；
- “人机协同模式”下，所有修改都应该人工批准，不能只是最高风险操作才审批。

### 第三阶段：再做“受控自动修复”

这不是“Agent 想怎么修就怎么修”，而是：

> 企业提前批准一小部分风险低、影响范围小、容易验证、能够回滚的动作，Agent 只能在这个小范围内自动执行。

例如：

- 自动清理一条已经确认失效的测试告警；
- 自动恢复某个非关键服务；
- 自动调整数字孪生或测试环境中的配置；
- 自动执行经过企业审核的标准恢复动作。

要补充这些保护措施：

| 保护措施 | 用人话解释 |
| --- | --- |
| 自动修复白名单 | 明确哪些动作可以自动做、能改哪些资源、参数允许什么值。 |
| 次数限制 | 同一个故障不能反复自动修，避免无限重启或反复改配置。 |
| 影响范围限制 | 一次只能修改一个小范围目标，不能批量影响整个网络。 |
| 熔断开关 | 连续失败、指标恶化或者异常增多时，立即停止所有自动修复。 |
| 自动降级 | Agent 拿不准、证据不足或风险升高时，自动转成人工审批。 |
| 灰度执行 | 先在一个小范围目标上执行，验证没问题后才能继续。 |
| 维护时间窗口 | 某些操作只能在客户允许的时间段内执行。 |
| 独立验证 | 不能由执行动作的结果自己证明“修好了”，要重新读取真实业务状态。 |
| 可靠回滚 | 自动修复失败后，系统必须自动恢复原状态；不能回滚时立即通知人工。 |

### 最简单的推进顺序

| 阶段 | 可以对外宣称什么 |
| --- | --- |
| 阶段一：只诊断商用版 | 能自主调查、定位根因、给建议，但绝不修改客户网络。 |
| 阶段二：人机协同版 | Agent 提出方案，真人批准后系统受控执行。 |
| 阶段三：受控自动修复版 | 只有企业提前批准的少量低风险动作可以自动执行。 |

因此，当前最应该优先补的是：

1. 把“只诊断模式”做成后台强制能力；
2. 接通两套产品的真实 Product E2E 评测接口；
3. 验证任务排队、执行、恢复、保存、审计和归档；
4. 在只诊断商用版通过后，再建设真实的人机协同操作；
5. 最后才开放受控自动修复。

一句话总结：

> 先证明 OpsMind 能稳定、可信地“看明白并说清楚”，再让它“经人批准后动手”，最后才让它在极小的安全范围内“自己动手”。

## 八、后续产品迭代方向

### 8.1 三个产品共同遵守的原则

1. 不把实验室能力冒充生产能力。
2. 不把 Agent 给出的文字建议冒充已经完成修复。
3. 不把“接口返回成功”冒充业务已经恢复。
4. 不让 Agent 自己批准自己的动作。
5. 不让工作模式只存在于页面，必须由后台统一强制执行。
6. 不因为追求自动化而牺牲租户隔离、审计、回滚和安全停止。
7. EvalOS 不规定固定解题路径，只冻结边界、预算、权限和通过标准。

### 8.2 Agent+Harness OpsMind 下一步

1. 建立租户级工作模式和后端统一策略门禁。
2. 优先完成只诊断商用版的可靠性、审计和 Product Adapter。
3. 将当前动作状态链接入真实但默认关闭的受控连接器。
4. 将 `autonomy_level` 从记录字段升级为正式策略输入。
5. 在企业白名单、熔断和降级机制完成前，不开放自动修复。

### 8.3 LangGraph OpsMind 下一步

1. 保持当前生产只诊断默认值。
2. 完成真实 Product Adapter，验证队列、Worker、Checkpoint 恢复、持久化、审计和归档。
3. 建立租户级工作模式。
4. 为经过批准的动作注册真实 Handler，并明确执行、验证和回滚合同。
5. 人机协同模式下，所有写操作均必须经过人工审批。
6. 在企业白名单和自动降级策略完成前，不开放自动修复。

### 8.4 EvalOS 下一步

1. 把评测模式从单一“处置闭环”拆成只诊断、人机协同和受控自动修复三类。
2. Case 和评分器改为模式感知。
3. 保留当前 Agent 能力通道，但明确标记为数字孪生实验室能力。
4. 接通两套产品的 Product E2E Adapter。
5. 先完成只诊断模式的公平资格评测，再测试人机协同。
6. 自动修复作为未来能力赛道，不能提前变成当前商用硬门禁。
7. 生成新的设计冻结版本，重新完成资格和容量试运行后，再决定是否启动正式 480 Trial。

## 九、当前正式结论

截至当前版本，可以对外准确表述为：

> Agent+Harness OpsMind 和 LangGraph OpsMind 都已经具备智能调查、证据收集、根因分析和修复建议能力。两套产品都具备不同程度的人机协同动作框架，但当前均未连接客户真实生产操作，也没有形成可租户配置的受控自动修复能力。OpsMind Agentic EvalOS 已经能够在隔离数字孪生环境中评测 Agent 的调查和实验室处置能力，但现有 M3 处置型评测合同需要升级为按工作模式评分，才能准确反映两套产品当前的商用能力边界。

当前产品路线的正确顺序是：

```text
只诊断商用版
    ↓
人机协同商用版
    ↓
受控自动修复版
```

正式 480 Trial 不应继续使用“所有考生默认具备自动修复能力”的隐含前提。应先完成模式化评测合同、两套 Product Adapter 和只诊断商用通道资格验收。
