# 真实5G根因调查时长设计依据——面试复习版

> 版本日期：2026-08-23
> 适用产品：OpsMind_Agentic_EvalOS、Agent+Harness OpsMind、LangGraph OpsMind
> 文档目的：用人话解释“为什么15分钟太短、45/60分钟怎么来的、EvalOS如何公平执行”。

## 一、先记住结论

如果15分钟表示“必须完成一次完整的真实5G网络根因调查，否则判失败”，这个限制偏短。

更合理的做法是：

| 时间 | 它真正代表什么 | EvalOS怎么处理 |
|---|---|---|
| 15分钟 | 首次进展检查点 | Agent说明查过什么、当前怀疑什么、还缺什么证据；没有最终根因不直接判失败 |
| 30分钟 | 普通Case目标完成时间 | 单域、证据比较完整的调查应争取完成，但超过30分钟不立即杀死 |
| 45分钟 | 普通Case的考生硬上限 | 到时仍未完成，要求安全停止、保留部分结论和全部轨迹 |
| 50分钟 | 普通Case的Trial总上限 | 比考生多出的5分钟用于独立验证、Twin复位、归档和安全清理 |
| 60分钟 | 复杂跨域Case的考生硬上限 | 用于同时涉及RAN、传输、核心网、鉴权、安全等多域问题 |
| 65分钟 | 复杂Case的Trial总上限 | 同样给考场保留5分钟收尾时间 |
| 数小时或更长 | 完整事故复盘 | 属于事故后的异步深度分析，不应塞进一条正式Trial |

一句话记忆：

> 15分钟交调查进度，30分钟争取查完，普通Case最晚45分钟安全停，复杂Case最晚60分钟安全停；考场额外留5分钟做验证和复位。

## 二、为什么不能把15分钟当成死亡线

### 2.1 真实5G问题不是只查一张告警表

一个表面现象可能来自完全不同的地方。例如“用户无法上网”，可能是：

- 无线侧注册或信号问题；
- AMF、SMF、UPF等核心网功能异常；
- 用户签约、DNN或切片配置不一致；
- 传输路由、DNS、NAT或云资源异常；
- 多个域分别正常，但组合在一起出现问题；
- 监控数据缺失、过期、冲突，甚至包含提示注入攻击。

Agent需要先确认影响范围，再提出多个可能原因，调用不同数据源逐个排除，最后还要说明证据是否足够。强制它在15分钟结束，容易奖励“猜得快”，惩罚“认真补证据”。

### 2.2 完整闭环不只有“猜根因”

ETSI的零接触网络和服务管理（ZSM）把闭环拆成监测、分析、决策、执行等阶段。执行后还需要继续监测，确认问题是否真正恢复。也就是说，完整闭环天然比一次问答复杂。[ETSI ZSM参考架构](https://www.etsi.org/deliver/etsi_gs/ZSM/001_099/002/01.01.01_60/gs_ZSM002v010101p.pdf)

ETSI关于闭环安全的资料进一步说明，分析阶段需要结合监控数据和历史数据形成洞察，错误或被篡改的分析结果会把后续决策和执行带偏。因此，调查不仅要快，还要证明数据可信。[ETSI ZSM闭环安全](https://www.etsi.org/deliver/etsi_gr/ZSM/001_099/017/01.01.01_60/gr_ZSM017v010101p.pdf)

### 2.3 5G端到端保障天然需要跨层关联

TM Forum指出，5G切片保障可能横跨通信服务、网络切片、子切片、网络功能，以及RAN、传输、核心网等自治域，还要把基础设施、虚拟资源、网络功能和业务影响做多层关联。[TM Forum：5G切片保障](https://inform.tmforum.org/features-and-opinion/5g-slice-assurance-in-autonomous-networks)

用人话说：Agent不能看到一个AMF告警就立刻宣布“AMF坏了”。它可能还要确认用户面、会话、路由、签约和业务影响，才能区分真正根因与连带现象。

## 三、业界为什么把“快速响应”和“完整根因”分开

Google SRE的事件响应案例中，事件发生数小时后仍可能没有完整根因或缓解措施。这不是说效率不重要，而是说明复杂事故的根因调查不能简单用一个很短的统一时间代替。[Google SRE事件响应](https://sre.google/workbook/incident-response/)

AWS把事件生命周期分为告警与人员响应、分诊、调查与缓解、事后分析。事后分析还会继续研究真正根因和预防措施。[AWS事件生命周期](https://docs.aws.amazon.com/incident-manager/latest/userguide/incident-lifecycle.html)

因此，产品上应分别记录：

1. 多久开始响应；
2. 多久形成第一版判断；
3. 多久完成止损或恢复；
4. 多久形成有证据的根因结论；
5. 多久完成事故复盘和预防改进。

把这五件事都压成“15分钟内查完”，既不真实，也无法解释系统究竟慢在哪里。

## 四、Agent评测为什么特别在意时间预算

Anthropic的Agent评测研究指出，计算资源和时间限制并不是中立的。限制太紧，测到的可能是“谁更能适应狭窄资源”，而不是谁真正更有能力解决问题。它建议分别定义正常资源保障和最后强制停止阈值，而不是只写一个没有余量的死值。[Anthropic：Agent评测中的基础设施噪声](https://www.anthropic.com/engineering/infrastructure-noise)

Anthropic对Agent评测的总体建议还强调：Agent会多轮使用工具，并根据中间结果改变调查方向，评测环境和Harness必须匹配被测任务的复杂度，同时应评价结果而不是固定步骤。[Anthropic：揭秘AI Agent评测](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

这对EvalOS的直接启发是：

- 不能提前写死Agent必须调用哪些工具、按什么顺序调查；
- 不能因为一个Agent认真补证据而在15分钟被掐断；
- 也不能无限放任Agent循环，必须有硬停止线和安全收尾；
- 两名考生面对同一Case必须得到完全相同的时间预算；
- 超时应记录明确原因和部分成果，不能只显示`unknown`。

## 五、45分钟和60分钟是怎么制定出来的

需要诚实说明：目前没有一个权威电信标准规定“所有5G RCA必须正好45分钟完成”。45/60分钟是结合标准思想、真实任务复杂度和EvalOS工程约束形成的评测设计，不是伪造的行业强制标准。

制定逻辑如下：

### 5.1 15分钟保留为进展门槛

15分钟足以要求Agent产出第一版调查状态，但不足以覆盖复杂跨域补证、审批、执行后验证。因此保留它的管理价值，不把它当能力死亡线。

### 5.2 普通Case给到45分钟

普通Case的目标仍是30分钟内完成。再提供15分钟余量，用来处理模型响应波动、工具延迟、补证和一次合理的假设修正。45分钟后仍无结果，效率和可靠性就应受到评价。

### 5.3 复杂Case给到60分钟

跨域、安全、审批、工具失败恢复、执行后复核和回滚等Case包含更多独立环节。多出的15分钟不是让Agent闲置，而是避免把“复杂度”误判成“能力失败”。

### 5.4 EvalOS额外保留5分钟

考生结束不等于考试结束。EvalOS还要：

- 从独立观察面验证真实终态；
- 保存完整追加式轨迹；
- 复位数字孪生考场；
- 检查环境是否干净；
- 必要时隔离被污染的考场槽位；
- 生成不可变账本和评分证据。

这5分钟属于考场，不属于考生，不能拿去继续调查。

## 六、EvalOS如何落地

### 6.1 普通资格Trial

```text
考生Agent调查：最多45分钟
EvalOS验证、复位、归档：预留5分钟
整条Trial：最多50分钟
15分钟时：记录一次进展检查点
```

### 6.2 复杂跨域Trial

```text
考生Agent调查及受控闭环：最多60分钟
EvalOS验证、复位、归档：预留5分钟
整条Trial：最多65分钟
15分钟时：记录第一次进展检查点
```

### 6.3 到达硬上限之后

正确行为不是粗暴杀进程后写一条“失败”，而是：

1. 通知考生停止；
2. 保存当前假设、已确认事实和证据缺口；
3. 等待考生进入明确终态；
4. 如果考生无法停止，隔离该环境，禁止下一个Trial复用；
5. 由Twin独立复位并检查是否干净；
6. 明确区分考生超时、模型服务超时、EvalOS故障和Twin故障；
7. 原始失败和后续清理记录全部追加保存，不能覆盖历史。

## 七、正式480个Trial前还要用数据校准

45/60分钟是当前合理起点，但正式冻结前还应运行12～20个不计分资格Trial：

- 统计有效Trial的P50、P90、P95完成时间；
- 排除EvalOS宕机、Twin断线、模型限流等基础设施无效样本；
- 检查慢是因为Case确实复杂，还是Agent进入了无效循环；
- 如果45分钟仍截断超过5%的有效普通Case，逐题检查并把合理的复杂Case升级为60分钟档；
- 不能因为某个考生慢，就临时给它更多时间；
- 时间档位、Case、Seed、模型、工具、评分器必须一起冻结。

这里的P95用人话解释就是：100次有效运行中，大约95次能在这个时间以内完成。它用来避免被少数偶发极慢请求牵着走。

## 八、一小时上限不等于黑盒等待一小时

用户最难接受的不是任务长，而是不知道系统究竟还在工作、等待模型、等待工具，还是已经卡死。因此EvalOS必须同时提供三层可观察性：

| 层次 | 频率或判断线 | 人话解释 |
|---|---|---|
| 在线心跳（Liveness heartbeat） | 每30秒追加一次 | 只证明真实考生接口还活着、EvalOS还能联系到它，不代表调查取得了新进展 |
| 页面刷新 | 每5秒 | 实时更新已运行多久、还剩多久、最新外显动作、工具结果和事件数量 |
| 实质进展监测 | 5分钟提醒、10分钟告警 | 5分钟没有新证据或动作时提示“在线等待/需关注”；10分钟没有实质进展时提示“可能卡住” |
| 考生内部流空闲保护 | 10分钟 | Claude Agent SDK 连续10分钟没有任何流消息时安全停止；不能保留3分钟这类会误伤复杂推理的旧阈值 |
| 首次正式检查点 | 15分钟 | 汇总已经查过什么、当前证据和缺口；不是强制结束 |

页面至少应回答六个问题：

1. 这条Trial已经运行多久，还剩多少时间？
2. EvalOS最近一次成功联系真实考生是什么时候？
3. 最近一次真正的调查进展是什么，而不只是心跳？
4. 当前是在等待模型、调用工具、等待审批、执行验证，还是没有可见动作？
5. 已产生多少外显事件和工具结果？
6. 如果继续没有进展，何时会提示风险、何时触发安全停止？

这套设计不会把Agent变成固定工作流。Agent仍然自主决定假设、工具、顺序和停止时机；EvalOS只是像飞机驾驶舱仪表一样，把运行事实显示出来。日志数量、心跳数量和“话多不多”不直接计分，避免Agent靠刷日志获得高分。

EvalOS只展示外显决策、工具调用、机器事件和结果，不展示、保存或伪造模型隐式思维链。

还要特别区分两种“没有声音”：页面30秒心跳证明接口仍在线；Claude Agent SDK内部10分钟流空闲线用于防止一次模型调用永久挂死。前者负责让人看得见，后者负责最后兜底，两者都不能冒充“Agent已经取得实质进展”。

## 九、成本和并发要怎么理解

50分钟是最坏情况下的Trial总上限，不表示每条Trial都会跑满50分钟。

如果480条Trial全部跑满50分钟：

- 总计约400个串行小时；
- 4并发理论下限约100小时；
- 8并发理论下限约50小时。

实际运行会因为很多Case提前完成而明显缩短。正式容量试跑要测CPU、内存、数据库锁、Twin槽位、模型限流和网络稳定性，不能只用数学除法承诺完成时间。

## 十、常见误解

### 误解1：时间越长越能体现Agent能力

不对。无限时间会掩盖低效循环，也会放大成本。合理设计是“足够完成真实任务，但仍有明确上限”。

### 误解2：15分钟没有最终根因就是失败

不对。15分钟应检查Agent有没有实质进展。如果它已经排除了多个假设并明确指出证据不足，这可能是正确且安全的表现。

### 误解3：超过45分钟一定是考生能力差

不一定。需要区分考生问题、模型服务问题、Twin问题、网络问题和EvalOS问题。只有考生自身无效循环、未能停止或产品运行不可靠，才应计入考生成绩。

### 误解4：业务SLA就是Agent评测时限

不完全相同。业务SLA关心客户多久恢复；评测时限还要保证两名考生公平、环境可复现、证据完整。EvalOS可以同时报告响应时间、恢复时间和根因完成时间，但不能把它们混成一个数字。

## 十一、面试时可以这样讲

> 我们最初设置过15分钟调查上限，真实资格Trial暴露出它会截断Claude Agent SDK的开放式调查。复盘后我们没有简单把超时调大，而是重新研究了ETSI电信闭环、TM Forum跨域保障、Google和AWS事件响应，以及Anthropic的Agent评测方法。最后把15分钟改成进展检查点，普通Case采用45分钟考生预算加5分钟考场收尾，复杂跨域Case采用60加5分钟。为了避免用户黑盒等待，Adapter每30秒记录在线心跳，页面每5秒刷新；5分钟无实质进展提醒，10分钟告警。它不规定Agent的调查步骤，也不按日志数量计分。正式冻结前再用资格Trial的P95校准。这样既不给Agent写死调查路径，也不会无限运行，同时还能公平区分考生超时、模型故障和考场故障。
