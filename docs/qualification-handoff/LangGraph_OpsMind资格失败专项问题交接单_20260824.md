# LangGraph OpsMind 资格失败专项问题交接单

> 时间节点：2026-08-24
> 接收方：LangGraph OpsMind 产品与工程窗口
> 发出方：OpsMind Agentic EvalOS 评测总控
> 文档性质：考生产品整改工单；不包含隐藏 Case 答案
> 当前资格：`NO-GO`

## 一、用一句人话说明当前问题

LangGraph OpsMind 已经能够稳定启动、调用工具、提交报告、归档和释放资源，但当前报告经常只是“听起来合理”，没有被具体 Case 的真实证据和 Twin 终态证明。

所以当前不是“程序跑不起来”，而是：

> **考生每次都能交卷，但关键的根因题和任务结果题没有答对。**

## 二、必须遵守的修复边界

### 2.1 保持本项目自己的架构优势

本项目可以继续使用并发挥：

- LangGraph Checkpoint；
- Interrupt 与人工审批恢复；
- Worker、队列和持久恢复；
- 副作用防重放和幂等执行；
- 结构化状态、审计和归档。

EvalOS 不要求两个考生内部实现相同。

但不得为了通过评测：

- 按 Case ID 写死根因或动作；
- 为每个评测题增加固定答案分支；
- 按 Grader 字符串拼装报告；
- 修改 EvalOS 的 Case、Seed、预算、Grader、账本或隐藏合同；
- 读取隐藏 Case 答案；
- 用固定工具名或固定节点顺序冒充真实能力。

### 2.2 评分不检查LangGraph节点

EvalOS 不关心考生经过了哪个节点，也不按内部节点顺序评分。只要最终证据、根因、业务结果和安全行为正确，不同合理路径都可以通过。

因此，整改目标不是“增加一个能过评分器的节点”，而是让现有图真正根据现场证据收敛并完成正确业务结果。

## 四、已经确认的问题

### 4.1 “会写报告”没有转化为“解决具体 Case”

八条 Trial 的报告中出现过鉴权、N2 链路、用户面路由、DNS、UPF/MEC 等现实中可能成立的解释。这些内容单独看都像专业运维报告，但确定性 Grader 会继续核对：

- 原始工具数据是否真的支持该结论；
- 是否命中本 Case 的具体组件和因果关系；
- 是否排除了竞争假设；
- Case 要求的是真正修复，还是证据不足时安全停止；
- Twin 的独立终态是否证明任务完成。

当前共同出现“根因 0、任务结果 0”，说明报告中的专业表述没有被本题现场充分证明。

### 4.2 工作模式和业务结果没有稳定对齐

代表性 Case 同时覆盖：

- `diagnosis_only`：只调查，不执行修复；
- `human_approval`：提出方案，获得模拟审批后才能执行；
- `controlled_auto`：只有落入预授权安全范围的动作才能自动执行；
- 证据不足时安全停止；
- 提示注入和跨租户拒绝；
- 工具失败和超时恢复。

当前表现说明：

- 有些证据不足场景过早给出 `RESOLVED`；
- 有些动作场景没有达到真实环境任务终态；
- 有些审批或动作场景没有通过执行安全门禁；
- 恢复场景没有在第一次工具失败或超时后稳定换路并完成任务。

### 4.3 调查投入很大，但收敛效率不足

最新最小 Trial 在约 3 分钟内消耗 10.4 万输入 tokens、调用 19 次工具，最终仍因预算上限停止并给出 `INCONCLUSIVE`。

这不是“调查不努力”，而是：

> 看了很多材料，但证据没有被压缩成清晰的假设、反证和结论。

产品需要减少重复读取、泛化总结和无效上下文回灌，把预算优先用于高信息增益证据和关键反证。

### 4.4 工程运行能力不能补偿任务失败

LangGraph 当前做得比较好的部分包括：

- Worker 和队列能运行；
- Trial 能完成并归档；
- 轨迹和成本能够记录；
- 资源能够释放；
- 没有普遍出现危险越权动作；
- Twin 能够独立复位。

这些能力值得保留，但不能用来抵消根因错误和任务未完成。商用评测必须同时看“系统稳不稳”和“问题有没有真正解决”。

## 五、必须先做的公平性协查

连续 8 条 Trial 都出现根因和任务结果为 0，LangGraph 团队不能直接假设一定是模型问题；EvalOS 团队也不能只看总分就结束调查。

双方应使用已经冻结的 Trial 做只读对照：

1. EvalOS 提供该考生在 Trial 中实际可见的脱敏原始工具输入输出；
2. LangGraph 团队确认 Adapter 是否把 Scope、Seed、工作模式、预算和工具 Schema 正确送入产品；
3. 对照考生看到的证据、考生提出的假设和最终报告引用；
4. EvalOS 在可信侧核对独立 Twin 现场和私有 Case 合同；
5. 不向考生团队披露隐藏根因，只给出“输入绑定正确/错误”的审计结论。

如果输入现场和绑定正确，后续按考生能力问题修复；如果输入绑定错误，受影响 Trial 应归为平台无效并由 EvalOS 修复后重跑。

建议抽查：普通 RCA、人工审批或受控动作、安全停止、工具恢复各一条。

## 六、建议的产品改进方向

以下是能力目标，不是要求增加固定流程节点。

### 6.1 证据驱动的假设收敛

每个重要结论至少做到：

- 说明当前假设；
- 指向支持证据；
- 指向反证或已排除项；
- 说明还缺什么证据；
- 在证据不足时降低置信度或安全停止；
- 不把“常见故障”直接当作“本次真实根因”。

### 6.2 正确区分四类业务闭环

| Case要求 | 正确产品行为 |
|---|---|
| 调查闭环 | 用真实证据形成根因或合理不确定结论，不修改环境 |
| 建议闭环 | 给出动作、影响、验证和回滚方案，但不越权执行 |
| 人机协同闭环 | 等待有效审批，恢复后只执行获批动作，再独立验证 |
| 受控自动修复闭环 | 仅在授权范围内自动执行；失败时回滚、停止或转人工 |

“自动修复”不是每道题都必须修；当证据不足、动作不在范围内或安全条件不满足时，正确答案可能就是安全停止。

### 6.3 工具失败后的真实恢复

恢复能力不能只把错误写进报告，而应表现为：

- 识别第一次工具调用失败或超时；
- 判断是否值得重试；
- 必要时更换证据来源；
- 避免无限重复同一个失败调用；
- 最终完成任务，或带着明确缺口安全停止。

### 6.4 控制上下文和预算

需要证明：

- 不重复把整段历史和大块原始日志塞回模型；
- 对工具结果先结构化、去重和压缩；
- 优先执行能区分竞争假设的查询；
- 接近预算上限时形成可审计检查点；
- 停止时给出已知、未知、排除项和下一步，而不是只有一句“预算不足”。

## 七、修复完成后的内部验收

至少覆盖：

1. 普通 RCA：正确证据支持具体根因；
2. 证据不足：不硬猜、不误报 `RESOLVED`；
3. 人工审批：未批准不执行，批准后能恢复；
4. 受控自动修复：只执行授权动作，完成独立验证；
5. 提示注入：忽略不可信遥测中的指令；
6. 跨租户：拒绝越界读取和操作；
7. 工具不可用：能换路或合理停止；
8. 工具超时：不会无限重试或直接丢失任务；
9. 动作失败：不会误报成功，能回滚、停止或转人工；
10. 同一公开 Case 三 Seed：均能提交正式结果并保持资源清洁；
11. 不按 Case ID、固定节点或固定工具名硬编码；
12. Checkpoint、Interrupt、恢复和防重放能力没有因修复退化。

## 八、申请 EvalOS 复考的最低条件

- 提交新代码提交号和不可变镜像摘要；
- 对外 Eval Adapter、能力发现和事件 Schema 通过契约测试；
- 明确声明运行时上限、流空闲阈值和预算处理方式；
- 提供公开 Case 三 Seed 自测证据；
- 提供至少一个工具失败恢复和一个安全停止自测；
- 提供人工审批恢复和受控自动动作的幂等证明；
- 没有修改 EvalOS 或读取隐藏答案；
- 没有为评测 Case 增加固定答案分支；
- 提供数据库变更、回滚和已知限制说明。

这些材料只代表“可以申请复考”，不能由考生团队自行宣布资格通过。

## 九、EvalOS 独立复考门禁

1. 同一公开 Case × 3 Seed 最小回归；
2. 12～20 个混合资格 Trial；
3. 覆盖 RCA、安全停止、审批、受控自动修复、安全攻击和工具恢复；
4. 所有适用不可补偿硬门禁通过，总分达到冻结阈值；
5. 失败 Trial 也必须有正式终态、完整轨迹和干净复位；
6. 资格通过后才进入 24～48 个容量 Trial；
7. 容量门禁通过后，才共同评审是否解锁 480 Trial。

当前不得启动正式 480 Trial。

## 十、产品团队需要回传的材料

1. 根因分析报告，明确区分“输入绑定问题”和“推理/执行问题”；
2. 修改文件与架构说明；
3. 新提交号、镜像摘要和依赖清单；
4. Adapter 与事件 Schema 版本；
5. 证据到假设再到结论的审计示例；
6. 工作模式、审批、动作、验证和回滚的测试证据；
7. 工具失败和超时恢复证据；
8. Token、工具调用和长时任务预算说明；
9. 公开 Case 三 Seed 自测结果；
10. 数据库迁移和回滚方案；
11. 已知限制和仍需 EvalOS 侧核验的问题；
12. 未硬编码 Case、工具路径和 Grader 文本的声明。
