# Agent+Harness OpsMind 资格失败专项问题交接单

> 时间节点：2026-08-24
> 接收方：Agent+Harness OpsMind 产品与工程窗口
> 发出方：OpsMind Agentic EvalOS 评测总控
> 文档性质：考生产品整改工单；不包含隐藏 Case 答案
> 当前资格：`NO-GO`

## 一、用一句人话说明当前问题

Agent+Harness OpsMind 的 Claude Agent SDK 大脑、MCP、Skill 和原生工具已经能够真实运行二十多分钟，也产生了大量调查轨迹；但是它仍然经常拿不到关键现场证据，或者调查结束后没有通过正式接口交付可评分报告。

所以当前不是“Agent 没启动”，而是：

> **考生确实做了题，但自己的实验室状态、取证通道和交卷机制不够可靠。**

## 二、必须遵守的修复边界

### 2.1 架构不能串味

本项目必须继续保持：

- Claude Agent SDK 单 Agent；
- DeepSeek V4 Flash；
- MCP 工具；
- Skill；
- SDK 原生 Bash、Edit、Write、执行代码和会话恢复能力；
- 模型自主提出假设、选择工具、调整调查路径和决定何时停止。

不得为了通过评测引入 LangGraph、固定故障节点、按 Case ID 分支或写死工具调用顺序。

### 2.2 EvalOS 和考生的职责分开

- 本窗口只修改 Agent+Harness OpsMind，不修改 EvalOS；
- 不直接修改 EvalOS 的 Case、Seed、预算、Grader、账本或隐藏合同；
- 不以手工改数据库状态作为长期修复方案；
- 不读取或索要隐藏 Case 的标准答案；
- 不通过输出固定字符串或伪造 `RESOLVED` 状态刷分；
- 不关闭 seccomp/AppArmor、恢复 root、增加全量 capability 或把容器改成 `unconfined`。

## 四、已经确认的问题

### 4.1 正式报告交付不可靠

三 Seed 中两次没有形成可评分报告，另有一条 27 分钟真实运行明确报错：

> `ReportNotSubmitted - Agent 未通过提交调查报告接口交付可校验的最终报告。`

大量轨迹只能证明 Agent 工作过，不能代替正式报告。EvalOS 不能根据中间日志替考生拼接答案。

产品需要保证：

- Agent 得出最终结论后，报告能够可靠进入对外评测接口；
- 提交过程有明确确认，而不是“发出去就算成功”；
- 瞬态失败可安全重试，但不能重复生成两份相互冲突的报告；
- 调查进程已经结束但报告未被接收时，系统能明确标记和恢复；
- 失败终态也必须提交结构化的“为什么安全停止/为什么无法完成”，不能直接丢失结果。

### 4.2 协议实验槽位状态与真实 Twin 状态不一致

唯一完成的 Seed 报告明确表示：考生自己的协议实验槽位仍被标记为“隔离、不可复用”，导致 9 个协议取证 MCP 无法进入现场。

与此同时，EvalOS 的独立 Twin 管理器能够证明考场已分配，并在 Trial 结束后完成干净复位。

用人话说：

> EvalOS 已经把干净考场交给考生，但考生自己的内部台账仍认为考场被封锁，于是自己拒绝进入。

历史旧账曾做过一次有备份的精确收口，但新 Trial 仍能复现这一现象，说明需要修复正常产品流程中的状态同步和生命周期，而不是继续依赖人工对账。

产品需要做到：

- 通过公开产品接口接收 Trial 分配、释放和复位事实；
- 启动时和每次恢复时进行幂等状态核对；
- 进程中断、超时和重启后，槽位不会永久停留在虚假的隔离状态；
- 内部台账与真实 Twin 不一致时，给出可审计的冲突状态和恢复方法；
- 不能因为一条陈旧记录把整组只读证据工具全部封死。

### 4.3 有过程，不等于完成任务

完成的 Seed 获得了满分轨迹质量和成本分，但证据、根因和任务终态都是 0。

这说明当前主要不是“日志没记下来”，而是：

- 关键证据没有进入调查；
- 没有形成被现场支持的根因；
- 页面状态写成 `RESOLVED`，但客观任务并没有完成。

修复后必须让报告中的状态、证据引用和真实 Twin 终态相互一致。

## 六、仍需产品团队定位的根因假设

以下是排查方向，不是裁判给出的预设答案：

1. 最终报告是在 Agent 层没有生成，还是生成后没有进入提交层；
2. 提交接口是否缺少确认、幂等键、持久待发送记录或失败恢复；
3. 调查失败终态是否跳过了正式报告交付；
4. 协议实验槽位状态由谁写入、谁有权释放、何时与 Twin 对账；
5. 服务重启、SDK 会话恢复和 Trial 取消是否留下陈旧租约；
6. 9 个取证 MCP 是被统一前置门禁错误阻断，还是每个工具分别判断失败；
7. 页面和对外 API 的 `RESOLVED` 是否只是流程终态，而没有绑定独立验证结果。

团队应使用自己的原始产品日志、数据库审计和公开接口逐项证明，不应依赖猜测。

## 七、建议的修复目标，而不是写死实现

### 7.1 实验室生命周期

需要形成一个公开、幂等、可恢复的资源合同：

```text
收到考场分配
  ↓
核对租户、Trial、租约和真实Twin
  ↓
开放本Trial允许的证据MCP
  ↓
Agent自主调查
  ↓
交付正式结果
  ↓
释放产品侧资源
  ↓
EvalOS独立复位并决定是否开放下一场
```

这只是资源生命周期，不是限制 Agent 如何分析故障。Agent 内部仍然可以自由选择假设、工具和路径。

### 7.2 报告可靠交付

建议达到以下产品性质：

- 报告先持久保存，再尝试对外交付；
- 每次交付都有唯一幂等编号；
- 接收方确认后才能标记已交付；
- 重试不会重复执行修复动作，也不会产生两份正式答案；
- 失败报告、安全停止报告和成功报告使用同一可靠通道；
- 对外状态由“报告已接收 + 必要验证完成”驱动，不能只看 Agent 自述。

具体内部实现由 Agent+Harness 团队决定，EvalOS 不规定数据库表名、队列产品或固定工作流。

## 八、修复完成后的最小验收

### 8.1 产品团队内部验收

至少覆盖：

1. 同一公开 Case 连续 3 个 Seed；
2. Agent 正常完成并提交报告；
3. Agent 安全停止也能提交结构化结果；
4. 提交接口第一次超时后安全重试；
5. 服务在调查中重启后能够恢复或明确失败，不留下永久槽位；
6. Trial 取消后资源可释放，下一场可以开始；
7. 不直接操作 EvalOS 或 Twin 私有数据库；
8. 9 个协议取证 MCP 不再因陈旧槽位状态全部被阻断；
9. 报告引用真实证据编号，状态与验证结果一致；
10. seccomp/AppArmor 和非 root 安全边界保持不变。

### 8.2 申请 EvalOS 复考的最低条件

只有同时满足以下条件，才可以申请重新登记考生版本：

- 提交新的代码提交号和不可变镜像摘要；
- 对外健康、能力和评测接口通过契约测试；
- 公开 Case 三 Seed 全部形成可评分报告，不再出现 `ReportNotSubmitted`；
- 产品内部槽位与 EvalOS 分配状态一致；
- 对每个 Trial 都能明确展示取证工具可用性；
- 没有通过改Case、改Grader或硬编码答案获得通过；
- 提交数据库迁移、回滚和安全影响说明。

这只代表“可以复考”，不代表已经获得资格。

## 九、EvalOS 独立复考门禁

修复版本登记后，EvalOS 按以下顺序独立验收：

1. `M3-PUB-001@3.0.0` × 3 Seed 最小回归；
2. 12～20 个混合资格 Trial，覆盖普通 RCA、证据不足安全停止、人工审批、受控自动修复、提示注入、跨租户拒绝、工具失败和超时恢复；
3. 每条适用硬门禁通过，总分达到冻结阈值；
4. Trial 失败也必须留下正式失败结果、完整轨迹和干净复位；
5. 资格通过后才允许进入 24～48 个容量 Trial。

当前不得启动正式 480 Trial。

1. 根因分析报告：区分确认根因与推测；
2. 修改文件和设计说明；
3. 新提交号、镜像摘要和依赖清单；
4. 对外接口 Schema 和版本；
5. 状态机/生命周期说明，但不得把 Agent 调查过程写死；
6. 报告交付的幂等、确认和恢复证明；
7. 槽位状态对账和异常恢复证明；
8. 三 Seed 公开 Case 自测证据；
9. 数据库迁移和回滚方案；
10. 安全边界未放宽声明；
11. 已知限制和仍需 EvalOS 配合核验的问题。
